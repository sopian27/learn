# Course Roadmap

## Course Information

* Course Name: Work Management — dari 0 sampai Expert
* Category: Work Management (Domain: work-management — lihat `domains/work-management/DOMAIN.md`)
* Difficulty: Level 0 (belum punya sistem kerja, jadwal reaktif/berantakan) → Expert (mampu menjalankan & mempertahankan satu Personal Work Operating System tanpa pengawasan, disiplin bukan karena tenggat)
* Estimated Duration: 9 modul, 4 lesson/modul, ~30-40 menit/lesson. Pace disesuaikan sambil jalan.
* Prerequisites: Tidak ada prasyarat teknis. Butuh akses ke workload nyata sendiri (kalender kerja, daftar tugas aktual) untuk Applied Practice, sesuai `domains/work-management/DOMAIN.md` bagian "Applied Practice Definition" — kalau belum ada workload aktif dipakai skenario realistis berlabel jelas.

---

# Learning Objectives

* [ ] Memilih dan menjalankan satu framework prioritas (bukan sekadar tahu nama-namanya) untuk memutuskan apa dikerjakan duluan
* [ ] Membangun kalender timeboxed dan estimasi tugas yang presisinya membaik dari waktu ke waktu (estimate-vs-actual mengecil)
* [ ] Menjaga fokus lewat protokol deep-work dan mematahkan procrastination pakai kerangka berbasis riset, bukan motivasi sesaat
* [ ] Menegakkan batas jam kerja harian dan mencegah kerja malam/akhir pekan lewat desain sistem, bukan pengecualian kasus-per-kasus
* [ ] Mengomunikasikan progres sejelas GitLab/Basecamp handbook-level async update sehingga atasan/stakeholder tidak perlu menagih status
* [ ] Menghasilkan satu Personal Work Operating System lengkap sebagai Capstone Project, dijalankan nyata minimal 2 minggu

# Course Modules

## Module 1 — Foundations: Energy, Time, and Why Systems Beat Willpower

Description: Fondasi sebelum menyentuh tool/teknik apapun — kenapa jadwal reaktif gagal, dan kenapa desain sistem selalu mengalahkan niat baik/motivasi.

Lessons:

* [ ] 1.1 Time management vs energy management — kenapa dua orang dengan jam kerja sama bisa punya output sangat berbeda
* [ ] 1.2 Reactive work vs designed work — anatomi hari kerja yang "penuh tapi tidak produktif"
* [ ] 1.3 Willpower sebagai sumber daya terbatas — kenapa sistem/lingkungan harus menggantikan disiplin manual
* [ ] 1.4 Audit dasar: memetakan satu minggu kerja aktual (kalender + catatan) sebelum mengubah apapun

Mini Project: Audit satu minggu kerja aktual (atau skenario realistis) — kalender nyata dipetakan jam per jam, ditandai mana waktu terdesain vs reaktif.

Status: Not started

---

## Module 2 — Prioritization Frameworks

Description: Kerangka untuk memutuskan "apa duluan" secara konsisten, bukan berdasarkan siapa yang paling berisik minta duluan.

Lessons:

* [ ] 2.1 Eisenhower Matrix (urgent vs important) — dan jebakan paling umum: menghabiskan hari di kuadran "urgent-not-important"
* [ ] 2.2 MoSCoW (Must/Should/Could/Won't) untuk daftar tugas dengan banyak stakeholder
* [ ] 2.3 ICE/RICE scoring untuk memilih di antara opsi yang sama-sama "penting"
* [ ] 2.4 Memilih SATU framework sebagai default pribadi — kriteria kapan ganti framework, kapan cukup stick dengan satu

Mini Project: Prioritaskan seluruh daftar tugas aktif minggu ini (atau skenario realistis) memakai satu framework pilihan, dengan justifikasi kenapa framework itu dipilih.

Status: Not started

---

## Module 3 — Timeboxing & Calendar Design

Description: Mengubah daftar prioritas Module 2 jadi slot waktu konkret di kalender — dari niat ke komitmen yang bisa dicek.

Lessons:

* [ ] 3.1 Time blocking dasar — setiap tugas penting dapat slot kalender, bukan cuma to-do list terpisah dari kalender
* [ ] 3.2 Pomodoro Technique (Francesco Cirillo) — timeboxing level mikro untuk fokus per sesi
* [ ] 3.3 Appetite-based timeboxing ala Shape Up (Basecamp) — menetapkan budget waktu SEBELUM scoping tugas, bukan sesudah
* [ ] 3.4 Buffer time & realistic scheduling — kenapa kalender 100% penuh selalu gagal, berapa persen buffer yang wajar

Mini Project: Kalender timeboxed satu minggu penuh (atau skenario realistis) berbasis hasil prioritas Module 2, termasuk buffer time eksplisit.

Status: Not started

---

## Module 4 — Task Estimation & Calibration

Description: Kenapa manusia (termasuk engineer berpengalaman) secara sistematis salah menaksir waktu, dan cara mengoreksinya lewat data sendiri.

Lessons:

* [ ] 4.1 Planning fallacy — bukti riset kenapa estimasi optimis-bias, dan kenapa "pengalaman" saja tidak menyembuhkannya
* [ ] 4.2 PERT estimation (optimistic/pessimistic/most-likely) untuk tugas dengan ketidakpastian tinggi
* [ ] 4.3 Story points & planning poker ala Agile — estimasi relatif vs estimasi absolut, kapan masing-masing lebih akurat
* [ ] 4.4 Membangun calibration log — mencatat estimate vs actual setiap tugas untuk mempersempit bias personal dari waktu ke waktu

Intermediate Project: Calibration log berjalan 2 minggu — setiap tugas nyata dicatat estimasi (pakai PERT atau story points) vs waktu aktual, dengan analisis pola bias sendiri (selalu under-estimate berapa persen, dsb).

Status: Not started

---

## Module 5 — Focus & Deep Work

Description: Menjaga kualitas jam kerja yang sudah dijadwalkan Module 3 — sesi timeboxed tidak berguna kalau isinya setengah fokus.

Lessons:

* [ ] 5.1 Deep Work vs shallow work (Cal Newport) — kenapa membedakan dua ini menentukan output riil, bukan jam duduk
* [ ] 5.2 Attention residue — kenapa multitasking/context-switching punya biaya tersembunyi yang lebih mahal dari terlihat
* [ ] 5.3 Merancang ritual & lingkungan fokus — cue-based trigger untuk masuk mode deep work lebih cepat
* [ ] 5.4 Distraction log — mengukur sumber gangguan nyata (notifikasi, kolega, self-interruption) sebelum mendesain countermeasure

Mini Project: Log 3 sesi deep-work nyata minggu ini — durasi, gangguan yang terjadi, dan satu perubahan lingkungan/ritual yang diuji untuk sesi berikutnya.

Status: Not started

---

## Module 6 — Procrastination: Psychology & Countermeasures

Description: Menangani penundaan berbasis riset psikologi (Piers Steel, Tim Pychyl), bukan nasihat "cuma butuh motivasi".

Lessons:

* [ ] 6.1 Procrastination Equation — expectancy, value, impulsiveness, delay — kenapa tugas tertentu selalu ditunda
* [ ] 6.2 Temporal discounting — kenapa otak sistematis mengecilkan nilai reward jangka panjang dibanding kenyamanan sekarang
* [ ] 6.3 Countermeasure berbasis riset: 2-minute rule, implementation intentions ("if-then planning"), temptation bundling
* [ ] 6.4 Membedakan procrastination biasa dari overload/burnout — kapan penundaan sebenarnya sinyal beban kerja tidak realistis (nyambung ke Module 4 & 7)

Mini Project: Identifikasi 1 tugas yang konsisten ditunda, analisis pakai Procrastination Equation, terapkan 1 countermeasure selama 1 minggu, catat hasilnya.

Status: Not started

---

## Module 7 — Work-Hour Boundaries & Preventing Night/Weekend Work

Description: Menegakkan batas jam kerja by design — merujuk `domains/work-management/DOMAIN.md` bagian "Trusted Sources" (GitLab non-linear workday, Basecamp calm boundaries) untuk praktik nyata perusahaan, bukan teori kosong.

Lessons:

* [ ] 7.1 Kenapa "kerja lebih lama" gagal secara matematis dalam knowledge work — hukum diminishing/negative returns pada jam kerja panjang
* [ ] 7.2 Shutdown ritual (Cal Newport) — prosedur konkret menutup hari kerja supaya otak benar-benar berhenti, bukan cuma laptop ditutup
* [ ] 7.3 Mendesain "stop-time" harian sebagai aturan sistem, bukan niat — termasuk cara bilang "tidak" ke request mendadak tanpa merasa bersalah
* [ ] 7.4 Mencegah kerja malam & akhir pekan secara spesifik — audit pola pelanggaran sendiri, dan pagar teknis/sosial yang mencegahnya berulang (notifikasi, kesepakatan tim, kalender)

Mini Project: Boundary contract tertulis (jam stop harian + aturan no-weekend) dijalankan 1 minggu penuh, dengan adherence log harian (dilanggar/tidak, dan kenapa kalau dilanggar).

Status: Not started

---

## Module 8 — Progress Communication

Description: Mengomunikasikan progres async-first ala GitLab handbook — supaya transparansi menggantikan kebutuhan orang menagih status, sekaligus melindungi batas jam kerja Module 7 (tidak perlu online 24 jam untuk dianggap "responsif").

Lessons:

* [ ] 8.1 Async-first communication (GitLab handbook) — kenapa update tertulis terdokumentasi mengalahkan update lisan/chat real-time untuk progres kerja
* [ ] 8.2 Anatomi status update yang baik: apa yang selesai, apa yang blocked, apa langkah berikutnya — format singkat yang bisa dibaca dalam 30 detik
* [ ] 8.3 Frekuensi & kanal update — harian vs mingguan, kapan sync check-in benar-benar perlu vs bisa digantikan tulisan
* [ ] 8.4 Mengomunikasikan blocker & keterlambatan secara proaktif — kenapa silent struggling lebih merusak trust daripada mengaku telat lebih awal

Mini Project: Tulis 5 status update harian (atau skenario realistis) untuk satu tugas/proyek nyata, memakai format dari 8.2, lalu self-review pakai kriteria "Communicability" di `domains/work-management/DOMAIN.md` bagian "Review Style".

Status: Not started

## Module 9 — Capstone: Personal Work Operating System

Description: Integrasi seluruh modul jadi satu sistem yang benar-benar dijalankan, bukan dokumen teori — mengikuti `domains/work-management/DOMAIN.md` bagian "Project Tiers" untuk definisi Capstone di domain ini.

Lessons:

* [ ] 9.1 Menyusun struktur Personal Work Operating System — menggabungkan framework prioritas, kalender timeboxed, sistem estimasi/kalibrasi, protokol fokus, countermeasure procrastination, boundary contract, dan template update progres jadi satu sistem koheren
* [ ] 9.2 Menjalankan sistem selama 2 minggu penuh dengan workload nyata (atau skenario realistis kalau belum ada workload aktif)
* [ ] 9.3 Retro & kalibrasi ulang — memakai kriteria `domains/work-management/DOMAIN.md` bagian "Review Style" (Realism, Adherence, Calibration, Communicability) untuk merevisi sistem berdasarkan data 2 minggu, bukan asumsi awal
* [ ] 9.4 Finalisasi dan penyimpanan dokumen sistem ke `portofolio/`, memenuhi bar "portfolio-worthy" di `standards/UNIVERSAL_STANDARDS.md`

Capstone Project: Satu dokumen Personal Work Operating System lengkap — prioritization framework, kalender timeboxed, estimation calibration log, focus protocol, procrastination countermeasures, boundary contract, dan template komunikasi progres — dijalankan nyata minimal 2 minggu, direvisi berdasarkan retro, disimpan ke `portofolio/`. Review memakai `domains/work-management/DOMAIN.md` bagian "Review Style" (Realism, Adherence, Calibration, Communicability) di atas Universal Review Rubric (`ai-los/CORE_LOS.md`), plus Assessment Form-nya (weekly self-audit) dan sesi tanya-jawab mempertahankan setiap keputusan desain sistem.

Status: Not started
