# Work Management — Domain Pack

## Domain Name

Work Management

## Scope

Individual-level management of time, tasks, focus, and boundaries for a knowledge worker: timeboxing, prioritization frameworks, task estimation, focus/deep work, procrastination, daily/weekly work-hour boundaries, progress communication, and preventing night/weekend work creep. Perspective is ONE person managing their own workload, not team process. Does NOT cover team-level Agile ceremonies, sprint planning, or Scrum roles (that's `courses/scrum-master`), career branding/job search (`courses/career-reinvention`), or personal finance (`courses/personal-finance`). Overlaps `domains/software-engineering` only where the learner's real tasks happen to be coding tasks — the frameworks taught here are role-agnostic.

## Trusted Sources / Research Priority

1. Cal Newport — *Deep Work*, *Slow Productivity*, *Digital Minimalism* (focus systems, shutdown ritual, attention residue)
2. David Allen — *Getting Things Done* (GTD) (capture/clarify/organize task system, prioritization)
3. GitLab Handbook (handbook.gitlab.com, public, real company policy) — async-first communication, non-linear workday, explicit no-expectation-outside-working-hours boundary
4. Basecamp/37signals — *It Doesn't Have to Be Crazy at Work*, *Shape Up* (appetite-based timeboxing, calm boundaries)
5. Procrastination research — Piers Steel (*The Procrastination Equation*), Tim Pychyl (Carleton University Procrastination Research Group) — evidence-based, not folk psychology
6. Steve McConnell — *Software Estimation: Demystifying the Black Art*, plus Agile estimation practice (PERT, planning poker, story points) for task-estimation calibration
7. Stephen Covey — *7 Habits*, Time Management Matrix (Eisenhower Matrix lineage) for prioritization
8. Harvard Business Review — cross-check contemporary org-level practice on the above, per `standards/UNIVERSAL_STANDARDS.md`'s Vetting a Source bar

Never build a lesson from a single listicle blog post — always triangulate against at least one primary source (1-7) above.

## Applied Practice Definition

Every lesson produces or updates a real artifact run against the learner's own actual workload — not a hypothetical to-do list. Examples: a timeboxed weekly calendar, a prioritized task list (Eisenhower/MoSCoW), an estimate-vs-actual log for a real task, a focus-session log (Pomodoro/deep-work block) with distraction notes, a written status update for a real or realistic stakeholder, a boundary contract (stop-work time, no-weekend rule) with a tracked adherence log. If the learner has no live workload to apply a lesson to, a clearly-labeled realistic scenario is used instead.

## Project Tiers

- **Mini Project** (per module): one artifact for one week or one task — e.g. one week's timeboxed calendar, or one task's estimate-vs-actual log.
- **Intermediate Project** (per major section): a combined system run across a real 2-week window — e.g. prioritization + estimation used together across a real personal sprint.
- **Capstone / Portfolio Project** (end of course): a complete "Personal Work Operating System" — timeboxing calendar, prioritization method, estimation calibration log, focus protocol, procrastination countermeasures, boundary contract, and progress-communication template — run for at least 2 real weeks, revised after a retro, saved to `portofolio/`.

## Review Style

On top of the Universal Review Rubric (Strengths / Weaknesses / Actionable Improvements / Score 0-100), every artifact review additionally checks:

- **Realism** — built from the learner's actual tasks/calendar, not a hypothetical
- **Adherence** — did the boundary/focus rules actually hold this week (tracked, not just designed on paper)?
- **Calibration** — is estimate-vs-actual variance shrinking over successive attempts?
- **Communicability** — could a manager/stakeholder understand real progress from the status update alone, without follow-up questions?

## Assessment Form

A short concept-check quiz after each lesson's theory portion, plus a weekly self-audit against the Adherence criterion above (did the learner work past stop-time, or on a night/weekend, and why) before that week's Applied Practice artifact is submitted for review.

## Practitioner Reference Frame

Compare four different lenses on the same problem: Cal Newport's academic/individual deep-work framing, GitLab/Basecamp's company-handbook-level async and boundary practice, Agile/software-engineering estimation norms (planning poker, PERT), and David Allen's GTD individual-productivity system. Use these four to answer "how would each of them handle this specific work-management problem".

## Domain-Specific Standards

None yet — `standards/UNIVERSAL_STANDARDS.md` is sufficient. Add `domains/work-management/standards/` only if a recurring domain-specific rigor rule emerges.

## Domain Goal

Build and actually run one working Personal Work Operating System: a system the learner can operate without willpower-dependent effort, that protects non-work hours by design (not by exception), and that communicates real progress clearly enough that a manager/stakeholder never has to chase a status update.
