### Exercise / Task

**Bagian 1 — Perbaiki kode berikut.** Class ini "jalan" tapi melanggar idiom generics yang dibahas di atas. Identifikasi tiap pelanggaran dan perbaiki, sertakan justifikasi (kenapa versi baru lebih benar, bukan cuma "supaya tidak warning"):

```java
public class DataBucket {
    private List items = new ArrayList(); // (a)

    public void addAll(List source) { // (b)
        for (Object o : source) items.add(o);
    }

    public static void copyInto(List dest, List src) { // (c)
        for (Object o : src) dest.add(o);
    }

    public boolean sameType(List a, List b) { // (d)
        return a.getClass() == b.getClass(); // dimaksudkan cek "elemen list sama tipe?"
    }
}
```

fix :
public class DataBucket<T> {

    private final List<T> items = new ArrayList<>(); // (a)

    public void addAll(List<? extends T> source) { // (b)
        for (T item : source) {
            items.add(item);
        }
    }

    public static <T> void copyInto(
            List<? super T> dest,
            List<? extends T> src) { // (c)

        for (T item : src) {
            dest.add(item);
        }
    }

    public boolean sameType(List<?> a, List<?> b) { // (d)
        // Tidak bisa menentukan tipe elemen generic dengan getClass().
        // Implementasi harus menggunakan pendekatan lain jika memang
        // ingin membandingkan tipe elemen.
        throw new UnsupportedOperationException(
                "Generic element type cannot be determined from List.getClass()");
    }
}

(a). DataBucket<String> bucket = new DataBucket<>();
    berarti items hanya menerima String.
    bucket.items.add("hello");

(b). public void addAll(List<? extends T> source) {
        for (T item : source) {
            items.add(item);
        }
    }

    Contoh:
    DataBucket<Number> bucket = new DataBucket<>();
    List<Integer> integers = List.of(1, 2, 3);
    bucket.addAll(integers);

    Ini valid karena:
    Integer extends Number

(a). public static <T> void copyInto(
            List<? super T> dest,
            List<? extends T> src) {


        for (T item : src) {
            dest.add(item);
        }
     }

    Contoh:
    List<Integer> src = List.of(1, 2, 3);
    List<Number> dest = new ArrayList<>();
    DataBucket.copyInto(dest, src);

    Compiler dapat menentukan:

    T = Integer

    src  = List<? extends Integer> → List<Integer>
    dest = List<? super Integer>  → List<Number>

(a). getClass() tidak bisa digunakan untuk mengecek apakah generic element type dari dua List sama, karena Java menerapkan type erasure. getClass() hanya mengetahui runtime class dari object List, bukan tipe generic elemennya.

Perbaikan:

public boolean sameType(List<?> a, List<?> b) {
    // Tidak dapat menentukan generic element type melalui getClass().
    throw new UnsupportedOperationException(
        "Cannot determine generic element type at runtime"
    );
}

Justifikasi: List<String> dan List<Integer> tidak dibedakan oleh getClass(). Jika memang perlu mengecek tipe elemen saat runtime, tipe tersebut harus diberikan secara eksplisit, misalnya melalui Class<T>.

**Bagian 2 — Jelaskan singkat.** Kenapa `public static <T> void foo(List<T> a, List<T> b)` TIDAK bisa dipanggil dengan `foo(listOfString, listOfInteger)` walau keduanya sama-sama `List`? Kaitkan jawaban dengan konsep *invariance* generic Java (bukan istilah dari Theory di atas — silakan cari 1 sumber resmi/terpercaya lalu jelaskan dengan kata-kata sendiri).

    Karena generic Java bersifat invariant: Walaupun String dan Integer sama-sama turunan Object, List<String> bukan turunan List<Object> begitupun dengan List<Integer>. Jadi List<String> dan List<Integer> adalah dua tipe yang berbeda dan tidak memiliki hubungan subtype satu sama lain.

    Pada:

    public static <T> void foo(List<T> a, List<T> b)

    kedua parameter harus menggunakan T yang sama. listOfString mengharuskan T = String, sedangkan listOfInteger mengharuskan T = Integer. Tidak ada satu T yang membuat keduanya cocok sebagai List<T>. Jadi List<String> ≠ List<Integer>, meskipun keduanya sama-sama List.

### Interview Questions

1. **Kenapa Java tidak bisa membuat array dari generic type (`new T[]`) secara langsung?**
   Arahkan jawaban ke: array di Java itu *reified* (tahu tipe elemennya saat runtime, dicek tiap kali `.set()`), sedangkan generic type di-erase saat runtime — kombinasi keduanya bisa menimbulkan heap pollution yang seharusnya dicegah generics, bukan diizinkan lewat pintu belakang array.
        Karena array reified: runtime tahu tipe elemennya dan bisa melakukan pengecekan saat .set(). Sementara generic T mengalami type erasure, sehingga runtime tidak tahu T sebenarnya apa. Menggabungkan keduanya bisa membuka peluang heap pollution, yang justru ingin dicegah oleh generics.

2. **Jelaskan PECS dengan contoh dari kode yang pernah Anda tulis (atau `Collections.copy`) — kenapa aturannya bukan sekadar hafalan?**
   Arahkan ke penjelasan by-reasoning: producer (`extends`) aman dibaca karena compiler tahu apa pun tipe aslinya pasti subtype T; consumer (`super`) aman ditulis karena compiler tahu supertype pasti bisa menampung T.
        PECS = Producer Extends, Consumer Super.

        ? extends T → producer, karena kita hanya membaca. Apa pun tipe konkretnya, elemennya pasti merupakan subtype T, sehingga aman diperlakukan sebagai T.
        ? super T → consumer, karena kita menulis T. Compiler menjamin tipe tersebut adalah T atau supertype-nya, sehingga pasti bisa menampung T.

        Jadi PECS bukan sekadar hafalan; arahnya ditentukan oleh bagaimana collection digunakan: dibaca atau ditulis.

3. **Kalau generic di-erase saat runtime, kenapa `List<String>.get()` tetap mengembalikan `String`, bukan `Object`, tanpa Anda cast manual?**
   Arahkan ke: compiler menyisipkan cast implisit di titik pemanggilan (compile-time), bukan JVM yang tahu tipe generic saat runtime — ini yang membuat generics terasa "type-safe" walau informasinya sudah hilang di bytecode.
        Karena compiler menyisipkan cast secara implisit pada titik pemanggilan.

        Secara konsep:

        String s = list.get(0);

        diproses seperti:

        String s = (String) list.get(0);

        Jadi JVM tidak mengetahui generic type String. Type safety tersebut dibantu oleh compiler sebelum bytecode dijalankan.
