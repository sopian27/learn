### Exercise / Task

**Bagian 1 — Hitung headroom.** Sebuah service akan di-deploy ke container Kubernetes dengan `resources.limits.memory: 1Gi`. Service ini punya thread pool tetap berukuran 200 thread (dari keputusan Module 2), dan tim yang menyiapkan awalnya mengusulkan konfigurasi berikut:

```
-Xmx900m -Xss1m
(tidak ada -XX:MaxMetaspaceSize, tidak ada flag heap dump)
```

Hitung secara kasar: berapa total memori yang dibutuhkan **di luar** heap hanya dari thread stack saja (`-Xss` × jumlah thread), lalu jelaskan kenapa konfigurasi ini berisiko tinggi `OOMKilled` walau `-Xmx` terlihat "aman" di bawah limit 1Gi. Usulkan konfigurasi flag pengganti yang lebih aman, dengan angka/pendekatan konkret (boleh pakai `MaxRAMPercentage` atau `-Xmx` tetap dengan margin yang Anda hitung sendiri — jelaskan kenapa memilih salah satu).

    thread stack : -Xss1m × 200 thread = 200 MiB
    Jadi, thread stack saja membutuhkan sekitar 200 MiB di luar heap.

    Heap maksimum = 900 MiB
    Thread stack  = 200 MiB
    --
    Total         = 1100 MiB

    1100 MiB > 1024 MiB, bahkan sebelum menghitung Metaspace, Code Cache, Direct Buffer, dan overhead native lainnya.

    Artinya, konfigurasi ini sudah berisiko OOMKilled hanya dari heap + thread stack.

    saran, Saya akan memilih MaxRAMPercentage agar konfigurasi lebih mudah menyesuaikan container limit :

    java \
    -XX:MaxRAMPercentage=65.0 -XX:InitialRAMPercentage=65.0 \    
    -XX:MaxMetaspaceSize=256m \                                   
    -Xss512k \                                                    

    -XX:+HeapDumpOnOutOfMemoryError \                             
    -XX:HeapDumpPath=/dumps \                                    
    -XX:+ExitOnOutOfMemoryError \                                 

    -Xlog:gc*:file=/logs/gc.log:time,uptime,level,tags \          ── OBSERVABILITY GC
        :filecount=5,filesize=50m \

    -jar app.jar

    Perkiraan:

    Heap maksimum ≈ 65% × 1024 MiB = 666 MiB
    Thread stack  = 512 KiB × 200 ≈ 100 MiB
    --
    Heap + stack ≈ 766 MiB

    -Xss1m × 200 thread = 200 MiB hanya untuk thread stack. Jika ditambah heap maksimum 900 MiB, totalnya sudah sekitar 1100 MiB, melebihi limit container 1 GiB, bahkan sebelum Metaspace dan native memory lainnya. Karena itu, -Xmx900m tidak aman hanya karena terlihat di bawah limit. Saya akan menggunakan MaxRAMPercentage dengan heap sekitar 65%, menurunkan stack ke 512 KiB jika sudah divalidasi aman, dan mengaktifkan heap dump serta exit-on-OOM untuk diagnosis dan recovery. Namun, angka final tetap harus divalidasi dengan pengukuran memory usage dan workload nyata.

**Bagian 2 — Audit startup command.** Diberikan startup command produksi berikut untuk sebuah **API service** biasa (bukan batch job, bukan trading system):

```
java -Xmx3800m -Xms256m -XX:+UseZGC -jar service.jar
```

Container yang menjalankannya punya limit memory 4Gi. Identifikasi **minimal 3 masalah** pada konfigurasi ini dengan merujuk ke konsep spesifik dari lesson ini (dan lesson-lesson sebelumnya di Module 3 kalau relevan), lalu tulis ulang command yang sudah diperbaiki lengkap dengan justifikasi tiap perubahan.

  masalah :
   1. -Xmx3800m terlalu agresif untuk container 4Gi

        Benar. 3800 MiB sudah sekitar 93% dari 4Gi (4096 MiB).

        Sisa hanya sekitar 296 MiB untuk:

        Thread stack
        Metaspace
        Code Cache
        Direct Buffer
        Native memory
        Overhead proses

        Koreksi: Masalahnya adalah heap terlalu dekat dengan limit container tanpa margin yang cukup.

  2. -XX:+UseZGC belum tentu pilihan terbaik
      
      ZGC dipilih ketika kebutuhan pause time sangat rendah dan heap besar, sedangkan G1GC biasanya menjadi pilihan awal untuk general-purpose backend.

  3. -Xms256m dan -Xmx3800m terlalu jauh

        -Xms256m
        -Xmx3800m

        Heap bisa berkembang sangat jauh dari 256 MiB ke 3800 MiB.

        Untuk production, lebih baik memory di prediksi saja terutama jika traffic sudah diperkirakan.

    4. Tidak ada proteksi dan observability

        -XX:+HeapDumpOnOutOfMemoryError
        -XX:+ExitOnOutOfMemoryError
        GC logging

        Akibatnya, ketika OOM terjadi, diagnosis menjadi lebih sulit.

    rekomendasi : 

        java \
        -XX:MaxRAMPercentage=75.0 \
        -XX:InitialRAMPercentage=75.0 \
        -XX:+UseG1GC \
        -XX:MaxGCPauseMillis=150 \
        -XX:+HeapDumpOnOutOfMemoryError \
        -XX:HeapDumpPath=/dumps \
        -XX:+ExitOnOutOfMemoryError \
        -Xlog:gc*:file=/logs/gc.log:time,uptime,level,tags:filecount=5,filesize=50m \
        -jar service.jar

    
    Konfigurasi awal terlalu agresif karena heap maksimum hampir memenuhi seluruh memory limit container, sementara non-heap memory belum diperhitungkan. Saya akan menggunakan sizing berbasis container limit, memilih G1GC sebagai baseline untuk API service, dan menambahkan observability serta recovery flags. Angka 75% adalah starting point, bukan angka sakral; finalnya harus divalidasi dengan workload dan memory metrics.

### Interview Questions

1. Kenapa production umumnya menyamakan `-Xms` dan `-Xmx`? Apa yang dikorbankan dan apa yang didapat dari keputusan ini?
    Production sering menyamakan -Xms dan -Xmx untuk membuat ukuran heap lebih predictable dan mengurangi kebutuhan JVM melakukan ekspansi heap saat aplikasi berjalan. Konsekuensinya, JVM membutuhkan lebih banyak memori sejak awal dan fleksibilitas untuk menggunakan heap kecil berkurang. Keuntungannya adalah perilaku memori lebih stabil, terutama pada service dengan traffic yang relatif predictable. Namun, ini bukan aturan wajib; pada container dengan memory limit ketat, kita tetap harus memperhitungkan non-heap memory.

2. Jelaskan kenapa `-XX:MaxRAMPercentage` dianggap lebih aman untuk deployment container dibanding `-Xmx` dengan angka tetap. Sertakan skenario konkret di mana angka tetap gagal.
 
    Kalau pakai `-Xmx` angka tetap (misalnya `-Xmx1800m`), begitu image yang sama dijalankan di environment dengan container limit berbeda (dev 512MB, staging 2GB, production 8GB), angka `-Xmx1800m` itu jadi tidak masuk akal di dua environment sekaligus — kekecilan di production (menyisakan memori nganggur), berpotensi terlalu besar di dev/staging. Solusi modern: `-XX:MaxRAMPercentage=75.0` (dan pasangannya `-XX:InitialRAMPercentage`, `-XX:MinRAMPercentage`) — JVM menghitung heap sebagai **persentase dari memori yang terlihat olehnya** (yaitu limit container, berkat container-awareness di atas), bukan angka absolut. Image Docker yang sama otomatis menyesuaikan diri ke limit container manapun dia dijalankan, tanpa perlu dikompilasi ulang atau di-override manual tiap environment.

    MaxRAMPercentage menghitung heap berdasarkan memori yang tersedia bagi JVM, yang pada JVM modern umumnya mempertimbangkan container limit, bukan selalu seluruh RAM host.

    Contoh:

    Container limit: 512 MiB
    MaxRAMPercentage=75
    Heap maksimum sekitar 384 MiB
    Sisa sekitar 128 MiB untuk non-heap dan kebutuhan proses lainnya.

3. Sebuah service menetapkan `-Xmx` sebesar 85% dari limit container, tanpa flag lain. Container tetap `OOMKilled` sesekali walau metrik heap usage dari monitoring terlihat baik-baik saja di bawah 85%. Apa kemungkinan penyebabnya, dan flag apa yang relevan untuk mendiagnosis/mencegahnya?

    Harusnya 75% (bukan 85% atau 100%)? Karena heap **bukan satu-satunya** pemakai memori proses JVM —  Metaspace, thread stack , buffer NIO, dan JIT code cache semuanya **di luar heap** tapi tetap makan memori proses yang sama yang dibatasi container. misalkan 25% untuk komponen non-heap itu bukan pemborosan — itu **pencegahan** `OOMKilled`.

4. Apa bedanya perilaku JVM setelah `OutOfMemoryError` dengan dan tanpa `-XX:+ExitOnOutOfMemoryError`? Kenapa perbedaan ini penting di lingkungan yang dikelola orchestrator seperti Kubernetes?

    `-XX:+ExitOnOutOfMemoryError` — setelah `OutOfMemoryError` dilempar, JVM **tidak otomatis mati**; beberapa thread bisa saja masih hidup dan aplikasi bisa terus "setengah jalan" dalam kondisi rusak/tidak konsisten (misalnya sebagian request masih diterima tapi gagal dengan cara yang aneh) — kondisi yang jauh lebih sulit didiagnosis daripada crash yang bersih. Flag ini membuat JVM langsung keluar (exit) begitu OOM terjadi, membiarkan orchestrator (Kubernetes) yang mendeteksi proses mati dan me-restart pod sesuai `restartPolicy` — gagal cepat dan bersih, daripada limbung dalam kondisi rusak.

5. Bagaimana Anda memutuskan antara `-XX:+UseG1GC`, `-XX:+UseZGC`, dan `-XX:+UseParallelGC` untuk sebuah service baru? Sebutkan pertanyaan-pertanyaan konkret yang akan Anda tanyakan sebelum memutuskan.

    * `-XX:+UseG1GC` — General-purpose backend, heap menengah-besar, butuh keseimbangan throughput dan pause time ?
    * `-XX:+UseZGC` — Heap besar dan membutuhkan pause time sangat rendah ?
    * `-XX:+UseParallelGC` — Batch processing yang lebih mengutamakan throughput daripada pause time ?

6. Kenapa mengaktifkan GC logging (`-Xlog:gc*`) secara default di semua service production dianggap praktik baik, padahal jarang ada yang benar-benar membaca log itu setiap hari?
    GC logging penting karena memberikan evidence tentang perilaku memory management JVM, seperti frekuensi GC, durasi pause, heap occupancy, dan alasan GC terjadi. Walaupun tidak dibaca setiap hari, log ini sangat berguna untuk troubleshooting OOM, latency spike, dan memory pressure. Dengan GC log, kita bisa membedakan apakah masalah berasal dari heap pressure, allocation rate, atau komponen lain, sehingga diagnosis tidak hanya berdasarkan dugaan dari kode.
