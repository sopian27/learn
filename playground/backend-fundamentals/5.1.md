**Bagian 1 — Audit & perbaiki.** Diberi API "asal-asalan" berikut, temukan **semua** pelanggaran terhadap `standards/API_STANDARDS.md` yang dibahas lesson ini (naming, method, status code), lalu tulis ulang jadi versi production-grade:

```java
@RestController
public class ProductController {

    @GetMapping("/getAllProducts")
    public ResponseEntity<List<Product>> getAll() {
        return ResponseEntity.ok(productRepository.findAll()); // tanpa pagination sama sekali
    }

    @PostMapping("/product/add")
    public String addProduct(@RequestBody Product p) {
        productRepository.save(p);
        return "OK"; // status code apa yang dibalikin di sini?
    }

    @GetMapping("/product/remove/{id}")
    public ResponseEntity<String> removeProduct(@PathVariable Long id) {
        productRepository.deleteById(id);
        return ResponseEntity.ok("deleted");
    }
}
```

Untuk tiap pelanggaran yang Anda temukan, sebutkan **kenapa** itu masalah (bukan cuma "melanggar standar"), merujuk ke konsekuensi nyata yang dibahas di Theory (idempotency, konsistensi klien, dll).

    Code |  Pelanggaran |    Kenapa masalah
    GET /getAllProducts | Verb di URL | URL seharusnya merepresentasikan resource, bukan aksi. /products lebih konsisten dan predictable.
    getAll() tanpa pagination   | Tidak ada pagination  | findAll() bisa mengembalikan data sangat besar → memory tinggi, response lambat, timeout.
    POST /product/add   | Naming + singular | Resource collection sebaiknya /products. add adalah aksi.
    POST return String "OK" | Status code tidak eksplisit   | Default biasanya 200 OK, padahal resource baru dibuat → semestinya 201 Created.
    GET /product/remove/{id}    | Method salah  | GET harus safe/read-only. Delete menggunakan DELETE.
    DELETE → 200 OK "deleted"   | Response kurang tepat | Bisa menggunakan 204 No Content jika tidak ada body.
    deleteById() langsung   | Tidak menangani resource tidak ditemukan  | Bisa menghasilkan error/response yang tidak konsisten jika ID tidak ada.

    Production-grade
    @RestController
    @RequestMapping("/products")
    @RequiredArgsConstructor
    public class ProductController {

        private final ProductRepository productRepository;

        @GetMapping
        public ResponseEntity<Page<Product>> getProducts(
                @PageableDefault(size = 20) Pageable pageable) {

            return ResponseEntity.ok(productRepository.findAll(pageable));
        }

        @PostMapping
        public ResponseEntity<Product> createProduct(
                @Valid @RequestBody Product product) {

            Product saved = productRepository.save(product);

            URI location = URI.create("/products/" + saved.getId());

            return ResponseEntity
                    .created(location)
                    .body(saved);
        }

        @DeleteMapping("/{id}")
        public ResponseEntity<Void> deleteProduct(@PathVariable Long id) {

            if (!productRepository.existsById(id)) {
                throw new ProductNotFoundException(id);
            }

            productRepository.deleteById(id);

            return ResponseEntity.noContent().build();
        }
    }

**Bagian 3 — Pilihan pagination.** Fitur "riwayat transaksi" di aplikasi e-wallet Anda diperkirakan akan punya jutaan baris per user aktif dalam setahun, dan data terus bertambah real-time. Apakah Anda pilih offset-based atau cursor-based pagination untuk endpoint ini? Jelaskan trade-off konkret yang jadi alasan pilihan Anda (bukan cuma "cursor lebih modern") — termasuk konsekuensi buat tim frontend yang mau bikin fitur "lompat ke halaman 10".
    Untuk jutaan transaksi per user + data terus bertambah, saya pilih cursor-based pagination.

    Contoh:

    GET /transactions?limit=50

    Response:

    {
    "data": [],
    "pagination": {
        "nextCursor": "eyJpZCI6MTIzNDU2fQ==",
        "hasNext": true
    }
    }
    Kenapa cursor?

    Offset:

    ?page=100000&size=50

    Database harus melewati banyak row terlebih dahulu:

    OFFSET 5,000,000

    Semakin jauh halaman → semakin mahal.

    Selain itu, karena data terus masuk, insert baru dapat membuat page shifting:

    Request page 1
    ↓
    ada transaksi baru
    ↓
    Request page 2
    ↓
    beberapa data bisa bergeser/terduplikasi/terlewat

    Cursor menggunakan posisi data terakhir:

    WHERE created_at < :lastCreatedAt
    ORDER BY created_at DESC
    LIMIT 50

    Sehingga lebih stabil untuk dataset besar dan continuously changing.

    Trade-off frontend

    Kekurangannya: frontend tidak bisa secara natural melakukan:

    "langsung ke halaman 10"

    karena cursor bukan nomor halaman.

    Frontend harus:

    page 1
    ↓ cursor
    page 2
    ↓ cursor
    page 3
    ↓ cursor
    ...
    page 10

    Jadi ada trade-off:

    Cursor = scalability + consistency, tetapi kehilangan random page navigation.

### Interview Questions

1. Kenapa REST menyarankan resource itu benda (noun) bukan aksi (verb) di URL? Apa masalah nyata yang muncul kalau dilanggar?
    Karena URL merepresentasikan resource, sedangkan HTTP method merepresentasikan aksi.

    Kurang baik:

    GET /getProducts
    POST /product/add
    GET /product/remove/10

    Lebih konsisten:

    GET    /products
    POST   /products
    DELETE /products/10

    Kalau verb dimasukkan ke URL, API menjadi tidak konsisten dan client harus menghafal banyak variasi endpoint.

2. Jelaskan beda `PUT` dan `PATCH` secara semantik, dan kenapa `PUT` harus idempotent sementara `PATCH` belum tentu.
    PUT = mengganti representation/resource secara keseluruhan.

    PUT /users/10

    Mengirim request yang sama berkali-kali menghasilkan state akhir yang sama → idempotent.

    PATCH = perubahan sebagian.

    PATCH /users/10
    {
    "name": "Budi"
    }

    PATCH tidak otomatis harus idempotent. Semuanya bergantung pada operasi patch-nya.

    Misalnya:

    PATCH /counter
    {
    "operation": "increment"
    }

    Retry dua kali:

    100 → 101 → 102

3. Kapan Anda pakai `400` vs `422`? Beri contoh konkret kasus yang tepat untuk masing-masing.
    400 Bad Request → request tidak dapat diproses sebagai request yang valid.

    Contoh:

    {
    "rating":
    }

    JSON malformed.

    422 Unprocessable Content → syntax request valid, tetapi datanya melanggar aturan bisnis/semantic validation.

    Contoh:

    {
    "rating": 10
    }

    JSON valid, tetapi rating hanya boleh 1–5.

4. Apa trade-off utama offset-based pagination vs cursor-based pagination? Kapan Anda memilih yang mana?
    |                | Offset             | Cursor         |
    | -------------- | ------------------ | -------------- |
    | Implementasi   | Lebih sederhana    | Lebih kompleks |
    | Random page    | ✅                | ❌/sulit       |
    | Dataset besar  | Bisa mahal         | Lebih scalable |
    | Data real-time | Bisa page shifting | Lebih stabil   |
    | UI page number | Mudah              | Tidak natural  |

5. Kenapa nested resource yang terlalu dalam (3+ level) dianggap anti-pattern? Apa alternatifnya?

    Contoh:

    /products/10/customers/20/orders/30/reviews

    URL menjadi panjang, coupling antar-resource tinggi, dan sulit digunakan ketika kita sebenarnya sudah mengetahui reviewId.

    Alternatif:

    GET /products/10/reviews
    GET /reviews/100
    DELETE /reviews/100

    Gunakan nesting hanya ketika parent-child relationship memang penting untuk konteks operasi.

6. Kenapa `POST` secara default tidak idempotent, dan apa konsekuensinya buat sistem yang melakukan automatic retry?

    Karena setiap request POST biasanya berarti buat resource baru.

    POST /orders

    Request pertama:

    Order #100

    Retry:

    Order #101

    Jadi automatic retry setelah network timeout berpotensi membuat duplicate resource.

    Solusinya untuk operasi yang membutuhkan retry aman bisa menggunakan idempotency key:

    Idempotency-Key: abc-123

    Server mengenali bahwa request retry adalah request yang sama sehingga tidak membuat resource kedua.
