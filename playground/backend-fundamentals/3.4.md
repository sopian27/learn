Tempel bagian "Found one Java-level deadlock" dari output Anda, lalu jelaskan dengan kata sendiri: kenapa `sleepQuietly(500)` di kedua thread itu penting supaya deadlock-nya **konsisten** terjadi (coba pikirkan: apa yang berubah kalau baris `sleepQuietly` itu dihapus — apakah deadlock-nya jadi tidak pernah terjadi, selalu terjadi, atau jadi tidak pasti/kadang terjadi kadang tidak)?

    ```java
        public class DeadlockDemo {
        private static final Object lockA = new Object();
        private static final Object lockB = new Object();

        public static void main(String[] args) {
            Thread threadA = new Thread(() -> {
                synchronized (lockA) {
                    System.out.println("Thread-A pegang lockA, mau ambil lockB...");
                    sleepQuietly(500); // beri waktu Thread-B pegang lockB duluan
                    synchronized (lockB) {
                        System.out.println("Thread-A pegang keduanya (tidak akan pernah tercetak)");
                    }
                }
            }, "Thread-A");

            Thread threadB = new Thread(() -> {
                synchronized (lockB) {
                    System.out.println("Thread-B pegang lockB, mau ambil lockA...");
                    sleepQuietly(500);
                    synchronized (lockA) {
                        System.out.println("Thread-B pegang keduanya (tidak akan pernah tercetak)");
                    }
                }
            }, "Thread-B");

            threadA.start();
            threadB.start();
            // Program ini TIDAK AKAN PERNAH selesai normal -- ini sengaja,
            // supaya ada proses hidup untuk diambil thread dump-nya.
        }

        private static void sleepQuietly(long ms) {
            try {
                Thread.sleep(ms);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        }
    }
    ```

### Interview Questions

1. Jelaskan kenapa `jcmd` lebih disukai dibanding `jstack`/`jmap` terpisah di Java modern, dan mekanisme apa yang sebenarnya dipakai di baliknya.
    jcmd adalah interface diagnostik JVM yang terpadu. Ia menggunakan Dynamic Attach mechanism untuk berkomunikasi dengan JVM yang sedang berjalan dan menjalankan diagnostic command. jstack dan jmap masih tersedia, tetapi jcmd lebih modern dan mencakup lebih banyak command.

2. Seorang thread punya state `BLOCKED`. Jelaskan persis apa artinya, dan bagaimana ini berbeda dari `WAITING`/`TIMED_WAITING`.
    BLOCKED berarti thread sedang menunggu intrinsic monitor dari synchronized yang sedang dipegang thread lain. WAITING menunggu tanpa timeout, sedangkan TIMED_WAITING memiliki timeout. Banyak BLOCKED belum tentu deadlock; deadlock membutuhkan cycle.

3. Apa bedanya shallow size dan retained size di heap dump, dan kenapa mengandalkan shallow size saja bisa membuat Anda melewatkan akar penyebab leak yang sesungguhnya?
    Shallow size adalah ukuran object itu sendiri. Retained size adalah memory yang secara efektif dapat dibebaskan jika object tersebut tidak lagi reachable. Karena itu object kecil seperti HashMap bisa memiliki retained size sangat besar jika menahan jutaan object.

4. Jelaskan risiko konkret dari mengambil heap dump penuh di instance production yang sedang melayani traffic tinggi. Sebutkan minimal 2 strategi mitigasi.
    Heap dump production bisa menyebabkan pause/latency dan I/O yang signifikan, terutama pada heap besar. Mitigasinya adalah mengambil dump dari replica/canary, melakukan drain traffic, melakukan triage dengan histogram terlebih dahulu, atau menggunakan automatic heap dump saat OOM.

5. Kapan Anda akan memilih JFR dibanding heap dump untuk mendiagnosis sebuah masalah? Berikan contoh skenario spesifik untuk masing-masing.
    Saya memilih JFR ketika masalahnya bersifat temporal/intermiten, misalnya sporadic latency, GC pause, lock contention, atau slow I/O. Heap dump saya pilih ketika ingin mengetahui object apa yang memenuhi heap, siapa yang menahannya, dan bagaimana path-nya ke GC Root.

6. Dua thread saling `BLOCKED` tapi ternyata **bukan** deadlock sungguhan (salah satunya akhirnya selesai dan melepas lock). Apa yang membedakan kontensi lock biasa dari deadlock sesungguhan secara mekanis, dan bagaimana `jcmd`/`jstack` bisa membedakan keduanya secara otomatis?
   Lock contention tidak memiliki cycle: thread yang memegang lock akhirnya selesai dan melepaskannya. Deadlock memiliki cycle, misalnya A menunggu B sementara B menunggu A. JVM dapat mendeteksi cycle tersebut dan jcmd Thread.print akan menampilkan Found one Java-level deadlock.
