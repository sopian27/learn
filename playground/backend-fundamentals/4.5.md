### Exercise / Task

**Bagian 1 — Prediksi exception.** Diberi kode berikut:

```java
@Service
public class InvoiceService {
    private final PaymentService paymentService;
    public InvoiceService(PaymentService paymentService) { this.paymentService = paymentService; }
}

@Service
public class PaymentService {
    private final InvoiceService invoiceService;
    public PaymentService(InvoiceService invoiceService) { this.invoiceService = invoiceService; }
}
```

Jelaskan **persis** exception apa yang akan muncul, dan kenapa ini secara logis **mustahil** diselesaikan walau Spring "mau" — bukan cuma "karena Spring belum secanggih itu". Rujuk kembali ke jaminan constructor injection dari Lesson 4.2.

    Sudah benar secara konsep. Saya hanya akan memperketat wording:

    Container mulai membuat InvoiceService → membutuhkan PaymentService untuk constructor.

    PaymentService juga membutuhkan InvoiceService untuk constructor.

    Masalahnya: constructor injection membutuhkan dependency sebelum constructor target dapat dipanggil. Jadi belum ada instance InvoiceService yang bisa diberikan kepada PaymentService.

    Tidak ada "early reference" yang bisa dipakai karena InvoiceService sendiri belum berhasil dibuat sebagai object.

    Akibatnya Spring mendeteksi circular dependency dan gagal membuat bean.

    Exception umumnya berbentuk:

    org.springframework.beans.factory.UnsatisfiedDependencyException:
    Error creating bean with name 'invoiceService':
    Unsatisfied dependency expressed through constructor parameter 0:
    Error creating bean with name 'paymentService':
    Unsatisfied dependency expressed through constructor parameter 0:
    Error creating bean with name 'invoiceService':
    Requested bean is currently in creation:
    Is there an unresolvable circular reference?

    Inti yang perlu ditekankan:

    Constructor injection membuat dependency harus tersedia sebelum object dapat lahir. Karena A membutuhkan B sebelum A lahir, sementara B membutuhkan A sebelum B lahir, tidak ada titik awal untuk memutus siklus tersebut.

    Ini lebih tepat daripada mengatakan Spring "tidak punya object setengah jadi".

**Bagian 2 — "Perbaiki" dengan field injection, lalu bongkar triknya.** Ubah kedua class di atas ke field injection, jalankan, buktikan aplikasi berhasil start (tempel bukti). Lalu jelaskan **langkah demi langkah** (rujuk 3 level cache di Theory) apa yang sebenarnya terjadi di balik layar sampai kedua bean bisa saling terhubung — termasuk sebutkan **momen persis** di mana salah satu bean sempat memegang reference ke bean lain yang belum sepenuhnya selesai diinisialisasi.

    ```java
        @Service
        public class InvoiceService {
            
            @Autowired
            private PaymentService paymentService;
        
        }

        @Service
        public class PaymentService {

            @Autowired
            private InvoiceService invoiceService;
        }
    ```

    Mekanismenya

    Urutannya secara sederhana:

    1. Spring mulai membuat InvoiceService.
    2. Constructor tanpa argumen selesai → instance InvoiceService sudah ada, tetapi paymentService == null.
    3. Sebelum dependency di-populate, Spring dapat mendaftarkan ObjectFactory untuk memperoleh early reference melalui singleton factory/cache level 3.
    4. Spring membutuhkan PaymentService, lalu mulai membuatnya.
    5. PaymentService juga sudah mempunyai instance fisik, tetapi invoiceService == null.
    6. Saat PaymentService membutuhkan InvoiceService, Spring belum menemukan bean final di level 1 maupun early object di level 2.
    7. Spring menggunakan factory di level 3 untuk memperoleh early reference InvoiceService.
    8. Early reference tersebut kemudian dapat dipromosikan ke level 2 (early singleton) dan diberikan kepada PaymentService.
    9. PaymentService selesai initialization → masuk level 1 (singletonObjects).
    10. Spring kembali ke InvoiceService, mengisi paymentService dengan PaymentService yang sudah selesai.
    11. InvoiceService selesai initialization → masuk level 1.

    Pada saat PaymentService menerima early reference InvoiceService, InvoiceService belum selesai initialization.

    Jadi memang ada object yang sudah eksis tetapi belum fully initialized.


**Bagian 3 — Ini pekerjaan sesungguhnya: refactor akarnya.** `InvoiceService` dan `PaymentService` di atas saling butuh karena (asumsikan) keduanya sama-sama perlu menghitung "total tagihan setelah diskon & pajak" untuk keperluan masing-masing. Rancang refactor yang **menghilangkan cycle-nya sepenuhnya** (bukan `@Lazy`, bukan field injection) — tunjukkan kode barunya, dan jelaskan komponen/abstraksi baru apa yang Anda ekstrak, serta kenapa itu solusi struktural, bukan sekadar mengakali gejala.

    ```java
            }

    ```

    kesimpulan : Karena kita menemukan tanggung jawab yang sebenarnya dibutuhkan bersama:

### Interview Questions

1. Kenapa circular dependency lewat constructor injection selalu gagal total, sementara lewat setter/field injection kadang bisa "diselesaikan"?
    Karena constructor injection terjadi saat instantiation. Sebelum constructor new dipanggil, semua dependency constructor harus sudah tersedia.

    Misalnya:

    InvoiceService(PaymentService paymentService)
    PaymentService(InvoiceService invoiceService)

    Untuk membuat InvoiceService, Spring harus punya PaymentService. Tetapi untuk membuat PaymentService, Spring harus punya InvoiceService.

    Masalahnya, InvoiceService sendiri belum selesai dibuat sehingga belum ada instance yang bisa diberikan ke PaymentService.

    Jadi:

    InvoiceService
        ↓ butuh
    PaymentService
        ↓ butuh
    InvoiceService
        ↓ belum selesai dibuat

    Tidak ada titik awal untuk memutus cycle tersebut.

    Sebaliknya, setter/field injection membutuhkan constructor yang tidak memerlukan dependency tersebut:

    new InvoiceService();

    Object sudah berhasil dibuat terlebih dahulu. Setelah itu Spring bisa melakukan dependency population dan, untuk singleton tertentu, menggunakan early reference untuk memutus circular dependency.

    Namun ini bukan berarti field injection membuat dependency yang tidak bisa di-resolve menjadi null lalu Spring tetap sukses startup. Dalam normal Spring wiring, dependency yang tidak dapat di-resolve tetap menyebabkan startup failure.

    Perbedaan utamanya adalah:

    Constructor injection membutuhkan dependency sebelum object lahir. Setter/field injection memungkinkan object lahir terlebih dahulu sebelum dependency di-inject.

2. Jelaskan mekanisme *three-level cache* (`singletonObjects`, `earlySingletonObjects`, `singletonFactories`) yang dipakai Spring untuk menangani circular dependency pada singleton.
    earlySingletonObjects, dan singletonFactories.

    Untuk singleton, Spring memiliki tiga level yang relevan dalam DefaultSingletonBeanRegistry:

    Level 1 — singletonObjects

        Berisi fully initialized singleton yang siap digunakan.

        singletonObjects
            ↓
        bean sudah selesai dibuat dan diinisialisasi

    Level 2 — earlySingletonObjects

        Berisi early singleton reference yang sudah diekspos sebelum proses creation bean tersebut selesai.

        earlySingletonObjects
            ↓
        instance/reference sudah tersedia
        tetapi lifecycle creation belum selesai

    Level 3 — singletonFactories

        Berisi ObjectFactory yang dapat digunakan untuk memperoleh early reference.

        Salah satu alasan penting adanya level ini adalah memberi kesempatan kepada BeanPostProcessor, termasuk mekanisme AOP, untuk menyediakan early reference/proxy.


3. Kenapa bean `prototype` tidak pernah bisa punya circular dependency yang terselesaikan, walau pakai field injection sekalipun?
    Karena mekanisme early singleton reference tersebut merupakan mekanisme untuk singleton, bukan prototype.

    Prototype tidak disimpan sebagai singleton dalam cache container. Setiap kali diminta, Spring membuat instance baru dan setelah instance diberikan kepada caller, lifecycle instance tersebut tidak dikelola seperti singleton.

    Akibatnya Spring tidak memiliki mekanisme singleton early-reference cache yang dapat digunakan untuk memutus cycle tersebut.

    Jadi circular dependency yang melibatkan prototype tidak dapat di-resolve oleh container dan akan berakhir pada BeanCurrentlyInCreationException.

    Contoh:

    Singleton A
        ↓
    Prototype B
        ↓
    Singleton A

    atau cycle lain yang melibatkan prototype tetap tidak mendapatkan mekanisme three-level singleton cache untuk memutus siklusnya.

4. Apa yang berubah di `spring.main.allow-circular-references` sejak Spring Boot 2.6, dan kenapa tim Spring membuat perubahan itu?
    Sejak Spring Boot 2.6, spring.main.allow-circular-references default-nya adalah:

    false

    Artinya circular reference yang sebelumnya dapat diselesaikan secara mekanis oleh Spring tidak lagi diizinkan secara default.

    Jika memang ingin mengaktifkan kembali perilaku tersebut:

    spring.main.allow-circular-references=true

    Namun konfigurasi tersebut sebaiknya dipandang sebagai compatibility/workaround, bukan sebagai solusi desain.

    Alasannya adalah circular dependency sering menjadi sinyal bahwa dependency graph atau pembagian responsibility perlu diperbaiki.

    Daripada:

    A → B → A

    lebih sehat jika desainnya menjadi:

    A → C ← B

    atau menggunakan event ketika hubungan tersebut sebenarnya bersifat komunikasi satu arah/asinkron.

    Intinya:

    Spring memilih fail-fast terhadap circular dependency daripada menjadikannya perilaku default yang diam-diam ditoleransi.

5. Kalau ditanya "bagaimana cara mengatasi circular dependency" saat interview, kenapa jawaban "pakai `@Lazy`" saja dianggap jawaban yang belum lengkap/kurang senior?
    Karena `@Lazy` tidak "menyelesaikan" circular dependency.** tapi cuma menunda **kapan** dependency-nya benar-benar di-resolve (sampai pemanggilan pertama), bukan menghilangkan fakta bahwa dua komponen itu saling bergantung secara desain. Aplikasi jadi bisa start, tapi coupling-nya tetap ada, cuma disembunyikan. Itu hanya temporary solution, sedangkan permanen solution nya seharusnya bisa di cegah di fase design, dengan menghindari circular dependency dengan cara :
        
        Karena @Lazy biasanya memutus masalah creation-time, bukan menghilangkan circular dependency secara desain.

        Contohnya:

        A → B
        ↑   ↓
        └───┘

        Dengan @Lazy, dependency dapat dibuat secara lazy/proxy sehingga startup bisa berhasil.

        Tetapi secara desain:

        A masih bergantung pada B
        B masih bergantung pada A

        Cycle-nya masih ada.

        Pendekatan yang lebih struktural adalah mencari kenapa cycle tersebut muncul.

        1. Ada responsibility yang seharusnya menjadi komponen ketiga

            Misalnya:

            OrderService ↔ NotificationService

            ternyata keduanya sama-sama membutuhkan logic tentang notification order.

            Logic tersebut dapat diekstrak:

            OrderService ──→ OrderNotificationPolicy ←── NotificationService

        2. Dependency terlalu lebar atau arahnya salah

            Jika ServiceB hanya membutuhkan sebagian kemampuan ServiceA, mungkin dependency dapat dipersempit menggunakan interface yang memiliki responsibility minimal:

            public interface OrderReader {
                Order findById(String orderId);
            }

            Kemudian ServiceB bergantung pada OrderReader, bukan seluruh OrderService.

        3. Hubungannya sebenarnya event, bukan direct call

            Misalnya:

            OrderService
                │
                │ publish
                ↓
            OrderCreatedEvent
                ↓
            NotificationService

            OrderService tidak perlu mengetahui keberadaan NotificationService.

            Jadi prinsipnya:

            @Lazy bisa menjadi alat teknis untuk menangani dependency tertentu, tetapi refactor dependency graph adalah solusi struktural ketika circular dependency menunjukkan masalah desain.

6. Jelaskan perbedaan mendasar antara circular dependency (Lesson 4.5) dan self-invocation pitfall (Lesson 4.4) — dari sisi fase kapan masalahnya terjadi.
    Perbedaannya terutama ada pada kapan masalah tersebut terjadi.

    Circular dependency

    Terjadi saat bean creation/startup:

    ApplicationContext startup
            ↓
    Bean creation
            ↓
    A → B → A
            ↓
    circular dependency
            ↓
    startup failure / early-reference mechanism

    Masalahnya berada pada dependency graph dan bean lifecycle.

    Diagnosis biasanya dimulai dari stack trace startup dan dependency antar-bean.

    Self-invocation

    Bean sudah selesai dibuat.

    Kemudian pada runtime:

    this.someMethod();

    Method dipanggil melalui this, sehingga panggilan tersebut tidak melewati Spring AOP proxy.

    Akibatnya advice tertentu, misalnya:

    @Transactional
    @Cacheable
    @Retryable

    dapat tidak diterapkan pada self-invocation tersebut.

    Jadi:

    Circular dependency
    → creation time
    → dependency graph
    → ApplicationContext startup

    Self-invocation
    → call time
    → proxy routing
    → runtime method invocation

    Circular dependency adalah masalah bagaimana bean saling membutuhkan saat dibuat; self-invocation adalah masalah bagaimana method dipanggil setelah bean sudah dibuat.
