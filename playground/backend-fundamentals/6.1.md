**Bagian 3 — Merancang "index budget" di kertas.** Tabel `orders` (1 juta baris sekarang, tumbuh ±2.000 insert/detik pada jam sibuk; kolom `status` di-update rata-rata 3× selama hidup sebuah order). Enam query:

* **Q-a (80% traffic):** order terbaru milik seorang customer, keyset pagination.
* **Q-b:** admin melihat 50 order `PENDING` terlama.
* **Q-c:** laporan pendapatan kemarin: `SELECT sum(total_amount) ... WHERE status = 'DONE' AND created_at >= :start AND created_at < :end`.
* **Q-d:** ambil satu order berdasarkan `id`.
* **Q-e:** ekspor BI sekali semalam yang membaca **semua** order.
* **Q-f:** `SELECT count(*) FROM orders WHERE status <> 'DONE'` (dipakai dashboard, 1× per menit).

Tugas: 
(1) Anggaran **maksimum 4 index tambahan** (di luar PK). Tulis DDL tiap index, **urutan kolom beserta alasan**, dan query mana yang dilayani. 
* **Q-a (80% traffic):** order terbaru milik seorang customer, keyset pagination. **Keputusan: pertahankan.**
  ```sql
  CREATE INDEX idx_orders_customer_created
  ON orders (customer_id, created_at DESC, id DESC);
  ```
  Alasan: melayani query 80% traffic; `customer_id` untuk filter (equality), lalu `created_at, id` untuk urutan + keyset pagination tanpa node `Sort` tambahan. `id` jadi tie-breaker kalau `created_at` sama.
  Catatan: `DESC` pada `created_at` bukan keharusan mutlak — PostgreSQL bisa backward scan pada B-tree. Arah index dipilih dari kombinasi arah `ORDER BY` dan kebutuhan query sebenarnya.

* **Q-b:** admin melihat 50 order `PENDING` terlama. **Keputusan: pertahankan.**
  ```sql
  CREATE INDEX idx_orders_pending_created
  ON orders (created_at ASC)
  WHERE status = 'PENDING';
  ```
  Alasan: index hanya menyimpan baris yang memenuhi predicate, jadi jauh lebih kecil dari index seluruh order. Dari lab: hanya ±0,5% baris relevan, query ±0,102 ms.
  Trade-off: perubahan `status` membuat baris masuk/keluar partial index.
  > **Catatan mentor (Part 3, #1):** kolom di predicate `WHERE status = 'PENDING'` dihitung sebagai kolom ter-index untuk keputusan HOT. Jadi tiap `UPDATE status` (3× per order) tidak bisa HOT dan harus menyentuh index. Biaya ini harus ikut ditimbang, bukan hanya ukuran index yang kecil.

* **Q-c:** laporan pendapatan kemarin: `SELECT sum(total_amount) ... WHERE status = 'DONE' AND created_at >= :start AND created_at < :end`. **Keputusan: tunda covering index.**
  Kandidat:
  ```sql
  CREATE INDEX idx_orders_status_created
  ON orders (status, created_at)
  INCLUDE (total_amount);
  ```
  Urutan `(status, created_at)`: equality di `status`, lanjut range di `created_at`.
  Dua pertanyaan sebelum menambah:
  1. Apakah `Index Only Scan` benar-benar mengurangi akses heap? Kalau visibility map belum menandai halaman all-visible, PostgreSQL tetap ke heap. Di tabel yang sering di-update, `Heap Fetches` bisa tinggi.
  2. Apakah laporan harian perlu membaca tabel operasional yang sibuk? Kalau data tidak harus real-time: read replica atau tabel ringkasan yang di-refresh berkala.
  Tidak ditambah sebelum membandingkan plan, biaya update, dan kebutuhan kesegaran laporan.

* **Q-d:** ambil satu order berdasarkan `id`.
  Sudah dilayani primary key.

* **Q-e:** ekspor BI sekali semalam yang membaca **semua** order.
  Sengaja tanpa index: membaca seluruh tabel, sequential scan lebih masuk akal. Index tidak menghilangkan kebutuhan membaca semua data dan hanya menambah biaya tulis + storage.

* **Q-f:** `SELECT count(*) FROM orders WHERE status <> 'DONE'` (dashboard, 1× per menit). **Keputusan: sengaja tidak diberi index (revisi; sebelumnya partial index `idx_orders_not_done`).**
  Alasan:
  * Hanya jalan 1× per menit.
  * Dari eksperimen, seq scan 1 juta baris ±34 ms. 34 ms × 60 menit ≈ 2,04 detik per jam.
  * Index tambahan harus dirawat di setiap perubahan yang relevan; index pada `status` menambah biaya update dan mengurangi peluang HOT.
  Kalau dashboard tidak perlu angka real-time: cache TTL beberapa detik, counter inkremental, tabel ringkasan, atau read replica (replica memindahkan beban baca dari primary, tidak membuat query lebih murah secara total).
  > **Catatan mentor (Part 3, #2):** alasan teknis tambahan — predicate `<>` tidak cocok untuk B-tree biasa. B-tree bagus untuk equality dan range terurut; `<>` berarti "semua kecuali satu nilai", jadi bukan satu range sempit. Kalau mayoritas order belum DONE, planner tetap memilih seq scan.

(2) **Query yang sengaja tanpa index khusus:** Q-e (dan Q-f, lihat di atas). Index tidak menghilangkan kebutuhan membaca seluruh data dan hanya menambah biaya tulis serta penyimpanan.

(3) **Q-c, dua desain:**
  * `(status, created_at)`: lebih kecil, tapi mengambil `total_amount` perlu akses heap.
  * `(status, created_at) INCLUDE (total_amount)`: index lebih besar dan biaya tulis naik, tapi berpotensi mengurangi akses heap lewat index-only scan.
  Yang akan diukur: ukuran index, waktu query, buffer, `Heap Fetches`, dampak ke INSERT/UPDATE.

(4) **Tantangan HOT:** perubahan pada kolom ter-index, termasuk `status`, mencegah HOT update. Index yang melibatkan `status` menaikkan biaya pemeliharaan dan berpotensi menambah bloat. Eksperimen: bandingkan dengan dan tanpa index `status`; ukur throughput UPDATE, WAL, dead tuples, ukuran index, statistik HOT update.

### Interview Questions

1. Jelaskan bagaimana B-tree index mempercepat pencarian. Kenapa tinggi pohonnya hanya 3–4 level walau tabelnya ratusan juta baris? Kenapa `ORDER BY` dan range scan ikut cepat?
   B-tree menyimpan key secara terurut dan membagi pencarian ke beberapa level. Pohonnya biasanya hanya 3–4 level karena setiap halaman dapat menunjuk ke banyak halaman anak (high fan-out), sehingga jumlah key yang bisa dijangkau tumbuh sangat cepat.

  Equality search: menelusuri pohon menuju key yang dicari.
  ORDER BY: membaca key sesuai urutan index tanpa perlu Sort jika urutannya cocok.
  Range scan: menemukan batas awal, lalu membaca key berikutnya secara berurutan.

2. Kenapa planner kadang memilih `Seq Scan` padahal ada index di kolom yang difilter? Kapan itu keputusan yang benar?

  Karena Seq Scan diperkirakan lebih murah, misalnya:

  Sebagian besar tabel harus dibaca.
  Filter kurang selektif.
  Banyak akses acak ke heap diperlukan.
  Tabel kecil sehingga sequential scan lebih murah.

  Seq Scan bukan selalu masalah. Yang penting adalah apakah biayanya sesuai dengan kebutuhan query.

3. Index `(a, b, c)` — query dengan filter hanya di `b` bisa memakainya? Jelaskan leftmost prefix dengan analogi. Bagaimana aturan urutan kolom untuk query `WHERE a = ? AND b > ? ORDER BY b`?
  Biasanya tidak optimal untuk pencarian langsung berdasarkan b, karena B-tree mengurutkan key berdasarkan a, lalu b, kemudian c.

  Analogi: buku telepon diurutkan berdasarkan kota, lalu nama. Mencari nama tanpa mengetahui kotanya lebih sulit.

  Untuk:

  WHERE a = ?
    AND b > ?
  ORDER BY b

  Index (a, b) sesuai untuk filter dan range scan, tetapi karena b > ? sudah menghasilkan urutan berdasarkan b, pengurutan tambahan umumnya tidak diperlukan. Jika arah pengurutan berbeda, periksa apakah index tetap bisa mendukungnya.

4. Anda punya `WHERE customer_id = ? ORDER BY created_at DESC LIMIT 20`. Kenapa satu composite index `(customer_id, created_at)` mengalahkan dua index terpisah?
    Index (customer_id, created_at DESC) memungkinkan PostgreSQL langsung mencari customer tersebut dan membaca 20 order terbaru tanpa harus menggabungkan hasil dari dua index atau mengurutkan banyak baris.

    Dua index terpisah belum tentu menyediakan akses sekaligus filter dan urutan secara efisien.

5. Apa itu covering index / Index Only Scan? Apa peran visibility map dan `Heap Fetches`? Apa harganya?
    Covering index memuat seluruh kolom yang dibutuhkan query. PostgreSQL berpotensi menjalankan Index Only Scan tanpa membaca heap untuk setiap baris.

    Namun, visibility map menentukan apakah PostgreSQL bisa memastikan visibilitas baris tanpa memeriksa heap.

    Heap Fetches: 0 → tidak ada pengambilan heap untuk memeriksa visibilitas.
    Heap Fetches tinggi → sebagian baris tetap perlu diperiksa di heap.

    Harganya: index lebih besar dan operasi tulis lebih mahal.

6. Kapan partial index lebih baik daripada index penuh? Sebutkan satu jebakan terkait prepared statement.
  Ketika query sering mengakses subset kecil yang stabil.

  CREATE INDEX idx_orders_pending
  ON orders (created_at)
  WHERE status = 'PENDING';

  Index hanya menyimpan baris PENDING, sehingga lebih kecil daripada index penuh.

  Jebakan prepared statement: jika kondisi status menggunakan parameter, misalnya status = $1, generic plan mungkin tidak dapat membuktikan bahwa kondisi query memenuhi predikat partial index.

7. Jelaskan semua yang terjadi di write path saat sebuah tabel punya 6 index. Apa itu HOT update, dan kenapa meng-index kolom yang sering di-update berbahaya?
  INSERT harus menulis heap dan memelihara setiap index yang relevan, serta menghasilkan WAL.

  UPDATE dapat memperbarui heap dan index terkait; DELETE menandai tuple untuk dihapus dan memerlukan pemeliharaan index serta vacuum.

  HOT update memungkinkan perubahan tuple tanpa menambahkan entri baru pada index jika tidak ada kolom yang diindeks berubah dan tersedia ruang pada halaman yang sama.

  Mengindeks kolom yang sering berubah dapat menghambat HOT, menambah WAL, dan meningkatkan bloat.

8. Kapan menambah index justru merugikan? Sebutkan minimal 4 situasi.
    1. Index jarang digunakan.
    2. Index menduplikasi index lain.
    3. Kolom memiliki selectivity rendah dan query membaca sebagian besar tabel.
    4. Beban INSERT/UPDATE/DELETE sangat tinggi.
    5. Index terlalu besar dan menambah tekanan storage/cache.
    6. Index tidak sesuai urutan filter dan pengurutan query.

9. Anda diberi plan `EXPLAIN (ANALYZE, BUFFERS)`. Apa 5 hal pertama yang Anda periksa? Bagaimana membedakan masalah "index tidak ada" dari "statistik basi" dari "index salah urutan"?
  1. Actual rows vs estimated rows: apakah estimasi planner meleset?
  2. Execution Time: node atau operasi mana yang mahal?
  3. Buffers: berapa banyak blok yang diakses dan dibaca?
  4. Scan dan join: apakah scan atau join strategy sesuai kebutuhan?
  5. Sort, loops, dan filter: apakah ada sorting mahal atau operasi berulang?

  Membedakan masalah:

  1. Index tidak ada: query memerlukan akses selektif, tetapi tidak tersedia index yang sesuai.
  2. Statistik basi: estimasi baris jauh berbeda dari hasil aktual; verifikasi dengan ANALYZE.
  3. Index salah urutan: index tersedia, tetapi urutan kolom tidak cocok dengan filter, range, atau ordering query.

10. (Senior) Bagaimana Anda menambah index ke tabel 500 GB yang menerima ribuan tulis per detik tanpa downtime? Apa yang bisa gagal, dan bagaimana mendeteksinya?
    CREATE INDEX CONCURRENTLY idx_orders_customer_created
    ON orders (customer_id, created_at DESC);

    Pantau progres melalui pg_stat_progress_create_index, beban CPU/I/O, latency, replica lag, dan kapasitas disk.

    Risikonya meliputi build gagal, transaksi lama, kehabisan disk, serta index invalid yang tertinggal. CREATE INDEX CONCURRENTLY menghindari pemblokiran operasi tulis normal, tetapi tetap memerlukan sumber daya dan dapat menunggu transaksi lama.

11. (Senior) Kenapa PostgreSQL tidak otomatis meng-index foreign key, dan apa konsekuensi operasionalnya untuk `DELETE`/`UPDATE` di tabel parent?
    PostgreSQL otomatis mengindeks primary key dan unique constraint, tetapi tidak otomatis mengindeks kolom foreign key pada tabel anak. Ketika parent dihapus atau key-nya diubah, PostgreSQL mungkin harus mencari baris anak yang terkait. Tanpa index pada foreign key, pencarian tersebut dapat memerlukan sequential scan besar dan memperpanjang transaksi serta lock.
    
12. (Senior) Tim Anda ingin "memperbaiki" semua query lambat dengan menambah index. Bagaimana Anda menjalankan proses yang disiplin (bukti, ukuran, dokumentasi), dan bagaimana Anda mencegah *index sprawl* dalam jangka panjang?
    Terapkan proses berbasis bukti:

    1.Identifikasi query lambat dari metrik dan execution plan.
    2.Buat hipotesis dan desain index berdasarkan pola query.
    3.Ukur manfaat terhadap latency, buffer, dan throughput tulis.
    4.Catat tujuan, ukuran, pemilik, serta query yang dilayani setiap index.
    5.Tinjau index redundan dan tidak terpakai secara berkala, dengan mempertimbangkan statistik reset dan replica.
    6.Hapus index secara aman setelah validasi, lalu ukur kembali dampaknya.
