### Coding

Kode nyata yang "jalan" tapi melanggar banyak lapisan konvensi sekaligus — perhatikan ini bukan cuma soal gaya, ada bug tersembunyi juga:

```java
package com.example.OrderService;   // (1) package tidak boleh ada huruf besar

public class order_processor {      // (2) class harus PascalCase, bukan snake_case

    public static final int maxRetryCount = 3; // (3) constant harus UPPER_SNAKE_CASE

    private String OrderStatus;     // (4) field harus camelCase, bukan PascalCase

    public boolean getPaid() {      // (5) boolean method idiomnya isPaid()/hasPaid(), bukan getPaid()
        return OrderStatus.equals("PAID");
    }

    public void Process_Order(String order_id) { // (6) method harus camelCase, bukan Process_Order
        // (7) DB column konvensinya snake_case (order_id) — tapi variable Java ini
        //     seharusnya tetap camelCase (orderId), snake_case cuma untuk lapisan DB/SQL
        System.out.println("Processing " + order_id);
    }
}
```

### Exercise / Task


**Bagian 1 — Perbaiki kode `order_processor` di atas.** Identifikasi ketujuh pelanggaran bernomor, perbaiki semuanya sesuai `standards/NAMING_CONVENTIONS.md`, dan jelaskan untuk **setiap** perbaikan: pelanggaran itu masuk kategori *typographical* atau *grammatical* (Effective Java Item 68), dan kenapa itu penting (bukan cuma "supaya sesuai aturan").

    package com.example.orderservice;

    public class OrderProcessor {

        public static final int MAX_RETRY_COUNT = 3;

        private String orderStatus;

        public boolean isPaid() {
            return "PAID".equals(orderStatus);
        }

        public void processOrder(String orderId) {
            System.out.println("Processing " + orderId);
        }
    }

    | No    | Perbaikan                            | Kategori                        | Kenapa penting                                                                                                                    |
    | ----- | ------------------------------------ | ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
    | **1** | `OrderService` → `orderservice`      | **Typographical**               | Package Java menggunakan lowercase agar konsisten dan mudah dikenali sebagai package, bukan type.                                 |
    | **2** | `order_processor` → `OrderProcessor` | **Typographical**               | Class PascalCase membuat type langsung mudah dibedakan dari variable/method.                                                      |
    | **3** | `maxRetryCount` → `MAX_RETRY_COUNT`  | **Typographical**               | Constant UPPER_SNAKE_CASE memberi sinyal jelas bahwa nilainya constant.                                                           |
    | **4** | `OrderStatus` → `orderStatus`        | **Typographical**               | Field camelCase membedakan state/object member dari class/type.                                                                   |
    | **5** | `getPaid()` → `isPaid()`             | **Grammatical**                 | `isPaid()` secara bahasa menyatakan predicate boolean: "apakah sudah paid?"                                                       |
    | **6** | `Process_Order()` → `processOrder()` | **Typographical + grammatical** | Method camelCase; lowercase awal juga mengikuti pola verb/action Java.                                                            |
    | **7** | `order_id` → `orderId`               | **Boundary translation**        | Nama DB dan Java berada di layer berbeda. SQL boleh `order_id`, Java harus `orderId`. Jangan bocorkan konvensi DB ke domain code. |

**Bagian 2 — Diagnosis.** Tim Anda punya endpoint `GET /api/products` yang mengembalikan JSON dengan field `createdAt`, `updatedAt`, `productName` (konsisten camelCase — konvensi tim untuk response API). Database-nya punya kolom `created_at`, `updated_at`, `product_name` (snake_case, sesuai konvensi SQL). Suatu hari, seorang developer baru menambahkan field baru `stock_quantity` langsung di entity JPA (field Java-nya juga ditulis `stock_quantity`, bukan `stockQuantity`, "supaya gampang, sama persis dengan nama kolom database"). Dua minggu kemudian ada dua masalah terpisah dilaporkan: (a) response JSON dari endpoint itu untuk field baru ini malah muncul sebagai `"stock_quantity"`, beda sendiri dari field lain yang semuanya `camelCase` — klien frontend yang sudah terbiasa konsisten `camelCase` jadi bingung harus akses field mana; (b) reviewer PR lain protes "kenapa field ini beda formatnya dari field lain di entity yang sama?" tapi developer itu membalas "kan sama persis dengan nama kolom database, jadi tidak ada bug". Jelaskan: apakah balasan developer itu benar bahwa "tidak ada bug"? Kaitkan jawaban Anda ke pembahasan *boundary translation* di Theory — mana yang salah paham di sini: soal *bug fungsional* atau soal *pelanggaran konvensi* (atau dua-duanya), dan kenapa keduanya tetap masalah nyata walau kodenya "jalan".

    Developer itu setengah benar: kodenya mungkin berjalan, tetapi kesimpulan "tidak ada bug" salah.

    Ada dua boundary:

    Java Entity
    stockQuantity
        ↓
    JPA mapping
        ↓
    Database
    stock_quantity

    Java tidak harus menggunakan nama yang sama dengan database.

    Masalah (a)

    Jika Jackson memakai field/property name Java secara default, JSON menjadi:

    {
    "stock_quantity": 10
    }

    Padahal API convention:

    {
    "stockQuantity": 10
    }

    Ini bisa menjadi functional/API compatibility bug, karena client yang mengharapkan stockQuantity bisa gagal membaca data.

    Masalah (b)

    stock_quantity di Java juga melanggar konvensi naming layer Java.

    Jadi ada dua masalah:

    Konvensi: Java field seharusnya stockQuantity.
    Fungsional: bisa menyebabkan kontrak JSON API berubah/inkonsisten.

    Boundary translation justru dibuat agar perbedaan antar-layer tidak bocor:

    Java convention       DB convention       API convention
    camelCase       →     snake_case    →     camelCase
    stockQuantity         stock_quantity       stockQuantity

### Interview Questions

Coba jawab dulu sebelum minta saya review — ini bukan kuis hafalan, jawab dengan alur reasoning-nya:

1. **Kenapa Effective Java membagi naming convention jadi dua kategori (typographical dan grammatical), bukan cuma satu daftar aturan format?**
        Typographical → bagaimana nama ditulis: OrderProcessor, orderId, MAX_RETRY_COUNT.
        Grammatical → bagaimana nama dibentuk secara bahasa/semantik: isPaid(), getName(), addItem().
        Jadi getPaid() bukan sekadar salah format; secara grammar, isPaid() lebih tepat karena method tersebut menjawab pertanyaan boolean "apakah sudah paid?".

2. **Kenapa database pakai `snake_case` dan Java pakai `camelCase` bukan dianggap sebagai "inkonsistensi yang harus diseragamkan", padahal keduanya representasi dari data yang sama?**
        Ini bukan inkonsistensi, tetapi boundary translation. ORM seperti JPA bertugas menerjemahkan:

        @Column(name = "stock_quantity")
        private Integer stockQuantity;

        Memaksa Java memakai stock_quantity justru membuat konvensi database bocor ke domain/application code.

3. **Sebutkan satu contoh konkret bagaimana pelanggaran naming convention bisa berubah dari "sekadar gaya" jadi bug fungsional nyata di titik boundary antar-lapisan (mis. Java-Database atau Java-JSON API).**
    Java field salah nama:

    private String user_name;

    Jackson bisa menghasilkan:

    {
    "user_name": "Sopian"
    }

    sementara kontrak API tim adalah:

    {
    "userName": "Sopian"
    }

    Frontend yang membaca response.userName mendapat undefined.

    Jadi awalnya terlihat seperti pelanggaran naming convention, tetapi di boundary JSON berubah menjadi functional/API contract bug.
