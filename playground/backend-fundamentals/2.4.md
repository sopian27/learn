### Exercise / Task

Anda pegang servis `ReportAggregatorService` yang saat ini pakai `ThreadPoolExecutor` gaya 2.2 (persis pola yang dibangun di Exercise 2.2/2.3 sebelumnya):

```java
public class ReportAggregatorService {

    // Dipanggil untuk TIAP salah satu dari 500 region cabang -- total 500 panggilan per laporan harian
    // Tiap panggilan: ~80ms network call ke servis regional, lalu ~5ms parsing response
    public RegionReport fetchRegionReport(String regionId) { /* ... */ }

    private final ExecutorService pool = new ThreadPoolExecutor(
        50, 50, 0, TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(600),
        new ThreadPoolExecutor.CallerRunsPolicy()
    );

    public List<RegionReport> generateDailyReport(List<String> regionIds) {
        List<Future<RegionReport>> futures = regionIds.stream()
            .map(id -> pool.submit(() -> fetchRegionReport(id)))
            .toList();

        List<RegionReport> results = new ArrayList<>();
        for (Future<RegionReport> f : futures) {
            try {
                results.add(f.get()); // blocking, satu-satu
            } catch (Exception e) {
                throw new ReportGenerationException("Gagal ambil laporan region", e);
            }
        }
        return results;
    }
}
```

Tim Anda baru migrasi ke Java 25 dan bertanya: "Ganti aja semua ke virtual thread, biar makin cepat dan gak usah pusing hitung pool size lagi kan?"

**Tugas Anda:**

1. **Hitung dulu** angka pool 50 di atas itu sudah tepat atau tidak, pakai rumus 2.2 (`N_cpu * U_cpu * (1 + W/C)`, asumsikan mesin 8 core, `U_cpu = 1`). Tunjukkan `W` dan `C` yang Anda pakai dari angka yang ada di soal (jangan asal tebak `W/C`, ini persis catatan yang menahan skor Exercise 2.3 kemarin).

    N_cpu = 8
    U_cpu = 1
    W = 80 ms
    C = 5 ms
    W/C = 80 / 5
        = 16

    N_threads = N_cpu * U_cpu * (1 + W/C)
    = 8 * 1 * (1 + 16)
    = 8 * 17
    = 136 thread

    kesimpulan :
    Pool 50 lebih kecil daripada hasil sizing teoritis 136.

    Teoritis = 136 threads
    Actual   = 50 threads

    Dengan pool 50, maksimal hanya sekitar 50 pekerjaan yang bisa aktif bersamaan. Karena workload sangat I/O-bound, 50 thread belum memanfaatkan kemampuan concurrency yang secara teoritis tersedia.

2. Refactor `generateDailyReport()` supaya pakai `Executors.newVirtualThreadPerTaskExecutor()`. Jelaskan **secara spesifik** kenapa kasus ini (500 region, tiap panggilan didominasi network wait) cocok untuk virtual thread — hubungkan ke mekanisme unmount-mount dari Theory, bukan cuma "soalnya lebih cepat".

    ```java
    public List<RegionReport> generateDailyReport(List<String> regionIds) {

        try (ExecutorService executor =
                Executors.newVirtualThreadPerTaskExecutor()) {

            List<Future<RegionReport>> futures = regionIds.stream()
                .map(id -> executor.submit(() -> fetchRegionReport(id)))
                .toList();

            List<RegionReport> results = new ArrayList<>(regionIds.size());

            for (Future<RegionReport> future : futures) {
                try {
                    results.add(future.get());
                } catch (ExecutionException e) {
                    throw new ReportGenerationException(
                        "Gagal ambil laporan region", e.getCause());
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                    throw new ReportGenerationException(
                        "Proses report diinterupsi", e);
                }
            }

            return results;
        }
    }
    ```

    Saat virtual thread melakukan blocking I/O yang didukung runtime:

    Virtual Thread A
        │
        ├── network call
        │
        └── WAIT
                ↓
        di-unmount
                ↓
    Carrier Thread bebas
                ↓
        menjalankan VT lain

    Kemudian ketika I/O siap:

    Network response
        ↓
    Virtual Thread A
        ↓
    di-mount kembali ke carrier
        ↓
    lanjut parsing 5 ms

    Jadi satu carrier/platform thread bisa digunakan untuk menjalankan banyak virtual thread secara bergantian selama virtual thread tersebut sedang menunggu blocking I/O.

    Itulah alasan 500 task I/O-bound seperti ini cocok untuk virtual thread.

3. **Cari 1 titik pinning risk** di kode ini kalau seandainya `fetchRegionReport` internalnya menulis hasil ke sebuah cache lokal lewat method `synchronized` yang JUGA melakukan network call di dalamnya (skenario umum: cache-aside pattern yang naif). Jelaskan kenapa ini beda antara kalau tim Anda masih di JDK 21-23 vs kalau sudah benar-benar di Java 25 (JEP 491) — dan tetap sebutkan alternatif desain yang lebih aman terlepas dari versi JDK-nya.

    Misalnya fetchRegionReport() ternyata melakukan:

    public RegionReport fetchRegionReport(String regionId) {

        // network call
        RegionReport report = callRegionalService(regionId);

        cache.put(regionId, report);

        return report;
    }

    dan cache-nya seperti:

    public synchronized void updateCache(
            String regionId,
            RegionReport report) {

        // network call ❌
        remoteCacheService.save(regionId, report);

        // update local cache
        localCache.put(regionId, report);
    }

    Ini berbahaya pada virtual thread di JDK 21–23.

    Kenapa?

    Virtual Thread
        │
        │ masuk synchronized
        ↓
    intrinsic lock
        │
        │ network call
        ↓
        BLOCK

    Pada kondisi tertentu, virtual thread bisa terpin ke carrier thread ketika blocking terjadi di dalam monitor synchronized.

    Akibatnya:

    VT-1
    │
    ├── synchronized
    │
    ├── network WAIT
    │
    └── carrier thread ikut tertahan

    Jadi keuntungan virtual thread bisa berkurang drastis jika banyak virtual thread melakukan pola seperti ini.

    Bagaimana dengan Java 25?

    Mulai JDK 24, melalui JEP 491, Java memperbaiki mekanisme virtual thread sehingga blocking di dalam synchronized tidak lagi menyebabkan pinning seperti pola problematic pada JDK 21–23.

    Jadi pada Java 25:

    synchronized
        ↓
    blocking I/O

    tidak lagi otomatis menjadi pinning risk seperti pada JDK 21–23.

    Desain yang lebih aman

    Pisahkan network I/O dari critical section:

    public void updateCache(String regionId, RegionReport report) {

        // network call DI LUAR lock
        remoteCacheService.save(regionId, report);

        synchronized (this) {
            localCache.put(regionId, report);
        }
    }

    Atau lebih baik lagi gunakan struktur concurrency yang sesuai, misalnya:

    ConcurrentHashMap

    dan desain cache yang tidak membutuhkan monitor besar untuk seluruh operasi.

4. **Jawab langsung pertanyaan tim Anda**: apakah "ganti semua ke virtual thread" itu keputusan yang tepat di sini? Ada bagian dari servis ini (bayangkan `generateDailyReport` juga melakukan agregasi angka yang berat — sum/average ribuan angka dari 500 region setelah semua response masuk) yang **tidak akan diuntungkan** oleh virtual thread — sebutkan bagian itu dan jelaskan kenapa, mengacu ke baris "Virtual thread tidak menambah paralelisme CPU" di Theory.

    Tidak.

    Untuk bagian:

    500 × fetchRegionReport()
            ↓
    80 ms network
            ↓
    5 ms parsing

    Ya, virtual thread sangat cocok.

    Tetapi untuk aggregate(results) yang melakukan:

    500 region
    ↓
    masing-masing ribuan angka
    ↓
    sum
    average
    statistical calculation
    ↓
    CPU-heavy

    Ini berbeda.

    Virtual thread tidak menambah jumlah CPU core.

    Misalnya mesin:

    8 CPU cores

    Virtual thread tidak mengubahnya menjadi:

    500 CPU cores.

    Kalau ada 500 virtual threads melakukan pekerjaan CPU-heavy:

    VT-1  ─┐
    VT-2  ─┤
    VT-3  ─┤
    ...    ├──→ 8 CPU cores
    VT-500 ─┘

    Mereka tetap harus berebut 8 core.

    Karena itu:

    I/O-bound
    VT
    │
    ├── network WAIT
    │       ↓
    │   unmount
    │       ↓
    carrier menjalankan VT lain
    │
    └── response → mount → lanjut

    Virtual thread sangat membantu concurrency.

    CPU-bound
    VT
    │
    └── hitung 100%
            ↓
        CPU

    Tidak ada waktu blocking yang bisa dimanfaatkan untuk unmount. Jadi virtual thread tidak memberikan tambahan paralelisme CPU. Untuk CPU-heavy aggregation, yang lebih tepat adalah memanfaatkan jumlah core secara efektif, misalnya executor CPU-bound dengan ukuran sekitar jumlah core yang tersedia (tergantung karakteristik pekerjaan), bukan membuat ratusan virtual thread dengan harapan perhitungan menjadi lebih cepat.
