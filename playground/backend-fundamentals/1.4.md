### Coding

Kode nyata yang "jalan" tapi melanggar ketiga idiom di atas:

```java
public class DiscountCoupon {
    // (1) mutable — public field, tidak ada final, bisa di-subclass (bukan final class)
    public String code;
    public double percentage;
    private List<String> applicableCategories;

    public DiscountCoupon(String code, double percentage, List<String> categories) {
        this.code = code;
        this.percentage = percentage;
        this.applicableCategories = categories; // (2) tidak ada defensive copy — reference dipegang langsung
    }

    public List<String> getApplicableCategories() {
        return applicableCategories; // (3) tidak ada defensive copy saat keluar — caller bisa .add()/.remove() langsung
    }

    // (4) equals pakai getClass() dicampur field yang tidak stabil (percentage bisa diubah langsung lewat public field)
    @Override
    public boolean equals(Object o) {
        if (getClass() != o.getClass()) return false; // NPE kalau o null!
        DiscountCoupon other = (DiscountCoupon) o;
        return code.equals(other.code);
    }
    // (5) tidak ada hashCode() override sama sekali — melanggar kontrak equals/hashCode dari Lesson 1.2

    // (6) tidak ada toString() override — default Object@hash tidak berguna untuk log
}
```

### Exercise / Task

**Bagian 1 — Perbaiki `DiscountCoupon` di atas.** Identifikasi keenam pelanggaran bernomor, lalu refactor jadi class yang benar-benar immutable (5 aturan Item 17), `equals`/`hashCode`/`toString` yang benar dan comply kontrak (termasuk perbaiki bug NPE di `equals`), DAN ubah constructor publik jadi static factory method dengan nama yang idiomatis — jelaskan kenapa static factory lebih tepat di sini dibanding constructor biasa (kaitkan ke salah satu dari 5 keunggulan di Theory, bukan cuma "supaya lebih modern"). Sertakan justifikasi tiap perubahan.
    Bagian 1 — DiscountCoupon

    Enam pelanggarannya:

    1. Mutable state — public field bisa diubah langsung.
    2. No defensive copy saat masuk — caller masih memegang categories.
    3. No defensive copy saat keluar — getter mengekspos mutable List.
    4. equals() bermasalah — getClass() perlu null-safe, dan desain equality harus berdasarkan state immutable yang stabil.
    5. Tidak override hashCode() — melanggar kontrak: jika a.equals(b), maka a.hashCode() == b.hashCode().
    6. Tidak override toString() — logging/debugging menjadi tidak informatif.

    Refactor:

    public final class DiscountCoupon {

        private final String code;
        private final double percentage;
        private final List<String> applicableCategories;

        private DiscountCoupon(
                String code,
                double percentage,
                List<String> categories) {

            this.code = Objects.requireNonNull(code);
            this.percentage = percentage;
            this.applicableCategories =
                    List.copyOf(categories);
        }

        public static DiscountCoupon of(
                String code,
                double percentage,
                List<String> categories) {

            return new DiscountCoupon(code, percentage, categories);
        }

        public String getCode() {
            return code;
        }

        public double getPercentage() {
            return percentage;
        }

        public List<String> getApplicableCategories() {
            return applicableCategories;
        }

        @Override
        public boolean equals(Object o) {
            if (this == o) return true;
            if (!(o instanceof DiscountCoupon other)) return false;

            return Double.compare(percentage, other.percentage) == 0
                    && code.equals(other.code)
                    && applicableCategories.equals(other.applicableCategories);
        }

        @Override
        public int hashCode() {
            return Objects.hash(
                    code,
                    percentage,
                    applicableCategories
            );
        }

        @Override
        public String toString() {
            return "DiscountCoupon{" +
                    "code='" + code + '\'' +
                    ", percentage=" + percentage +
                    ", applicableCategories=" + applicableCategories +
                    '}';
        }
    }

    Kenapa benar-benar immutable:

    final class → tidak bisa disubclass sehingga tidak ada subclass yang bisa mengubah/mengganggu invariant.
    Semua field private final.
    Tidak ada setter.
    Constructor melakukan List.copyOf() → defensive copy + hasilnya unmodifiable.
    Getter mengembalikan list immutable.
    State setelah construction tidak berubah.
    Kenapa static factory of()?

    Bukan sekadar "lebih modern". Salah satu keunggulan static factory adalah bisa memberikan nama yang menjelaskan cara/semantik pembuatan object.

    DiscountCoupon.of(...) menyatakan bahwa kita sedang membuat value object coupon dari data tersebut. Selain itu, static factory tidak wajib membuat instance baru setiap kali dipanggil, sehingga implementasinya nanti bisa berubah ke caching/internering tanpa mengubah API caller.

**Bagian 2 — Diagnosis.** Tim Anda punya class `Range` (merepresentasikan rentang harga minimum-maksimum) yang dipakai luas sebagai key di `Map<Range, List<Product>>` untuk mengelompokkan produk per rentang harga. Suatu hari `PremiumRange extends Range` dibuat untuk menambah field `minimumMembershipTier`, dengan `equals()` di `PremiumRange` yang override begini: kalau `o` instance `Range` biasa (bukan `PremiumRange`), bandingkan cuma `min`/`max`; kalau `o` juga `PremiumRange`, bandingkan `min`/`max`/`minimumMembershipTier` juga. Beberapa minggu kemudian ada bug aneh: `map.get(rangeKey)` dan `map.get(premiumRangeKeyDenganMinMaxSama)` kadang mengembalikan hasil **berbeda** tergantung urutan mana yang di-`put()` duluan, padahal secara logis "rentang harga"-nya sama. Jelaskan (tanpa lihat lagi Theory di atas — coba rekonstruksi sendiri) akar masalahnya, kaitkan ke properti kontrak `equals()` mana yang dilanggar, dan usulkan perbaikan strukturalnya (bukan sekadar "hati-hati saat override").

        Akar masalahnya adalah simetri (symmetry) dalam kontrak equals() dilanggar.

        Misalnya:

        Range range = new Range(100, 500);

        PremiumRange premium =
                new PremiumRange(100, 500, GOLD);

        Range.equals() mungkin berkata:

        range.equals(premium) == true

        karena dia hanya peduli min/max.

        Tetapi:

        premium.equals(range) == false

        karena PremiumRange juga membutuhkan minimumMembershipTier.

        Jadi:

        a.equals(b) == true
        b.equals(a) == false

        Kontrak symmetry rusak.

        Ini sangat berbahaya ketika object digunakan sebagai Map key. Hash map lookup mengandalkan equality secara konsisten. Akibatnya perilaku bisa tampak bergantung pada object mana yang dimasukkan/dicari terlebih dahulu.

        Perbaikan struktural

        Jangan membuat superclass dan subclass memiliki definisi equality yang berbeda berdasarkan state tambahan subclass.

        Pilihan paling aman:

        public final class Range {

            private final BigDecimal min;
            private final BigDecimal max;

            // equals/hashCode hanya min + max
        }

        Lalu:

        public final class PremiumRange {

            private final Range range;
            private final MembershipTier minimumMembershipTier;

            // equality berdasarkan range + tier
        }

        Jadi composition over inheritance.

        Contohnya:

        PremiumRange premiumRange =
                new PremiumRange(
                        new Range(min, max),
                        MembershipTier.GOLD
                );

        Dengan begitu Range dan PremiumRange bukan berada dalam inheritance hierarchy yang memaksa mereka berbagi kontrak equality.

**Bagian 3 — Pilihan constructor vs static factory.** Untuk tiap skenario berikut, tentukan constructor publik biasa atau static factory method DAN alasan singkatnya (kaitkan ke salah satu dari 5 keunggulan static factory di Theory, bukan sekadar "lebih modern"):

* (a) Class `ConnectionPool` yang HARUS hanya ada satu instance per aplikasi (singleton) — memanggil "buat pool baru" berkali-kali seharusnya mengembalikan pool yang sama, bukan membuat pool baru tiap kali.
        Static factory tidak harus membuat instance baru. ConnectionPool.getInstance() dapat selalu mengembalikan instance yang sama. Constructor public justru memungkinkan new ConnectionPool() berkali-kali.

* (b) Spring `@Service` class `OrderService` yang dependency-nya (`OrderRepository`, `PaymentClient`) di-inject oleh Spring container saat aplikasi start.
        Object lifecycle dan dependency injection dikelola Spring container. Constructor secara eksplisit menyatakan dependency: OrderService(OrderRepository repo, PaymentClient client). Tidak perlu static factory karena instance management bukan tanggung jawab class.
        
* (c) Class `UserId` (value object pembungkus `UUID` mentah) yang kadang dibuat dari `UUID` baru (`UserId.generate()`), kadang di-parse dari string yang datang dari request HTTP (`UserId.fromString(raw)`) — dua "cara membuat" yang secara semantik berbeda maksudnya.
    Static factory bisa memiliki nama yang berbeda untuk semantic creation: generate() vs fromString(). Ini jauh lebih expressive daripada constructor yang sama-sama terlihat sebagai new UserId(...).
