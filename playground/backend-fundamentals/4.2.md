**Bagian 1 — Refactor.** Diberi class berikut (field injection, 4 dependency):

```java
@Service
public class InvoiceService {
    @Autowired
    private InvoiceRepository invoiceRepository;
    @Autowired
    private CustomerClient customerClient;
    @Autowired
    private TaxCalculator taxCalculator;
    @Autowired
    private NotificationSender notificationSender;

    public Invoice createInvoice(Long customerId, BigDecimal amount) {
        Customer customer = customerClient.fetch(customerId);
        BigDecimal tax = taxCalculator.calculate(amount, customer.getCountry());
        Invoice invoice = new Invoice(customer, amount, tax);
        invoiceRepository.save(invoice);
        notificationSender.send(customer, invoice);
        return invoice;
    }
}
```

Refactor ke constructor injection. Setelah itu, **tulis 1 unit test** untuk `createInvoice(...)` yang membuktikan constructor injection Anda benar-benar bisa di-test **tanpa Spring context** (murni `new InvoiceService(...)` dengan mock).

    ```java
        @Service
        public class InvoiceService {

        private final InvoiceRepository invoiceRepository;
        private final CustomerClient customerClient;
        private final TaxCalculator taxCalculator;
        private final NotificationSender notificationSender;

        public InvoiceService(
                InvoiceRepository invoiceRepository,
                CustomerClient customerClient,
                TaxCalculator taxCalculator,
                NotificationSender notificationSender) {

            this.invoiceRepository = invoiceRepository;
            this.customerClient = customerClient;
            this.taxCalculator = taxCalculator;
            this.notificationSender = notificationSender;
        }

        public Invoice createInvoice(Long customerId, BigDecimal amount) {
            Customer customer = customerClient.fetch(customerId);

            BigDecimal tax = taxCalculator.calculate(
                    amount,
                    customer.getCountry()
            );

            Invoice invoice = new Invoice(customer, amount, tax);

            invoiceRepository.save(invoice);
            notificationSender.send(customer, invoice);

            return invoice;
        }
    }
    ```

    unit test
    ```java
    class InvoiceServiceTest {

        private InvoiceRepository invoiceRepository;
        private CustomerClient customerClient;
        private TaxCalculator taxCalculator;
        private NotificationSender notificationSender;

        private InvoiceService invoiceService;

        @BeforeEach
        void setUp() {
            invoiceRepository = mock(InvoiceRepository.class);
            customerClient = mock(CustomerClient.class);
            taxCalculator = mock(TaxCalculator.class);
            notificationSender = mock(NotificationSender.class);

            invoiceService = new InvoiceService(
                    invoiceRepository,
                    customerClient,
                    taxCalculator,
                    notificationSender
            );
        }

        @Test
        void shouldCreateInvoice() {
            Long customerId = 1L;
            BigDecimal amount = new BigDecimal("100.00");
            BigDecimal tax = new BigDecimal("10.00");

            Customer customer = mock(Customer.class);

            when(customerClient.fetch(customerId))
                    .thenReturn(customer);

            when(customer.getCountry())
                    .thenReturn("ID");

            when(taxCalculator.calculate(amount, "ID"))
                    .thenReturn(tax);

            Invoice result = invoiceService.createInvoice(customerId, amount);

            assertThat(result).isNotNull();

            verify(customerClient).fetch(customerId);
            verify(taxCalculator).calculate(amount, "ID");
            verify(invoiceRepository).save(result);
            verify(notificationSender).send(customer, result);
        }
    }
    ```

**Bagian 2 — Analisis "bau desain".** Setelah refactor Bagian 1, Anda punya constructor dengan 4 parameter. Menurut Anda, apakah ini sudah termasuk sinyal "constructor terlalu gemuk, class-nya ngelakuin terlalu banyak"? Jelaskan alasannya (boleh "belum", boleh "sudah mulai") — bukan sekadar jawab ya/tidak, tapi tunjukkan **di angka berapa** menurut Anda constructor mulai jadi sinyal masalah, dan kenapa angka itu, bukan angka lain.

        ```java
        private final InvoiceRepository invoiceRepository;
        private final CustomerClient customerClient;
        private final TaxCalculator taxCalculator;
        private final NotificationSender notificationSender;
        ```

        4 dependency masih wajar. Saya mulai menganggap constructor sebagai sinyal desain ketika dependency sudah sekitar 6–8 dependency, terutama jika dependency tersebut berasal dari banyak concern yang berbeda. Angka ini bukan aturan baku, tetapi heuristic untuk memicu pemeriksaan apakah class memiliki terlalu banyak tanggung jawab. Yang lebih penting bukan jumlahnya, tetapi apakah dependency-dependency tersebut masih mendukung satu alasan perubahan yang sama.

**Bagian 3 — Kasus setter injection yang sah.** Rancang 1 contoh nyata (boleh dari domain kerjaan Anda sehari-hari) di mana setter injection untuk dependency **optional** benar-benar masuk akal dipakai, ketimbang dipaksa masuk constructor. Tunjukkan kodenya, dan jelaskan kenapa memaksanya jadi parameter constructor wajib justru salah secara desain.

        ```java
        @Component
        public class InvoiceService {

            private InvoiceRepository invoiceRepository;

            @Autowired
            public InvoiceService(InvoiceRepository invoiceRepository) {
                this.invoiceRepository = invoiceRepository;
            }

            private NotificationSender notificationSender;

            @Autowired(required = false)
            public void setNotificationSender(
                    NotificationSender notificationSender) {
                this.notificationSender = notificationSender;
            }

            public void createInvoice(Invoice invoice) {
                invoiceRepository.save(invoice);

                if (notificationSender != null) {
                    notificationSender.send(invoice);
                }
            }
        }
        ```

    Misalnya NotificationSender memang optional karena aplikasi tertentu boleh berjalan tanpa fitur notifikasi. Kalau dipaksa masuk constructor:

    ```java
    public InvoiceService(
            InvoiceRepository repository,
            NotificationSender notificationSender)
    ```

    maka semua deployment harus menyediakan NotificationSender, padahal fitur tersebut memang opsional.


###  Questions

1. Jelaskan 3 alasan teknis (bukan "best practice kata orang") kenapa constructor injection dianggap standar di Spring modern.
    Immutability — dependency bisa final, sehingga reference tidak dapat diganti setelah object dibuat.
    Testability — object bisa dibuat langsung dengan new, tanpa Spring context atau reflection.
    Fail-fast — semua dependency wajib tersedia saat constructor dipanggil. Jika dependency tidak bisa di-resolve, bean gagal dibuat saat startup.

2. Kenapa field yang di-inject lewat `@Autowired` biasanya tidak bisa dideklarasikan `final`, sementara field constructor-injected bisa?
    Masalahnya adalah timing assignment.
    
    @Autowired
    private PaymentClient paymentClient;

    Field injection terjadi setelah object dibuat. Sedangkan:

    private final PaymentClient paymentClient;

    harus diinisialisasi ketika constructor berjalan.

    Jadi:

    public OrderService(PaymentClient paymentClient) {
        this.paymentClient = paymentClient;
    }

    bisa final karena dependency tersedia saat object dibuat.

    Sedangkan field injection mencoba mengisi field setelah constructor selesai, sehingga tidak cocok dengan aturan final.

3. Jelaskan bagaimana constructor injection membuat aplikasi Spring Boot fail-fast, dan kenapa field/setter injection tidak punya jaminan yang sama.
    constructor dipanggil di fase 1, dan kalau pakai constructor injection, **semua dependency constructor harus sudah tersedia sebelum object itu bisa lahir**. Kalau ada dependency yang tidak ketemu (misalnya lupa daftarin bean, atau ambigu 2 kandidat tanpa `@Qualifier`), Spring akan gagal **tepat di titik itu**, saat `ApplicationContext` startup — aplikasi gagal total untuk start, dengan stack trace yang jelas nunjuk ke bean mana yang bermasalah. Sedangkan Field/setter injection tidak memberikan jaminan dependency sudah tersedia pada saat constructor membuat object, karena object sudah lahir sebelum dependency tersebut diinjeksi, sehingga kejadian bukan di compile time tapi di runtime.

4. Kapan setter injection tetap pilihan yang sah, ketimbang dipaksa jadi constructor injection?
    ketika dependency itu bersifat opsional, boleh di set boleh juga tidak, jangan dipaksakan jadi wajib (constructor injection).
    Setter injection masuk akal ketika dependency memang opsional dan object tetap valid serta bisa bekerja tanpa dependency tersebut.

    Contohnya:

    private NotificationSender notificationSender;

    @Autowired(required = false)
    public void setNotificationSender(NotificationSender sender) {
        this.notificationSender = sender;
    }

    Jangan menggunakan setter injection hanya karena "dependency bisa berubah". Kalau dependency memang wajib, constructor lebih tepat.

5. Kenapa constructor dengan banyak parameter dianggap "code smell", dan apa hubungan constructor injection dengan Single Responsibility Principle?
    Efek samping penting lainnya: kalau constructor  butuh 7 parameter, itu **kelihatan** dan **berasa menyakitkan** langsung waktu Anda nulis test-nya (harus bikin 7 mock). Field injection **menyembunyikan** rasa sakit itu — class dengan 7 `@Autowired` field kelihatan "bersih" di kode, padahal secara desain sama buruknya (melanggar Single Responsibility, class-nya ngerjain terlalu banyak hal). Constructor injection membuat "bau desain" itu kelihatan lebih cepat — ini disebut efek **"constructor injection sebagai code smell detector"**.

6. Sejak versi Spring berapa `@Autowired` jadi opsional untuk constructor tunggal, dan kenapa itu tidak menghilangkan sifat dependency injection-nya?
    Contoh:

    @Service
    public class OrderService {

        private final PaymentClient paymentClient;

        public OrderService(PaymentClient paymentClient) {
            this.paymentClient = paymentClient;
        }
    }

    Spring tetap melakukan Dependency Injection.

    @Autowired bukan yang membuat constructor menjadi "DI". @Autowired hanya salah satu cara memberi instruksi eksplisit kepada Spring mengenai injection point.
