
    emailClient.getDefaultSender();

    dijalankan, emailClient sudah tersedia.

### Interview Questions

1. Jelaskan apa itu Inversion of Control, dan bagaimana Dependency Injection jadi implementasi konkretnya di Spring.
     IoC adalah prinsip/desain idea bahwa kontrol pembuatan dan pengelolaan dependency dipindahkan dari object ke container/framework. DI adalah salah satu mekanisme untuk mencapai IoC, yaitu dependency diberikan dari luar ke object. Dan DI adalah bentuk implementasi/pola untuk IoC.

2. Apa beda `BeanFactory` dan `ApplicationContext`, khususnya soal kapan bean singleton diinstansiasi?
    `BeanFactory` adalah interface container paling dasar — cuma nyediain mekanisme inti: daftarin bean definition, buat instance, resolve dependency. `ApplicationContext` **extends** `BeanFactory`, nambahin fitur enterprise: event publishing (`ApplicationEventPublisher`), internationalization (`MessageSource`), integrasi AOP otomatis, `Environment` abstraction (profile, properties).

    BeanFactory sendiri menyediakan mekanisme dasar dan tidak melakukan eager pre-instantiation seperti ApplicationContext. Bean singleton baru dibuat pas pertama kali diminta (`getBean()`). `ApplicationContext` secara default **eager** — begitu container selesai *refresh* (proses startup), **semua bean singleton non-lazy langsung diinstansiasi di muka**, sebelum ada satu request pun masuk. Ini kenapa kalau ada bean yang gagal dibuat (misalnya salah config, dependency tidak ketemu), aplikasi Spring Boot **gagal start total** dengan stack trace panjang — bukan baru error nanti pas endpoint dipanggil.

3. Apa itu `BeanDefinition`, dan kenapa registrasi definition dipisah dari instantiation jadi dua fase berbeda?
    Saat Spring "scan" `@Component`/`@Service`/`@Repository`/`@Configuration` (via `@ComponentScan`, otomatis aktif lewat `@SpringBootApplication`), yang terjadi **bukan** langsung bikin object. Yang terjadi: Spring bikin `BeanDefinition` — metadata berisi: class apa, scope apa (singleton/prototype), constructor argument apa, nama init/destroy method kalau ada, lazy atau tidak, dsb. Ini murni **data/resep**, disimpan di registry internal (`BeanDefinitionRegistry`).

    Proses startup itu **dua fase terpisah**:
    1. **Fase registrasi** — semua `BeanDefinition` didaftarkan dulu (dari component scan, dari `@Bean` method di class `@Configuration`, dari config lain). Di fase ini juga `BeanFactoryPostProcessor` jalan — hook yang bisa **memodifikasi** `BeanDefinition` sebelum ada satu bean pun dibuat (contoh nyata: `PropertySourcesPlaceholderConfigurer` yang resolve `${...}` di `@Value`).
    2. **Fase instantiation** — baru di fase ini, satu per satu `BeanDefinition` "dieksekusi" jadi object nyata, lewat urutan lifecycle di bawah.

    Kenapa dipisah begini? Spring perlu memiliki metadata/blueprint bean terlebih dahulu agar container bisa melakukan berbagai processing terhadap definition sebelum object sebenarnya dibuat.

5. Kenapa dependency yang di-inject lewat field/setter bisa `null` kalau diakses di constructor, sementara constructor-injected dependency tidak pernah begitu?
    Karena urutan lifecycle-nya constructor dulu baru lah field/setter memang begitu secara desain. Pada field/setter injection, dependency belum tersedia ketika constructor body berjalan. Pada constructor injection, dependency sudah di-resolve dan diberikan sebagai argument sebelum constructor body dijalankan. makanya kalau butuh dependency saat inisialisasi, tempatnya bukan constructor manual + field injection, tapi salah satu dari: constructor injection (dependency dijamin ada **sebelum** body constructor jalan), atau `@PostConstruct` (dijamin jalan **setelah** fase constructor inject selesai).
