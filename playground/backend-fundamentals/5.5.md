### Interview Questions

1. Apa beda *safe* dan *idempotent*? Kasih contoh method yang idempotent tapi tidak safe, dan jelaskan kenapa `DELETE` yang kedua balikin `404` tetap dianggap idempotent.
    Safe → tidak dimaksudkan mengubah state resource.
    Idempotent → efek akhirnya sama walaupun request yang sama dilakukan berkali-kali.
    Yang dibandingkan adalah state/efek server, bukan response.

    Contoh DELETE juga benar.

    DELETE /products/7 → 204
    DELETE /products/7 → 404

    Tetap idempotent karena:

    setelah request pertama → product 7 tidak ada
    setelah request kedua  → product 7 tetap tidak ada

    Response berbeda tidak membatalkan idempotency.

    Satu tambahan: PATCH memang tidak otomatis idempotent, tetapi patch tertentu bisa idempotent.

    {"price": 25000}

    diulang → tetap 25000 → idempotent.

    Sedangkan operasi konseptual seperti:

    {"op": "increment", "amount": 1}

    diulang → +2 → tidak idempotent.

2. Kapan Anda pilih `PUT`, kapan `PATCH`? Sebutkan satu bug nyata `PUT` yang muncul justru karena API-nya berevolusi (nambah field).

    * **`PUT`** = *replace*. Body adalah **representasi lengkap** resource. Server mengganti seluruh resource dengan body itu. Field yang gak ada di body? Dianggap **kosong/default**, bukan "biarin yang lama".
    * **`PATCH`** = *partial update*. Body cuma berisi **perubahan**. Yang gak disebut, gak disentuh.

    di method PUT *nambah field baru ke response* itu additive/aman. Tapi lihat efeknya ke `PUT`: Anda nambah field `weightGram` ke resource `Product`. Klien lama (mobile app versi lama) **belum tahu field itu**. Dia `GET` produk (dapat body tanpa `weightGram` karena parsernya membuang field asing, atau memang gak ditampilkan), edit nama, lalu `PUT` balik body yang **gak mengandung `weightGram`** → server yang patuh pada semantik `PUT` akan mengosongkan `weightGram`. Data hilang, gak ada error, dan bug-nya baru muncul berminggu-minggu kemudian. Ini kenapa PUT aman ketika client memang mampu mengirim representasi lengkap sesuai kontrak resource. Ketika schema berkembang, perlu strategi kompatibilitas agar client lama tidak menghilangkan field yang belum dikenalnya.

3. Jelaskan beda JSON Merge Patch dan JSON Patch. Untuk masing-masing, sebutkan satu hal yang bisa dilakukan dan satu yang tidak.

    JSON Merge Patch** (RFC 7396, `Content-Type: application/merge-patch+json`) — body-nya *berbentuk seperti resource*, cuma berisi field yang berubah:
   ```json
   { "price": 25000, "description": null }
   ```
   Aturannya: field yang disebut → di-set; field bernilai dalam JSON Merge Patch, member dengan nilai null berarti member tersebut dihapus dari target object; field yang gak disebut → dibiarkan. Gampang dibaca dan ditulis. 
   Kelemahan: (a) `null` sudah "dipakai" sebagai arti "hapus", jadi gak bisa membedakan "set jadi null" vs "hapus" (biasanya sama saja); 
              (b) **array selalu diganti total** — gak bisa "tambah 1 item ke array"; 
              (c) gak bisa operasi seperti "geser posisi".

   **JSON Patch** (RFC 6902, `Content-Type: application/json-patch+json`) — body-nya **array operasi**:
   ```json
   [ { "op": "replace", "path": "/price", "value": 25000 },
     { "op": "add", "path": "/tags/-", "value": "promo" } ]
   ```
   Lebih ekspresif (bisa `add`/`remove`/`replace`/`move`/`test`), tapi lebih verbose dan lebih sulit divalidasi & didokumentasikan. `test` op-nya bahkan bisa dipakai sebagai precondition kecil-kecilan.

   **Rekomendasi praktis:** default ke **JSON Merge Patch** untuk hampir semua kasus bisnis. JSON Patch dipakai kalau memang butuh operasi array/dokumen yang presisi (editor kolaboratif, dokumen bersarang). Jangan bikin format `PATCH` karangan sendiri tanpa `Content-Type` yang jelas — konsumen gak bisa tahu aturan mainnya dari kontrak.

4. Di Java, bagaimana Anda membedakan "field tidak dikirim" dari "field dikirim `null`" pada `PATCH`? Apa yang terjadi kalau Anda pakai `record` biasa?
    Solusi standar di ekosistem Java: `JsonNullable<T>` (library `jackson-databind-nullable`, yang juga dipakai OpenAPI Generator) — punya 3 keadaan: *undefined* (gak dikirim), *present dengan nilai*, *present dengan null*. Alternatif: terima `Map<String, Object>` (fleksibel tapi kehilangan type safety & OpenAPI schema jadi longgar).

5. Jelaskan lost update dengan timeline konkret dan bagaimana `ETag` + `If-Match` mencegahnya. Kenapa `412` (dan kapan `428`)?
     **`ETag`** (*entity tag*) = string **buram (opaque)** yang dikirim server di response, mewakili "versi" resource saat ini: `ETag: "v7"`. Klien gak boleh menebak isinya, cuma menyimpan dan mengirim balik. Header pasangannya:

    | Header | Dikirim klien saat | Artinya | Kalau gagal |
    |---|---|---|---|
    | `If-None-Match: "v7"` | `GET` (cache validation) | "Kirim datanya kalau sudah beda dari v7" | Server balikin **`304 Not Modified`** tanpa body (hemat bandwidth) |
    | `If-Match: "v7"` | `PUT`/`PATCH`/`DELETE` | "Lakukan ini **hanya kalau** versi sekarang masih v7" | Server balikin **`412 Precondition Failed`**, data gak disentuh |
    | `If-None-Match: *` | `PUT` (create-only) | "Buat ini **hanya kalau belum ada**" | `412` kalau sudah ada — mencegah timpa tak sengaja |

    Jadi satu mekanisme, dua kegunaan: **caching** (GET + `If-None-Match` → `304`) dan **concurrency control** (write + `If-Match` → `412`).

    Timeline sekarang pakai ETag:
    ```
    A: GET /products/7 → 200, ETag: "v7"
    B: GET /products/7 → 200, ETag: "v7"
    A: PUT /products/7  If-Match: "v7" → 200, ETag: "v8"    (versi naik)
    B: PUT /products/7  If-Match: "v7" → 412 Precondition Failed
    ↑ B diberi tahu: "kamu edit versi lama" → B GET ulang, lihat harga 25000, merge, coba lagi
    ```
    Update A **selamat**, B **tahu** dan harus sadar — bukan diam-diam menimpa.

    412 : terjadi ketika B update tapi masih menggunakan Etag yang sebelumnya (PRECONDITION_FAILED)
    428 : terjadi ketika header E-tag tidak dikirim kan oleh client

6. Kenapa `If-Match` saja tidak cukup tanpa `@Version`? Sebut dua "jendela" waktunya.
    Dua "jendela" bahaya — kenapa `If-Match` saja belum cukup, dan bukan berarti @Version tidak berguna. @Version melindungi concurrent update di server/database, sedangkan ETag/If-Match membawa versi yang dilihat client ke request berikutnya.

    Jadi pasangan konsepnya:

    ETag + If-Match
            ↓
    stale client detection

    @Version
            ↓
    database optimistic locking

    * **Jendela panjang (detik sampai menit):** dari saat klien `GET` sampai klien `PUT` — manusia baca, mikir, edit. Di sini yang menjaga adalah **`If-Match`**: server membandingkan versi yang dilihat klien dengan versi sekarang.
    * **Jendela pendek (milidetik):** di dalam server, antara "load entity, bandingkan versi" dan "commit UPDATE". Dua request yang **sama-sama lolos** pengecekan `If-Match` bisa bersamaan menulis (check-then-act lagi!). Di sini yang menjaga adalah **`@Version`**: Hibernate mengeluarkan `UPDATE ... SET ..., version = 8 WHERE id = ? AND version = 7`; kalau ada request lain yang sudah lebih dulu menaikkan versi, `WHERE` gak cocok, 0 baris terupdate, dan Hibernate melempar `ObjectOptimisticLockingFailureException`. Anda harus menerjemahkan exception itu jadi `412`/`409` juga.

    ```java
            // Native ON CONFLICT DO NOTHING: return 1 = kita yang menang, 0 = key sudah ada.
            // Sengaja BUKAN "save() lalu tangkap DataIntegrityViolationException": pada PostgreSQL, error di dalam
            // transaksi membuat transaksi ABORTED — query berikutnya (membaca record lama) ikut gagal.
            @Modifying
            @Query(value = """
                    INSERT INTO idempotency_key (client_id, idem_key, request_hash)
                    VALUES (:clientId, :key, :hash)
                    ON CONFLICT (client_id, idem_key) DO NOTHING
                    """, nativeQuery = true)
            int tryInsert(@Param("clientId") String clientId, @Param("key") String key, @Param("hash") String hash);

            Optional<IdempotencyRecord> findByClientIdAndIdemKey(String clientId, String idemKey);
        }

        @Service
        public class IdempotentPaymentService {

            private final IdempotencyRepository keys;
            private final PaymentService paymentService;
            private final ObjectMapper objectMapper;

            // ... constructor injection

            // SATU transaksi: baris key + efek bisnis commit/rollback BERSAMAAN.
            // Request kembar yang bersamaan akan MENUNGGU di unique index sampai request pertama commit,
            // lalu tryInsert() mengembalikan 0 dan record yang sudah lengkap tinggal di-replay.
            @Transactional
            public IdempotentResult<PaymentDto> create(String clientId, String key, CreatePaymentRequest req) {
                String hash = Sha256.hex(canonicalJson(req));

                if (keys.tryInsert(clientId, key, hash) == 0) {
                    IdempotencyRecord existing = keys.findByClientIdAndIdemKey(clientId, key).orElseThrow();
                    if (!existing.getRequestHash().equals(hash)) {
                        throw new IdempotencyKeyReuseException(
                                "Idempotency-Key '%s' sudah dipakai untuk request dengan isi berbeda.".formatted(key));   // → 422
                    }
                    return IdempotentResult.replayed(existing.getResponseStatus(), readBody(existing));
                }

                PaymentDto created = paymentService.create(req);
                keys.markCompleted(clientId, key, 201, toJson(created));
                return IdempotentResult.fresh(201, created);
            }
        }
    ```

    Request kembar yang bersamaan akan MENUNGGU di unique index sampai request pertama commit, lalu tryInsert() mengembalikan 0 dan record yang sudah lengkap tinggal di-replay.

8. Kenapa `ShallowEtagHeaderFilter` tidak bisa dipakai untuk mencegah lost update?
    ShallowEtagHeaderFilter
        ↓
    hash response body
            ↓
    cache validation
            ↓
    If-None-Match / 304

    Bukan concurrency-control mechanism.

    Untuk lost update:

    GET → ETag
    PUT → If-Match
        ↓
    compare current version
        ↓
    412 jika stale

    ETag yang digunakan untuk optimistic concurrency idealnya berasal dari versi resource yang stabil, bukan sekadar hash response yang kebetulan dikirim.

9. (Senior) Klien Anda menerima `412`. Bagaimana idealnya klien bereaksi (UX & teknis)? Apa yang berbahaya kalau klien otomatis mengulang `PUT` yang sama dengan ETag baru tanpa menampilkan perubahan ke user?
    Seharusnya, ketika menerima `412 Precondition Failed`, client melakukan reload untuk mengambil data terbaru dari server dan menampilkannya kepada user. Dengan begitu, user mengetahui bahwa resource sudah berubah sejak terakhir kali dibaca.

    Client sebaiknya tidak langsung melakukan retry dengan ETag baru tanpa memberi tahu user. Jika dilakukan secara otomatis, perubahan yang baru saja dilakukan oleh client lain bisa tertimpa oleh data lama dari client ini. Karena itu, client perlu mengambil versi terbaru, mendeteksi atau menampilkan perubahan yang terjadi, lalu melakukan merge atau meminta user menyesuaikan perubahan sebelum mengirim update kembali.

    Kasus sederhana

    User belum melakukan banyak perubahan:

    PUT
    ↓
    412
    ↓
    GET terbaru
    ↓
    tampilkan perubahan server
    Kasus user sudah melakukan perubahan lokal

    Misalnya:

    Server:

    price = 20.000

    User A mengubah:

    price = 25.000

    Sementara user B mengubah:

    description = "Arabica"

    A berhasil lebih dulu.

    B mendapat 412.

    Client B sebaiknya:

    GET latest
        ↓
    deteksi perubahan server
        ↓
    bandingkan dengan perubahan lokal
        ↓
    tampilkan conflict/merge UI
        ↓
    user memilih/menyesuaikan
        ↓
    PUT/PATCH dengan ETag terbaru

    Yang berbahaya adalah automatic blind retry:

    412
    ↓
    GET v8
    ↓
    ambil data v8
    ↓
    tempel kembali payload lama
    ↓
    PUT If-Match v8

    Karena ini dapat menghasilkan:

    A mengubah price 20.000 → 25.000

    B punya payload lama:
    price = 20.000
    name = "Kopi Baru"

    B mendapat 412

    B otomatis GET v8
    B memakai ETag v8
    B mengirim payload lamanya

    → price A bisa tertimpa kembali menjadi 20.000

    Jadi retry boleh, tetapi bukan:

    "ulang request lama dengan ETag baru."

    Yang benar:

    ambil state terbaru → rekonsiliasi perubahan → kirim perubahan yang sudah disesuaikan dengan versi terbaru.
