### Exercise / Task

**Bagian 1 — Diagnosis mekanis.** Diberi kode berikut:

```java
@Component
@Scope("prototype")
public class ShoppingCartCalculator {
    private BigDecimal runningTotal = BigDecimal.ZERO;
    public ShoppingCartCalculator addItem(BigDecimal price) {
        runningTotal = runningTotal.add(price);
        return this;
    }
    public BigDecimal getTotal() { return runningTotal; }
}

@Service
public class CheckoutService {
    private final ShoppingCartCalculator calculator; // constructor injection biasa

    public CheckoutService(ShoppingCartCalculator calculator) {
        this.calculator = calculator;
    }

    public BigDecimal checkout(List<BigDecimal> prices) {
        prices.forEach(calculator::addItem);
        return calculator.getTotal();
    }
}
```

Aplikasi ini dipakai banyak user sekaligus. Jelaskan **persis** apa yang akan terjadi kalau 2 user checkout hampir bersamaan (bukan cuma "salah", tapi jelaskan mekanismenya: kenapa `runningTotal` bisa tercampur antar user, merujuk ke titik resolusi mana di lifecycle yang jadi akar masalahnya).
   
    Constructor injection ke singleton hanya melakukan resolusi dependency ketika singleton tersebut dibuat.

    Jadi urutannya:

    ApplicationContext membuat CheckoutService
            ↓
    resolve ShoppingCartCalculator
            ↓
    buat 1 instance prototype
            ↓
    simpan reference di field calculator
            ↓
    CheckoutService dipakai User A
            ↓
    calculator yang sama
            ↓
    CheckoutService dipakai User B
            ↓
    calculator yang sama lagi

    Akibatnya:

    User A → runningTotal = 100
    User B → runningTotal = 100 + 200 = 300

    Bukan thread-safety yang menjadi akar utama, tetapi lifetime mismatch + dependency resolution hanya sekali.

    getTotal() mengembalikan state dari instance calculator yang sama, sehingga total terus terakumulasi antar checkout.

**Bagian 2 — Perbaikan dengan 2 pendekatan berbeda.** Perbaiki `CheckoutService` dengan **dua cara berbeda**: (a) `ObjectFactory<ShoppingCartCalculator>`, dan (b) scoped proxy (`proxyMode = ScopedProxyMode.TARGET_CLASS`). Tulis kode lengkap kedua versi, lalu jelaskan **1 trade-off konkret** antara keduanya (bukan cuma "sama-sama benar") — pertimbangkan hal seperti: eksplisit vs tersembunyi, kebutuhan class tidak-`final` untuk CGLIB, dan seberapa jelas niat kodenya buat pembaca lain.

    **Solusi 1 — `ObjectFactory<T>` / `Provider<T>`: inject "pabrik", bukan instance.**

    ```java
    @Service
    public class FixedCheckoutServiceWithObjectFactory {
        private final ObjectFactory<ShoppingCartCalculator> calculatorFactory;

        public FixedCheckoutServiceWithObjectFactory(ObjectFactory<ShoppingCartCalculator> calculatorFactory) {
            this.calculatorFactory = calculatorFactory; // yang di-inject adalah pabriknya
        }

        public BigDecimal getTotal() {
            return calculatorFactory.getObject().getTotal(); // getObject() = getBean() baru, TIAP panggilan
        }
    }
    ```

    **Solusi 2 — Scoped proxy: inject "wakil" yang mendelegasikan tiap panggilan.**

    ```java
        @Component
        @Scope(value = "prototype", proxyMode = ScopedProxyMode.TARGET_CLASS)
        public class ShoppingCartCalculatorProxied {
            private BigDecimal runningTotal = BigDecimal.ZERO;
            public ShoppingCartCalculatorProxied addItem(BigDecimal price) {
                runningTotal = runningTotal.add(price);
                return this;
            }
            public BigDecimal getTotal() { return runningTotal; }
        }

        @Service
        public class FixedCheckoutServiceWithProxy {
            private final ShoppingCartCalculatorProxied calculator; // constructor injection biasa

            public CheckoutService(ShoppingCartCalculatorProxied calculator) {
                this.calculator = calculator;
            }

            public BigDecimal checkout(List<BigDecimal> prices) {
                prices.forEach(calculator::addItem);
                return calculator.getTotal();
            }
        }
    ```

    Trade-off:

    ObjectFactory

    eksplisit: pembaca melihat getObject()
    jelas kapan instance baru diminta
    sedikit lebih verbose
    cocok ketika lifecycle instance memang bagian dari business flow

    Scoped proxy

    kode bisnis lebih bersih
    lifecycle tersembunyi di balik proxy
    membutuhkan class/interface yang bisa diproxy; TARGET_CLASS menggunakan CGLIB sehingga ada batasan terkait final
    lebih “magis”, sehingga lifecycle object lebih sulit terlihat dari kode

**Bagian 3 — Keputusan desain.** Untuk kasus `ShoppingCartCalculator` di atas, menurut Anda apakah `prototype` scope memang pilihan paling tepat, atau ada desain lain yang lebih sederhana (misalnya bikin `ShoppingCartCalculator` stateless — total dihitung dari parameter, bukan field mutable — sehingga bisa tetap `singleton`)? Jelaskan alasan Anda, termasuk kapan `prototype` scope **benar-benar** jadi pilihan yang tidak tergantikan (petunjuk: pikirkan kasus di mana bean stateful itu sendiri butuh dependency lain yang harus di-inject container).

    Tentu saja bisa diselesaikan dengan pendekatan yang lebih sederhana dengan bean stateless (singleton) + parameter method, tanpa perlu container mengelola instance sama sekali (`new ShoppingCartCalculator()` biasa pun sudah cukup kalau tidak butuh dependency injection ke dalamnya). Prototype scope paling masuk akal justru ketika object stateful itu **sendiri butuh dependency lain yang di-inject** (kalau tidak butuh DI sama sekali, cukup `new` manual, tidak perlu jadi bean Spring sama sekali).


### Interview Questions

1. Apa beda mendasar antara Singleton *scope* di Spring dengan Singleton *pattern* klasik (GoF)?
    GoF Singleton mengatur jumlah instance melalui class itu sendiri. Spring singleton scope mengatur jumlah instance melalui container: satu instance per ApplicationContext.

2. Kenapa bean prototype yang di-inject langsung (constructor/field injection biasa) ke bean singleton tetap kelihatan seperti "1 instance yang sama" tiap dipanggil, walau scope-nya prototype?
    Prototype bukan “jadi singleton”. Instance prototype yang pertama kali di-resolve itulah yang disimpan sebagai reference oleh singleton.

    Jadi:

    Prototype scope
        ≠
    reference field selalu prototype-aware

    Field calculator hanya sebuah reference Java biasa.

3. Sebutkan 2 cara mengatasi masalah nomor 2, dan jelaskan trade-off di antara keduanya.
    **Solusi 1 — `ObjectFactory<T>` / `Provider<T>`: inject "pabrik", bukan instance.**
    **Solusi 2 — Scoped proxy: inject "wakil" yang mendelegasikan tiap panggilan.**

    ObjectFactory eksplisit dan terlihat jelas kapan instance baru diminta; scoped proxy lebih bersih bagi consumer tetapi mekanisme resolution tersembunyi di proxy dan bergantung pada proxying mechanism.

4. Kenapa Spring container tidak memanggil destroy callback (`@PreDestroy`, dst) untuk bean prototype secara otomatis?
   Spring memang tidak secara otomatis menjalankan destruction lifecycle untuk prototype. Setelah memberikan instance kepada caller, container tidak mengelola destruction-nya.

5. Apa itu scoped proxy, dan kenapa `@RequestScope`/`@SessionScope` secara default sudah menggunakannya begitu bean itu di-inject ke singleton?
    
    kalau kita inject bean `@RequestScope` ke bean singleton (misal `@Controller`), singleton-nya cuma di-*wire* sekali saat startup — padahal saat startup itu **belum tentu ada HTTP request yang sedang aktif sama sekali**. Karena itu, `@RequestScope`/`@SessionScope` di Spring **default-nya sudah otomatis pakai scoped proxy** (Anda tidak perlu tulis `proxyMode` manual seperti contoh prototype di atas) — proxy itu yang menunda resolusi bean real sampai method-nya benar-benar dipanggil di dalam konteks request/session yang sedang aktif.

    @RequestScope secara default memang:

    @Scope(
        value = WebApplicationContext.SCOPE_REQUEST,
        proxyMode = ScopedProxyMode.TARGET_CLASS
    )

    Jadi singleton dapat memegang proxy sementara target real di-resolve berdasarkan request aktif.

6. Kenapa REST API modern cenderung menghindari `session` scope untuk menyimpan state user, dan apa alternatif yang lebih umum dipakai di produksi?
    REST API umumnya dirancang stateless, sehingga server tidak perlu mempertahankan conversational state antar-request.

    Karena dalam praktik, REST API tetap bisa menggunakan server-side session, walaupun itu mengurangi sifat stateless dan biasanya tidak ideal untuk arsitektur modern yang ingin horizontal scaling.

    JWT juga bukan satu-satunya alternatif. Bisa menggunakan:

    opaque access token + introspection
    centralized session/state store
    database
    Redis
