### Exercise / Task

Anda dipanggil untuk investigasi insiden: servis `WarehouseTransferService` di production kadang **hang total** di jam sibuk (butuh restart manual buat pulih), dan terpisah dari itu, tim customer support juga laporkan user kadang melihat stok barang yang "salah" sesaat setelah transfer stok antar-gudang selesai (lalu benar lagi beberapa detik kemudian tanpa ada yang mengubah apa pun). Berikut kodenya:

```java
public class Warehouse {
    final Object lock = new Object();
    private volatile int stock;

    public Warehouse(int initialStock) { this.stock = initialStock; }

    void deduct(int qty) { stock -= qty; }
    void add(int qty) { stock += qty; }
    int getStock() { return stock; }
}

public class WarehouseTransferService {

    // Dipanggil dari banyak thread request bersamaan, arah transfer bisa dari gudang mana pun ke mana pun
    public void transferStock(Warehouse from, Warehouse to, int qty) {
        synchronized (from.lock) {
            synchronized (to.lock) {
                if (from.getStock() < qty) {
                    throw new InsufficientStockException();
                }
                from.deduct(qty);
                to.add(qty);
                notifyStockSystem(from, to, qty); // panggilan HTTP ke servis stok pusat, ~150ms
            }
        }
    }

    private void notifyStockSystem(Warehouse from, Warehouse to, int qty) {
        // HTTP call ke servis eksternal
    }
}
```

**Tugas Anda:**

1. **Diagnosis hang total.** Dari 2 gejala yang dilaporkan, mana yang cocok dengan deadlock dan mana yang cocok dengan stale read? Jelaskan alasannya berdasarkan tabel perbandingan state thread di Visualization — bukan cuma menebak dari nama gejala.
    Gejala : Service hang total sampai perlu restart
    Diagnosis : Deadlock
    alasan : Thread saling menunggu lock dan tidak ada yang bisa maju → state BLOCKED/menunggu monitor

    Gejala : Stok terlihat salah sementara, lalu benar lagi
    Diagnosis : Stale read level sistem
    alasan : volatile sudah menjamin visibility antar-thread JVM; kemungkinan pembaca lain seperti service/cache/dashboard belum melihat state terbaru

2. **Buktikan dari kode.** Untuk gejala yang Anda diagnosis sebagai deadlock: tunjukkan persis baris/kondisi di `transferStock()` yang membuat 4 kondisi Coffman bisa terpenuhi bersamaan. Kalau Anda mengambil `jstack` dari proses yang sedang hang ini, apa yang Anda **harapkan** muncul di outputnya (sebutkan section spesifiknya)?
    Masalahnya ada di nested lock:

    synchronized (from.lock) {
        synchronized (to.lock) {

    Misalnya:

    Thread A: transfer(A → B)
    Thread B: transfer(B → A)

    Maka:

    Thread A
    lock A ✓
    menunggu lock B ...

    Thread B
    lock B ✓
    menunggu lock A ...

    Empat kondisi Coffman terpenuhi:

    Mutual exclusion → synchronized hanya bisa dimiliki satu thread.
    Hold and wait → Thread A memegang A.lock, sambil menunggu B.lock.
    No preemption → lock tidak bisa direbut paksa dari thread lain.
    Circular wait → A menunggu B, B menunggu A.

    Di jstack, yang diharapkan muncul adalah:

    Found one Java-level deadlock:
    =============================
    "Thread-A":
    waiting to lock monitor ... (object A.lock)
    which is held by "Thread-B"

    "Thread-B":
    waiting to lock monitor ... (object B.lock)
    which is held by "Thread-A"

    Section paling spesifik yang dicari: Found one Java-level deadlock: beserta informasi waiting to lock / locked.

3. **Untuk gejala yang Anda diagnosis sebagai stale read**: `stock` sudah `volatile` di kode ini — kenapa masalahnya (kalau memang masih ada) BUKAN lagi soal visibility level JVM? Petunjuk: perhatikan urutan `deduct()`/`add()` vs `notifyStockSystem()`, dan pikirkan siapa lagi yang mungkin membaca "stok" selain method ini secara langsung (mis. servis lain, cache, dashboard) — jelaskan kelas stale read mana (level JVM atau level sistem) yang lebih mungkin jadi penyebab, dan kenapa `jstack` tidak akan membantu membuktikannya.
    stock sudah:

    private volatile int stock;

    Jadi untuk JVM-level visibility, write:

    stock -= qty;
    stock += qty;

    akan terlihat oleh thread lain sesuai jaminan volatile. Jadi kemungkinan lebih besar adalah system-level stale read.

    Urutannya:

    from.deduct(qty);
    to.add(qty);

    notifyStockSystem(from, to, qty); // HTTP ~150ms

    Local JVM sudah berubah sebelum sistem eksternal diberi tahu.

    Bisa terjadi:

    Warehouse JVM
        ↓ stock sudah berubah
        ↓
    HTTP notification
        ↓ ~150ms
    Stock Service / Cache / Dashboard
        ↓
    masih membaca state lama

    Atau external service/cache mengalami propagation delay.

    Jadi masalahnya bukan:

    "Thread Java tidak melihat perubahan volatile."

    Melainkan:

    "Sistem lain belum melihat/menyajikan state terbaru."

    jstack tidak membantu membuktikan ini, karena jstack digunakan untuk melihat state thread, lock, deadlock, BLOCKED, WAITING, dll. Ia tidak menunjukkan apakah Redis/cache/database/service eksternal sudah menerima atau mem-publish state terbaru.

4. **Perbaiki `transferStock()`** supaya bebas dari risiko deadlock — pilih salah satu pendekatan dari Coding (lock ordering atau `tryLock(timeout)`) dan jelaskan kenapa Anda pilih itu untuk kasus spesifik ini (perhatikan: `from`/`to` adalah objek `Warehouse` yang jumlahnya banyak dan arah transfer sepenuhnya ditentukan runtime, bukan hardcoded 2 objek seperti contoh Simple Example).
    Untuk kasus ini saya pilih lock ordering, karena Warehouse banyak dan arah transfer ditentukan runtime.

    Buat urutan lock berdasarkan identity yang konsisten:

    public void transferStock(Warehouse from, Warehouse to, int qty) {
        if (from == to) {
            throw new IllegalArgumentException("Source and destination must differ");
        }

        Warehouse first = from;
        Warehouse second = to;

        if (System.identityHashCode(first) > System.identityHashCode(second)) {
            first = to;
            second = from;
        }

        synchronized (first.lock) {
            synchronized (second.lock) {
                if (from.getStock() < qty) {
                    throw new InsufficientStockException();
                }

                from.deduct(qty);
                to.add(qty);
            }
        }
    }

    Intinya semua thread selalu memperoleh lock dalam urutan yang sama.

    Contoh:

    A → B  => lock A lalu B
    B → A  => tetap lock A lalu B

    Sehingga tidak mungkin:

    A pegang A → tunggu B
    B pegang B → tunggu A

    Kenapa bukan tryLock(timeout)?

    Karena transfer harus mendapatkan dua lock secara atomik. tryLock membutuhkan handling ketika lock kedua gagal: release lock pertama, retry/abort, dan menentukan behaviour transaksi. Untuk jumlah warehouse banyak dengan ordering deterministik, lock ordering lebih sederhana dan predictable.

5. **Satu perbaikan tambahan** yang tidak berhubungan dengan lock sama sekali, tapi seharusnya Anda usulkan berdasarkan prinsip granularity dari Lesson 2.1 (alasan #3) — ada satu baris di dalam `synchronized` block ini yang seharusnya sudah jadi tanda bahaya sejak Lesson 2.1, sekarang di lesson ini konsekuensinya jadi lebih jelas kenapa itu berbahaya (hubungkan ke durasi lock dipegang dan seberapa besar window untuk terjadinya deadlock).
    notifyStockSystem(from, to, qty); // HTTP ~150ms

    karena berada di dalam:

    synchronized (first.lock) {
        synchronized (second.lock) {
            ...
            notifyStockSystem(...);
        }
    }

    Artinya lock bisa dipegang ±150 ms atau lebih.

    Akibatnya:

    Thread A
    lock Warehouse A
    lock Warehouse B
    HTTP 150ms  ← lock masih dipegang
                    ↓
    Thread lain yang butuh A/B harus menunggu

    Ini memperbesar lock contention dan memperbesar window terjadinya deadlock bila pola locking salah.

    Idealnya:

    synchronized (...) {
        synchronized (...) {
            // validasi + update stock saja
        }
    }

    // setelah lock dilepas
    notifyStockSystem(from, to, qty);

    Bahkan lebih baik lagi, notification dibuat asynchronous/event-driven sehingga external HTTP call tidak memperpanjang critical section.
