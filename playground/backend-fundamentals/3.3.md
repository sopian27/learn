**Bagian 1 — Temukan & perbaiki.** Kode berikut punya kombinasi 2 dari 3 pola leak yang dibahas di lesson ini (tidak dikasih tahu yang mana). Identifikasi keduanya, jelaskan **mekanisme reachability**-nya persis (siapa GC Root-nya, jalur reference-nya lewat mana), lalu tulis versi perbaikannya.

```java
@Component
public class AuditTrailService implements ApplicationListener<OrderPlacedEvent> {

    private static final Map<Long, List<String>> auditLog = new HashMap<>();
    private static final ThreadLocal<String> currentActor = new ThreadLocal<>();

    public void setCurrentActor(String actor) {
        currentActor.set(actor);
    }

    @Override
    public void onApplicationEvent(OrderPlacedEvent event) {
        String actor = currentActor.get();
        auditLog.computeIfAbsent(event.getOrderId(), id -> new ArrayList<>())
                 .add(actor + " placed order at " + Instant.now());
    }
}
```

(Petunjuk: `ApplicationListener` yang didaftarkan sebagai Spring bean itu sendiri bukan sumber leak-nya — Spring mengelola siklus hidupnya dengan benar. Fokus ke 2 field static di atas.)

    Dua pola yang paling jelas adalah:

    Static collection yang tumbuh tanpa batas.
    ThreadLocal yang tidak dibersihkan pada thread pool.

    Keduanya berbeda mekanisme, tetapi sama-sama dapat menyebabkan objek tetap reachable lebih lama dari yang seharusnya.

    Issue 1 — Static collection yang tumbuh tanpa batas

    Kode:

    private static final Map<Long, List<String>> auditLog = new HashMap<>();

    Masalahnya bukan karena HashMap atau ArrayList otomatis menyebabkan leak. Masalahnya adalah data terus ditambahkan, tetapi tidak ada kebijakan penghapusan atau pembatasan ukuran.

    Setiap kali event baru datang:

    auditLog.computeIfAbsent(event.getOrderId(), id -> new ArrayList<>())
            .add(actor + " placed order at " + Instant.now());

    Jika orderId baru terus berdatangan, map akan terus memiliki entry baru. Jika order yang sama menerima banyak event, list-nya juga terus bertambah.

    Mekanisme reachability

    Jalur reference-nya:

    GC Root
    ↓
    Class object AuditTrailService
    ↓
    static field auditLog
    ↓
    HashMap
    ↓
    List<String>
    ↓
    String audit entries

    auditLog adalah static, sehingga map tersebut tetap reachable selama class yang memilikinya masih loaded.

    Akibatnya:

    GC terjadi
        ↓
    GC memeriksa auditLog
        ↓
    Entry lama masih reachable
        ↓
    Entry tidak dikumpulkan
        ↓
    Entry baru terus ditambahkan
        ↓
    Retained heap terus bertambah

    Jadi, GC tetap berjalan, tetapi baseline heap dapat terus naik karena objek lama masih reachable dari GC Root.

    ###Perbaikan Issue 1

    Jika audit log memang harus disimpan. Perbaikannya adalah menggunakan penyimpanan dengan lifecycle yang jelas, misalnya database, atau cache yang 
    
    memiliki batas ukuran dan eviction policy.

    @Component
    public class AuditTrailService
            implements ApplicationListener<OrderPlacedEvent> {

        private static final int MAX_ENTRIES_PER_ORDER = 100;

        private final Map<Long, List<String>> auditLog = new ConcurrentHashMap<>();

        @Override
        public void onApplicationEvent(OrderPlacedEvent event) {
            auditLog.computeIfAbsent(
                    event.getOrderId(),
                    id -> Collections.synchronizedList(new ArrayList<>())
            );

            List<String> entries = auditLog.get(event.getOrderId());

            synchronized (entries) {
                if (entries.size() >= MAX_ENTRIES_PER_ORDER) {
                    entries.remove(0);
                }

                entries.add(
                        "order placed at " + Instant.now()
                );
            }
        }
    }

    Issue 2 — ThreadLocal yang tidak dibersihkan

    Kode:

    private static final ThreadLocal<String> currentActor = new ThreadLocal<>();

    Masalahnya:

    public void setCurrentActor(String actor) {
        currentActor.set(actor);
    }

    Value di-set, tetapi tidak pernah di-remove.

    Mekanisme reachability

    Jalur reference-nya:

    GC Root
    ↓
    Thread yang hidup di thread pool
    ↓
    Thread.threadLocals
    ↓
    ThreadLocalMap
    ↓
    Entry
    ↓
    value = String actor

    Secara konseptual, ThreadLocalMap menyimpan:

    Entry {
        key   = WeakReference<ThreadLocal>
        value = String actor
    }

    Yang penting:

    Key adalah weak reference.
    Value adalah strong reference.
    Selama thread masih hidup dan value masih tersimpan, value tetap reachable.

    Jadi:

    Request A
        ↓
    currentActor.set("Alice")
        ↓
    ThreadLocalMap menyimpan value "Alice"
        ↓
    Request selesai
        ↓
    Tidak ada remove()
        ↓
    Thread pool thread tetap hidup
        ↓
    "Alice" masih reachable

    Jika value hanya String kecil, dampaknya mungkin tidak besar. Tetapi jika value berupa object besar, misalnya:

    ThreadLocal<RequestContext>

    yang berisi:

    RequestContext
    ↓
    UserSession
    ↓
    Large DTO
    ↓
    Large List
    ↓
    Buffers

    maka retention-nya bisa jauh lebih besar.

    Catatan: ThreadLocal bukan otomatis leak. Yang menjadi masalah adalah value yang tidak dibersihkan ketika lifecycle request selesai.

    Perbaikan Issue 2

    Gunakan try/finally agar cleanup tetap terjadi meskipun proses request mengalami exception.

    @Component
    public class AuditTrailService
            implements ApplicationListener<OrderPlacedEvent> {

        private final ThreadLocal<String> currentActor = new ThreadLocal<>();

        public void setCurrentActor(String actor) {
            currentActor.set(actor);
        }

        @Override
        public void onApplicationEvent(OrderPlacedEvent event) {
            try {
                String actor = currentActor.get();

                // Process event
                System.out.println(
                        actor + " placed order at " + Instant.now()
                );

            } finally {
                currentActor.remove();
            }
        }
    }

* **Insiden A:** Sebuah endpoint `/api/support/lookup` kadang-kadang mengembalikan data user yang **berbeda** dari user yang sedang login — tidak konsisten, cuma terjadi sesekali, dan tidak bisa direproduksi di lingkungan development (yang selalu jalan dengan 1 request dalam satu waktu).

    kasus : pola 3 `ThreadLocal` yang tidak dibersihkan menjadi issue Correctness bug. 
    
    Mekanisme terjadinya

    Misalnya:

    Request A → User Alice
    Request B → User Bob

    Thread pool:

    pool-1-thread-1

    Urutannya:

    Request A
        ↓
    ThreadLocal.set("Alice")
        ↓
    Request A selesai
        ↓
    Tidak ada remove()
        ↓
    Thread tetap hidup
        ↓
    Request B memakai thread yang sama
        ↓
    ThreadLocal.get()
        ↓
    Masih membaca "Alice"

    Akibatnya:

    User Bob
        ↓
    Request B
        ↓
    ThreadLocal.get()
        ↓
    "Alice"
        ↓
    Data Alice dikembalikan

    Ini bukan hanya memory leak. Ini juga correctness bug dan potensi kebocoran data antar-user.

    Investigasi konkret yang akan saya lakukan

    Sebelum menyimpulkan, saya akan:

    Cari seluruh penggunaan ThreadLocal
    Di mana set() dilakukan?
    Di mana get() dilakukan?
    Apakah ada remove()?
    Apakah cleanup dilakukan dalam finally?
    Periksa lifecycle thread pool
    Apakah thread digunakan ulang?
    Apakah request A dan B bisa dilayani thread yang sama?
    Tambahkan logging sementara
    User ID.
    Thread name.
    ThreadLocal value.
    Request ID.

    Contoh:

    log.info(
        "thread={}, requestId={}, userId={}, actor={}",
        Thread.currentThread().getName(),
        requestId,
        userId,
        currentActor.get()
    );

    Jika terlihat:

    Request A → thread-1 → user=Alice
    Request B → thread-1 → user=Alice

    padahal Request B seharusnya Bob, maka hipotesis ThreadLocal contamination semakin kuat.

    Buat reproduksi dengan fixed thread pool 1 thread.

    Jika bug hanya muncul ketika thread digunakan ulang, maka itu bukti kuat bahwa lifecycle cleanup bermasalah.

    Diagnosis paling mungkin: Pola 1 — Static/singleton collection yang tumbuh tanpa batas

    Ini adalah kandidat paling kuat dari gejala yang diberikan.

    Namun, tidak cukup hanya melihat grafik heap untuk membedakan pola 1 dan pola 2.

    Baseline naik mengindikasikan adanya retained objects yang terus bertambah.

    Tetapi penyebabnya bisa:

    Static collection.
    Singleton bean collection.
    Listener yang tidak di-unregister.

    ThreadLocal value yang tertahan.
    Object graph lain yang tetap reachable.

    JVM lama
        ↓
    Semua object heap dibuang
        ↓
    JVM baru
        ↓
    Collection mulai kosong

    Request baru
        ↓
    Object baru masuk
        ↓
    Collection bertambah
        ↓
    Object lama tetap reachable
        ↓
    Baseline naik lagi

    Maka:

    Restart hanya mengembalikan heap ke kondisi awal. Restart tidak memperbaiki retention path.

        Dominator tree.
        Retained heap terbesar.
        Object count yang terus bertambah.
        GC Root path.

    2. Cari collection yang terus tumbuh

        Misalnya:

        HashMap
        ArrayList
        ConcurrentHashMap

        Lalu lihat siapa yang menahannya:

        GC Root
        ↓
        static field
        ↓
        Map
        ↓
        Entry
        ↓
        Large object graph

    3. Periksa listener/observer

        Cari pola:

        listeners.add(listener);

        tetapi tidak ada:

        listeners.remove(listener);

        atau:

        unregister(listener);

        Jika listener tidak di-unregister, retention path-nya bisa:

        GC Root
        ↓
        EventPublisher
        ↓
        listeners
        ↓
        Listener
        ↓
        Session
        ↓
        Large object graph

**Bagian 3 — Jalankan kode.** Jalankan `ThreadLocalLeakDemo` dari bagian Coding di atas. Tempel output yang Anda dapat, lalu jelaskan dengan kata Anda sendiri: kenapa "Request B" bisa membaca value yang di-set "Request A", dikaitkan dengan struktur `ThreadLocalMap` (key weak reference, value strong reference) yang dibahas di Theory — dan apa yang akan berubah dari output itu kalau ditambahkan `requestData.remove()` di akhir task "Request A".

        public class ThreadLocalLeakDemo {
            private static final ThreadLocal<String> requestData = new ThreadLocal<>();

            public static void main(String[] args) throws InterruptedException {
                // Pool 1 thread -> gampang lihat thread yang sama dipakai ulang
                ExecutorService pool = Executors.newFixedThreadPool(1);

                // "Request A"
                pool.submit(() -> {
                    requestData.set("data milik Request A");
                    System.out.println(Thread.currentThread().getName() + " set: " + requestData.get());
                    // LUPA requestData.remove() -- ini bug-nya
                });

                Thread.sleep(200);

                // "Request B" -- dilayani thread pool yang SAMA (karena pool cuma 1 thread)
                pool.submit(() -> {
                    String leaked = requestData.get();
                    System.out.println(Thread.currentThread().getName() + " baca di awal Request B: " + leaked);
                    // Kalau output-nya "data milik Request A", itu BUKTI kebocoran --
                    // Request B belum pernah memanggil requestData.set() sama sekali!
                });

                Thread.sleep(200);
                pool.shutdown();
            }
        }

        output :
            pool-1-thread-1 set: data milik Request A
            pool-1-thread-1 baca di awal Request B: data milik Request A

        penjelasan : 
            Karena ThreadLocal menyimpan value per thread, bukan per request.

            Kode:

            private static final ThreadLocal<String> requestData = new ThreadLocal<>();

            Request A:

            requestData.set("data milik Request A");

            Value tersebut disimpan di ThreadLocalMap milik thread yang menjalankan task.

            Secara konseptual:

            pool-1-thread-1
                ↓
            ThreadLocalMap
                ↓
            Entry
                ↓
            key   = WeakReference<ThreadLocal>
            value = "data milik Request A"

            Ketika Request A selesai, kode tidak memanggil:

            requestData.remove();

            Akibatnya:

            Thread pool tetap hidup
                ↓
            ThreadLocalMap tetap hidup
                ↓
            Value tetap tersimpan
                ↓
            Request B memakai thread yang sama
                ↓
            requestData.get()
                ↓
            "data milik Request A"

            Jadi, Request B membaca value lama karena thread yang sama masih memiliki value tersebut.


### Interview Questions

1. Jelaskan kenapa `ConcurrentHashMap` yang thread-safe tetap bisa jadi sumber memory leak. Apa yang membedakan "thread-safe" dari "tidak bocor"?
     
    ConcurrentHashMap yang thread-safe tetap bisa menjadi sumber memory leak karena thread-safety dan memory management adalah dua masalah yang berbeda.

    Thread-safety menjawab:

    “Apakah beberapa thread boleh mengakses atau memodifikasi map secara bersamaan tanpa merusak struktur data?”

    Memory management menjawab:

    “Kapan entry lama sudah tidak dibutuhkan dan boleh dibuang?”

    Contoh:

    private final ConcurrentHashMap<Long, UserSession> sessions
            = new ConcurrentHashMap<>();

    public void register(Long userId, UserSession session) {
        sessions.put(userId, session);
    }

    Jika setiap user baru ditambahkan, tetapi tidak pernah ada:

    sessions.remove(userId);

    maka map akan terus tumbuh.

    Mekanisme reachability-nya:

    GC Root
    ↓
    Singleton bean
    ↓
    ConcurrentHashMap
    ↓
    Entry
    ↓
    UserSession
    ↓
    Object graph milik session

    Selama entry masih berada di map, session tetap reachable dan tidak eligible for GC.

    Jadi:

    Thread-safe bukan berarti memory-safe.

    ConcurrentHashMap bisa aman diakses banyak thread, tetapi tetap mengalami unbounded retention jika tidak memiliki eviction atau cleanup policy.

2. Sebuah listener terdaftar di singleton registry lewat lambda yang meng-capture sebuah object session. Jelaskan **rantai reference lengkap** dari GC Root sampai ke object session itu, dan kenapa menutup socket/koneksi saja tidak cukup untuk membuat session itu eligible for GC.
    
    Misalnya:

    registry.register(event -> session.send(event));

    Lambda tersebut dapat menyimpan reference ke session.

    Jika registry hidup selama aplikasi berjalan dan listener tidak pernah di-unregister, maka retention path-nya bisa seperti ini:

    GC Root
    ↓
    Spring ApplicationContext
    ↓
    Singleton Registry
    ↓
    listeners
    ↓
    Lambda listener
    ↓
    Captured session
    ↓
    Session object graph

    Atau jika registry disimpan di static field:

    GC Root
    ↓
    Class object
    ↓
    static registry
    ↓
    listeners
    ↓
    Lambda
    ↓
    Session

    Menutup socket saja tidak cukup, karena menutup socket hanya mengakhiri koneksi jaringan. Itu tidak otomatis menghapus reference Java ke object session.

    Misalnya:

    Socket sudah ditutup
        ↓
    Session masih direferensikan listener
        ↓
    Listener masih direferensikan registry
        ↓
    Session tetap reachable
        ↓
    GC tidak boleh membebaskannya

    Karena itu, lifecycle yang benar harus mencakup:

    Listener listener = event -> session.send(event);

    registry.register(listener);

    // Saat session selesai
    registry.unregister(listener);
    session.close();

    Urutan cleanup dapat disesuaikan dengan desain sistem, tetapi reference ke listener harus dilepas dari registry jika session memang sudah tidak dibutuhkan.

3. Jelaskan struktur internal `ThreadLocalMap`: kenapa key-nya `WeakReference` tapi value-nya strong reference, dan konsekuensi apa yang muncul dari desain asimetris ini.

    Secara konseptual, ThreadLocalMap menyimpan entry seperti ini:

    Entry {
        WeakReference<ThreadLocal<?>> key;
        Object value;
    }

    Artinya:

    key   → weak reference
    value → strong reference

    Misalnya:

    ThreadLocal<LargeObject> local = new ThreadLocal<>();

    local.set(new LargeObject());

    Secara konseptual:

    Thread
    ↓
    ThreadLocalMap
    ↓
    Entry
    ├── key   → WeakReference<ThreadLocal>
    └── value → LargeObject

    Kenapa key dibuat weak?

    Agar object ThreadLocal itu sendiri tidak dipertahankan hanya karena masih ada entry di ThreadLocalMap.

    Jika tidak ada strong reference lain ke object ThreadLocal, maka key dapat menjadi null setelah GC.

    Contoh:

    ThreadLocal object
        ↓
    Tidak ada strong reference lain
        ↓
    GC
        ↓
    key menjadi null
    Lalu apa masalahnya?

    Value tetap strong reference.

    ThreadLocalMap
    ↓
    Entry
    ├── key   = null
    └── value = LargeObject

    Selama entry tersebut masih berada di map milik thread yang hidup, value masih reachable.

    Ini disebut stale entry.

    Apakah stale entry otomatis dibersihkan?

    Tidak ada background thread khusus yang secara berkala membersihkan semua stale entry.

    Cleanup dapat terjadi ketika operasi tertentu pada ThreadLocalMap, seperti:

    get()
    set()
    remove()

    memicu proses pembersihan entry stale.

    Tetapi tidak ada jaminan setiap operasi langsung membersihkan semua stale entry.

    Jadi, jika thread hidup lama dan stale entry tidak tersapu, value dapat tertahan lebih lama dari yang diharapkan.

4. Kenapa `ThreadLocal` yang tidak dibersihkan jadi jauh lebih berbahaya di aplikasi dengan thread pool (seperti server Spring Boot) dibanding aplikasi yang selalu membuat thread baru per unit kerja?
    
    Karena thread pool menggunakan thread yang hidup lama dan dipakai ulang.

    Misalnya:

    Request A → pool-1-thread-1
    Request B → pool-1-thread-1

    Request A:

    requestData.set("data milik A");

    Jika tidak ada:

    requestData.remove();

    maka value tetap berada di ThreadLocalMap milik thread tersebut.

    Ketika Request B menggunakan thread yang sama:

    requestData.get();

    Request B dapat membaca value dari Request A.

    Mekanismenya:

    Request A
    ↓
    ThreadLocal.set("A")
    ↓
    ThreadLocalMap menyimpan value "A"
    ↓
    Request A selesai
    ↓
    Tidak ada remove()
    ↓
    Thread tetap hidup
    ↓
    Request B memakai thread yang sama
    ↓
    ThreadLocal.get()
    ↓
    "A"
    Bagaimana dengan aplikasi yang selalu membuat thread baru?

    Jika setiap unit kerja membuat thread baru dan thread tersebut benar-benar mati setelah pekerjaan selesai, maka ketika thread mati:

    Thread mati
    ↓
    ThreadLocalMap tidak lagi reachable
    ↓
    Value menjadi eligible for GC

    Jadi, perbedaan utamanya adalah:

    Thread baru per unit kerja | Thread pool
    Thread biasanya mati setelah pekerjaan selesai| Thread hidup lama
    ThreadLocalMap ikut hilang ketika thread mati | ThreadLocalMap tetap hidup
    Value lebih cepat kehilangan retention path | Value dapat tertahan sampai thread mati atau di-remove

    Thread pool bukan penyebab tunggal leak. ThreadLocal yang tidak dibersihkan + thread yang hidup lama adalah kombinasi yang berbahaya.

5. Selain memory leak, sebutkan risiko lain yang bisa muncul dari `ThreadLocal` yang tidak dibersihkan di lingkungan thread pool. Berikan contoh konkret.
    Risiko lainnya adalah correctness bug, terutama kebocoran context antar-request.

    Misalnya:

    private static final ThreadLocal<String> currentUser
            = new ThreadLocal<>();

    Request A:

    currentUser.set("Alice");

    Request A selesai, tetapi tidak melakukan cleanup.

    Request B menggunakan thread yang sama:

    String user = currentUser.get();

    Jika kode menganggap:

    “Kalau request baru, pasti ThreadLocal kosong.”

    maka asumsi tersebut salah.

    Request B dapat membaca:

    "Alice"

    padahal user yang sedang login adalah Bob.

    Akibatnya bisa terjadi:

    Data user A dikembalikan ke user B.
    Authorization menggunakan user yang salah.
    Audit log mencatat actor yang salah.
    Tenant context tertukar.
    Transaction context atau tracing context terbawa ke request lain.

    Jadi:

    ThreadLocal contamination bukan hanya masalah memory. Ini bisa menjadi masalah correctness dan security.

6. Seorang junior engineer bilang "saya pakai `HashMap` biasa buat cache di service saya, kok lama-lama out of memory ya?" — jelaskan ke dia apa yang salah, dan solusi konkret apa yang harus dipakai sebagai gantinya.
    
    Yang salah bukan semata-mata karena menggunakan HashMap.

    HashMap bisa menjadi cache yang valid. Masalahnya adalah jika cache tersebut terus menambah entry tanpa kebijakan pembuangan.

    Misalnya:

    private final Map<Long, UserProfile> cache = new HashMap<>();

    public UserProfile getUser(Long userId) {
        return cache.computeIfAbsent(
                userId,
                id -> loadUserProfile(id)
        );
    }

    Jika setiap user baru memiliki ID yang berbeda dan tidak pernah ada eviction:

    Request user 1
    ↓
    cache.put(1, profile1)

    Request user 2
    ↓
    cache.put(2, profile2)

    Request user 3
    ↓
    cache.put(3, profile3)

    Maka:

    GC Root
    ↓
    Singleton bean
    ↓
    cache
    ↓
    UserProfile entries

    Entry lama tetap reachable.

    GC tidak dapat membebaskannya hanya karena entry tersebut sudah jarang digunakan.

    Solusi konkret

    Gunakan cache yang memiliki lifecycle dan eviction policy yang jelas.

    Contohnya:

    Maximum size — batasi jumlah entry.
    TTL — entry kedaluwarsa setelah waktu tertentu.
    Idle expiration — entry dihapus jika lama tidak digunakan.
    Explicit invalidation — hapus ketika data berubah atau session selesai.
    External cache — jika kebutuhan cache lebih besar dari memory JVM.

    Contoh konsep:

    Cache
    ↓
    Maximum size
    ↓
    TTL / eviction
    ↓
    Entry lama dibuang

    Misalnya:

    Cache<Long, UserProfile> cache = Caffeine.newBuilder()
            .maximumSize(10_000)
            .expireAfterWrite(Duration.ofMinutes(10))
            .build();

    Dengan demikian, cache tidak terus tumbuh tanpa batas.

    Kesimpulan

    Cache tanpa eviction bukan otomatis “salah”, tetapi jika entry terus bertambah tanpa batas dan tidak ada alasan bisnis untuk mempertahankannya, maka secara praktis itu adalah unbounded retention.
