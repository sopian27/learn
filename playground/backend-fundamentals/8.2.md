### Exercise / Task

```java
    // AllocationChurnDemo.java
    // Simulasi beban kerja khas web service: banyak object jangka pendek,
    // sedikit yang jadi long-lived (masuk "cache").
    import java.util.ArrayList;
    import java.util.List;

    public class AllocationChurnDemo {
        // long-lived, sengaja disimpan -> akan naik ke Old Gen
        private static final List<byte[]> longLivedCache = new ArrayList<>();

        public static void main(String[] args) throws InterruptedException {
            long start = System.currentTimeMillis();
            int iteration = 0;

            while (System.currentTimeMillis() - start < 15_000) { // jalan 15 detik
                iteration++;

                // short-lived: dibuat, dipakai sebentar, langsung tidak direference lagi
                for (int i = 0; i < 500; i++) {
                    byte[] shortLived = new byte[4 * 1024]; // 4KB, khas ukuran DTO/response kecil
                    consume(shortLived);
                }

                // sekali-sekali, sesuatu "menempel" jadi long-lived (mis. cache entry)
                if (iteration % 200 == 0) {
                    longLivedCache.add(new byte[256 * 1024]); // 256KB
                    if (longLivedCache.size() > 50) {
                        longLivedCache.remove(0); // dibatasi -- bukan unbounded leak (bandingkan Lesson 3.3)
                    }
                }
            }
            System.out.println("Selesai, iterasi: " + iteration);
        }

        private static void consume(byte[] data) {
            data[0] = 1; // sekadar "dipakai" biar tidak dioptimasi hilang JIT
        }
    }
```

Untuk masing-masing, catat: (a) total jumlah GC event yang tercatat di log, (b) pause terpanjang yang tercatat, (c) total waktu program selesai (harusnya ~15 detik + overhead GC). Buat tabel perbandingan 3 kolom, lalu jelaskan **satu kalimat kesimpulan** dari masing-masing collector: mana yang pause-nya paling pendek, mana yang GC event-nya paling sedikit (throughput terbaik), apakah itu sesuai prediksi Theory di atas.

    | ------------------- | ----------: | -----------: | --------: |

**Bagian 2 — Diagnosis skenario.** Untuk masing-masing skenario berikut, tentukan **collector mana yang paling tepat** dan jelaskan alasannya berdasarkan trade-off throughput/latency/footprint dari Theory (bukan sekadar "pilih yang paling baru"):

* **Skenario A:** Job batch nightly yang memproses 50 juta baris data dari database, transform, lalu tulis ke data warehouse. Tidak ada user yang menunggu response langsung — yang penting job selesai sebelum jam 6 pagi.
    Pilihan: Parallel GC

    Alasannya, job ini tidak memiliki user yang menunggu response secara langsung. Yang paling penting adalah throughput dan total waktu penyelesaian pekerjaan.

    Parallel GC cocok karena dapat menggunakan CPU secara paralel untuk mempercepat pekerjaan GC. Pause yang relatif lebih panjang tidak terlalu bermasalah selama job tetap selesai sebelum deadline.

* **Skenario B:** API pembayaran (payment gateway) dengan kontrak SLA p99 latency di bawah 100ms per request, heap service ini sekitar 4GB, traffic stabil (tidak ada lonjakan ekstrem).
    
    Pilihan: G1 GC

    G1 cocok sebagai pilihan awal untuk service dengan heap sekitar 4GB dan kebutuhan latency yang cukup ketat, karena G1 dirancang untuk menyeimbangkan throughput dan pause time.

    -XX:MaxGCPauseMillis adalah target pause GC, bukan jaminan latency request. Misalnya:

    -XX:+UseG1GC
    -XX:MaxGCPauseMillis=50

    Artinya JVM berusaha menyesuaikan perilaku GC agar pause mendekati target 50ms. Tetapi target tersebut bukan SLA guarantee.

    Selain itu, latency request tidak hanya dipengaruhi GC. Ada juga:

    database;
    network;
    lock contention;
    CPU scheduling;
    thread pool;
    dan aktivitas aplikasi lainnya.

    Jadi, untuk SLA p99 <100ms, G1 bisa menjadi pilihan awal, tetapi tetap harus diuji dengan workload nyata.

* **Skenario C:** Service matching engine untuk marketplace real-time bidding, heap 64GB (menyimpan order book besar di memori), kontrak dengan partner: **tidak boleh** ada pause GC di atas 10ms, karena di atas itu dianggap "downtime" oleh SLA.
    
    Pilihan: ZGC

    ZGC cocok karena kebutuhan utamanya adalah pause GC yang sangat rendah, terutama ketika heap besar dan banyak object long-lived seperti order book.

    Dengan heap 64GB, ZGC dirancang agar sebagian besar pekerjaan GC dilakukan secara concurrent sehingga aplikasi tidak perlu berhenti lama hanya karena GC.

    ZGC memang dirancang untuk pause yang sangat rendah, tetapi pause tetap dipengaruhi oleh:

    ukuran dan pola allocation;
    CPU;
    memory pressure;
    konfigurasi JVM;
    dan aktivitas aplikasi.

    Jadi, jika kontraknya benar-benar tidak boleh ada pause di atas 10ms, maka pemilihan ZGC harus divalidasi melalui load test dan observability, bukan hanya berdasarkan nama collector.

**Bagian 3 — Konsep mendalam.** Jawab dengan kata-kata sendiri:
1. Kenapa minor GC bisa "menganggap Eden kosong lagi" tanpa harus membersihkan object mati satu-satu, sementara Old Gen (mark-sweep-compact) tidak bisa melakukan trik yang sama?
    
    Minor GC tidak harus menggunakan mark-sweep-compact untuk membersihkan object mati.

    Pada Young Gen, sebagian besar object biasanya berumur pendek. Karena itu, JVM dapat menggunakan pendekatan copying / evacuation.

    Misalnya Eden berisi:

    Eden:
    [A][B][C][D][E]

    Setelah Minor GC:

    A → mati
    B → hidup
    C → mati
    D → mati
    E → hidup

    JVM cukup menyalin object yang masih hidup ke Survivor:

    Survivor:
    [B][E]

    Kemudian Eden dianggap kosong dan siap digunakan lagi.

    Jadi, JVM tidak perlu mencari dan menghapus object mati satu per satu. Object mati cukup ditinggalkan di Eden, lalu region tersebut digunakan kembali.

    Kenapa ini efisien?

    Karena Young Gen biasanya memiliki banyak object mati.

    Misalnya:

    Eden = 1GB
    Object hidup = 5%
    Object mati = 95%

    Kalau JVM harus memeriksa dan membersihkan setiap object mati satu per satu, pekerjaannya bisa tidak efisien.

    Dengan copying, JVM cukup menyalin 5% object yang hidup, lalu menganggap sisa region kosong.

    Kenapa Old Gen tidak bisa menggunakan trik yang sama?

    Old Gen biasanya memiliki lebih banyak object yang masih hidup. Misalnya:

    Old Gen = 1GB
    Object hidup = 80%
    Object mati = 20%

    Kalau semua object hidup harus disalin ke tempat baru, biaya copying bisa sangat besar.

    Karena itu, Old Gen membutuhkan pendekatan yang berbeda, misalnya:

    mark-sweep-compact

2. Jelaskan kenapa G1 disebut **region-based** mengubah cara berpikir soal "kapan full GC terjadi" dibanding GC generational klasik yang Young Gen/Old Gen-nya berupa blok kontinu tetap.

    G1 membagi heap menjadi banyak region berukuran sama, bukan satu blok Young Gen dan satu blok Old Gen yang posisinya tetap.

    Misalnya:

    Heap:
    ┌────┬────┬────┬────┬────┬────┐
    │ E  │ E  │ S  │ O  │ O  │ O  │
    └────┴────┴────┴────┴────┴────┘

    Setiap region dapat digunakan sebagai:

    Eden;
    Survivor;
    Old;
    atau Humongous region untuk object besar.

    Peran region dapat berubah sesuai kebutuhan JVM.

    Kenapa ini mengubah cara berpikir tentang Full GC?

    Pada collector generational klasik, Young Gen dan Old Gen biasanya berupa area yang relatif tetap. Ketika Old Gen penuh, JVM dapat perlu melakukan collection yang lebih besar.

    Pada G1, JVM dapat memilih region mana yang paling menguntungkan untuk dikumpulkan terlebih dahulu.

    Misalnya:

    Region A → 90% sampah
    Region B → 10% sampah
    Region C → 80% sampah

    G1 dapat memprioritaskan:

    A → C → B

    karena region yang paling banyak sampahnya berpotensi membebaskan memori lebih banyak dengan pekerjaan yang lebih sedikit.

3. ZGC bisa melakukan compaction/relocation **sambil** aplikasi tetap jalan. Jelaskan risiko correctness apa yang seharusnya muncul kalau ini dilakukan naif tanpa mekanisme khusus, dan bagaimana colored pointer + load barrier mencegah risiko itu.

    Misalnya:

    Reference → Alamat lama

    GC memindahkan object:

    Alamat lama → Alamat baru

    Kalau aplikasi masih menggunakan alamat lama tanpa mekanisme khusus, aplikasi bisa membaca object yang salah atau alamat yang sudah tidak valid.

    Cara ZGC mengatasi masalah tersebut

    ZGC menggunakan mekanisme seperti colored pointer dan load barrier.

    Secara sederhana:

    Aplikasi ingin membaca object
            ↓
        Load Barrier
            ↓
    Periksa status reference
            ↓
    Apakah object sudah dipindahkan?
        /           \
        Tidak          Ya
        ↓             ↓
    Baca object    Cari alamat baru
                        ↓
                Baca object yang benar

    Jadi, ketika aplikasi mencoba membaca reference yang masih menunjuk ke lokasi lama, load barrier dapat membantu memastikan bahwa aplikasi tetap mendapatkan object yang benar.

    Analogi sederhana

    Misalnya Andi pindah rumah:

    Alamat lama:
    Jl. Mawar No. 10

    Alamat baru:
    Jl. Melati No. 20

    Aplikasi masih memiliki alamat lama.

    Ketika aplikasi mencoba mengakses Andi:

    Pergi ke alamat lama
            ↓
    Load Barrier
            ↓
    "Oh, Andi sudah pindah."
            ↓
    Cari alamat baru
            ↓
    Jl. Melati No. 20
    Koreksi penting tentang colored pointer

    Colored pointer bukan berarti JVM menyimpan alamat baru langsung di pointer biasa seperti contoh Java-level tersebut.

    Colored pointer adalah mekanisme internal ZGC untuk menyimpan informasi status GC pada reference. Load barrier kemudian menggunakan informasi tersebut untuk membantu memastikan reference yang digunakan aplikasi tetap valid.

    Jadi, analogi alamat rumah Anda bagus untuk memahami konsep forwarding / relocation, tetapi implementasi aslinya jauh lebih kompleks.
