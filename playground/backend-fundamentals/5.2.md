### Exercise / Task

**Bagian 1 — Klasifikasi breaking vs non-breaking.** Untuk tiap perubahan berikut pada API `/orders` yang sudah production, tentukan **breaking** atau **non-breaking**, dan jelaskan **mekanisme kenapa** (siapa yang terdampak dan bagaimana):

1. Menambah field `discountAmount` baru di response `GET /orders/{id}`, nilainya `0` kalau tidak ada diskon.  (non breaking : Menambah response field umumnya tidak merusak consumer yang mengabaikan field yang tidak dikenal.)
2. Mengubah field `totalPrice` dari tipe `int` (dalam rupiah, misal `50000`) menjadi `string` berformat `"Rp 50.000"`. (breaking : Tipe dan format berubah sehingga consumer yang mengharapkan int bisa gagal parsing/deserialisasi.)
3. Mengubah `GET /orders?status=invalid_value` yang sebelumnya diam-diam mengembalikan semua order (mengabaikan filter salah), menjadi menolak dengan `400 Bad Request`. (breaking : Consumer yang sebelumnya mengandalkan fallback “semua order” sekarang mendapat 400.)
4. Menambah endpoint baru `POST /orders/{id}/cancel` untuk membatalkan order (sebelumnya pembatalan cuma bisa lewat `DELETE /orders/{id}`). (non breaking : Menambah endpoint baru tidak merusak consumer yang sudah ada)
5. Mengubah `PATCH /orders/{id}` yang sebelumnya menerima field apa saja untuk diupdate, menjadi menolak field `status` lewat endpoint ini (harus lewat endpoint khusus `POST /orders/{id}/cancel`). (breaking : Consumer yang sebelumnya boleh mengubah status akan gagal ketika request yang sama ditolak.)

**Bagian 2 — Pilih strategi & justifikasi.** Anda sedang membangun capstone Module 15 yang akan dipakai beberapa klien freelance internasional berbeda (masing-masing tidak tahu satu sama lain, rilis aplikasi mereka sendiri-sendiri dengan jadwal berbeda). Anda memperkirakan akan ada breaking change di masa depan (struktur response reporting akan berubah setelah dapat feedback klien pertama). Pilih strategi versioning (URI path / custom header / Accept header) untuk API ini, dan jelaskan **kenapa** dengan merujuk ke trade-off konkret di Theory — bukan cuma "karena paling umum dipakai".
    Saya memilih URI path versioning, misalnya /v1/orders dan /v2/orders, karena consumer API bersifat eksternal dan saya tidak bisa mengontrol jadwal deployment mereka. Path versioning lebih mudah ditemukan, didokumentasikan, diuji, dan umumnya lebih sederhana untuk caching dibanding header-based versioning. v1 tetap dipertahankan selama migration/deprecation period sehingga setiap consumer punya waktu migrasi tanpa memaksa semua client upgrade bersamaan.

**Bagian 3 — Implementasi.** Endpoint `GET /v1/orders/{id}` production Anda saat ini mengembalikan response flat:
```json
{ "id": 10, "customerName": "Budi", "customerEmail": "budi@mail.com", "total": 150000 }
```
Anda perlu mengubah struktur customer jadi nested object (`customer.name`, `customer.email`) — ini breaking change yang butuh `v2`. Implementasikan `OrderV2Controller` dengan DTO barunya (pola URI path versioning seperti contoh Coding), **tanpa mengduplikasi business logic** dari `OrderService` yang sudah ada — jelaskan juga bagaimana Anda akan menjaga `v1` tetap hidup selama masa transisi, dan kapan menurut Anda `v1` boleh benar-benar dihapus.

    ```java
        @RestController
        @RequestMapping("/v1/orders")
        public class OrderV1Controller {

            private final OrderService orderService;

            public OrderV1Controller(OrderService orderService) {
                this.orderService = orderService;
            }

            @GetMapping("/{id}")
            public ResponseEntity<OrderV1Response> getOrder(@PathVariable Long id) {
                return orderService.findById(id)
                        .map(OrderV1Response::from)
                        .map(ResponseEntity::ok)
                        .orElse(ResponseEntity.notFound().build());
            }
        }

        @RestController
        @RequestMapping("/v2/orders")
        public class OrderV2Controller {

            private final OrderService orderService;

            public OrderV2Controller(OrderService orderService) {
                this.orderService = orderService;
            }

            @GetMapping("/{id}")
            public ResponseEntity<OrderV2Response> getOrder(@PathVariable Long id) {
                return orderService.findById(id)
                        .map(OrderV2Response::from)
                        .map(ResponseEntity::ok)
                        .orElse(ResponseEntity.notFound().build());
            }
        }

        public record OrderV1Response(
            Long id,
            String customerName,
            String customerEmail,
            BigDecimal total
        ) {
            public static OrderV1Response from(Order order) {
                return new OrderV1Response(
                        order.getId(),
                        order.getCustomerName(),
                        order.getCustomerEmail(),
                        order.getTotal()

            }
        }

        public record OrderV2Response(
            Long id,
            CustomerResponse customer,
            BigDecimal total

            public static OrderV2Response from(Order order) {

                        order.getId(),
                        new CustomerResponse(
                                order.getCustomerName(),
                                order.getCustomerEmail()

                        order.getTotal()

            }
        }

        public record CustomerResponse(

                String email
    ```

### Interview Questions

1. Apa definisi paling praktis dari "breaking change" pada API? Kenapa definisinya berpusat ke sisi konsumen, bukan ke seberapa banyak kode yang Anda ubah?
    Breaking change adalah perubahan pada API yang dapat membuat consumer yang sebelumnya valid gagal berfungsi, gagal parsing, atau menghasilkan perilaku yang salah. Fokusnya pada consumer karena kontrak API dinilai dari kompatibilitas terhadap client yang sudah menggunakannya, bukan dari besar kecilnya perubahan kode server.

2. Kenapa menambah value baru ke sebuah enum bisa jadi breaking change, padahal kelihatannya cuma "nambah", bukan "menghapus/mengubah"?
    Menambah enum value dapat breaking jika consumer memiliki exhaustive handling, misalnya switch tanpa default, atau schema/deserializer yang hanya mengenal value lama. Jadi additive change tidak selalu otomatis non-breaking.

3. Bandingkan URI path versioning dan header versioning dari sisi caching dan discoverability. Kapan Anda memilih yang mana?
      URI path versioning lebih mudah di-discover karena versinya terlihat langsung di URL dan umumnya lebih sederhana untuk caching. Header versioning membuat URL tetap bersih, tetapi version information tersembunyi di request header sehingga kurang discoverable dan konfigurasi caching/CDN bisa lebih kompleks karena cache perlu mempertimbangkan header tersebut. Untuk external API dengan banyak consumer independen, saya cenderung memilih URI path karena operasional dan migrasinya lebih sederhana.

4. Jelaskan pendekatan Stripe untuk versioning (date-based header + compatibility shim). Kenapa pendekatan ini mahal untuk dibangun, dan kapan investasi itu masuk akal?
    Tiap akun Stripe "dikunci" ke tanggal versi tertentu (`Stripe-Version: 2024-06-20`) waktu pertama kali dibuat. Setiap kali Stripe ubah API secara breaking, mereka rilis versi tanggal baru, tapi akun lama dapat tetap menggunakan versi yang ditetapkan sampai Stripe melakukan perubahan terhadap lifecycle/support versi tersebut — di balik layar, request dari akun lama ditranslasi otomatis lewat compatibility shim ke logic terbaru. Ini pendekatan paling mahal untuk dibangun (butuh infrastruktur transformasi request/response per versi), tapi paling ramah untuk konsumen — mereka gak pernah dipaksa migrasi mendadak. Ini contoh nyata kenapa "versioning strategy" bukan cuma pilihan sintaks URL/header, tapi keputusan arsitektur jangka panjang.

5. Kenapa `standards/API_STANDARDS.md` bilang "avoid unnecessary version increments"? Apa biaya nyata dari memelihara N versi API secara paralel?
    Setiap versi yang dipertahankan menambah biaya maintenance: testing, bug fixing, security patching, dokumentasi, monitoring, dan kemungkinan backport. Karena itu versioning sebaiknya hanya dilakukan ketika perubahan benar-benar breaking; perubahan additive sebaiknya tetap di versi yang sama.

6. Anda menemukan breaking change yang harus dilakukan, tapi semua konsumennya adalah service internal yang Anda kontrol penuh deploy-nya. Apakah Anda tetap bikin versi baru? Jelaskan alasannya.
    Tidak selalu perlu membuat versi baru. Karena consumer internal berada dalam kontrol organisasi yang sama, saya bisa mengoordinasikan perubahan antara producer dan consumer, melakukan migration terjadwal, lalu deploy keduanya secara terkontrol. Versioning tetap diperlukan jika consumer tidak bisa dimigrasikan secara serentak, memiliki lifecycle independen, atau perubahan harus didukung dalam waktu lama.
