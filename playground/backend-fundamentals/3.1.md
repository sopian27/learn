**Bagian 1 — Prediksi tempat & lifecycle.** Untuk kode berikut, jelaskan **untuk setiap variabel/object bernomor**: (a) apakah dia disimpan di stack atau heap, dan (b) kapan tepatnya (kondisi apa) dia menjadi eligible for GC.

```java
public class ReportGenerator {
    private static final Map<String, Report> reportCache = new HashMap<>(); // (1)

    public void generate(String customerId) {
        int retryCount = 0;                          // (2)
        Report report = buildReport(customerId);      // (3)

        if (shouldCache(customerId)) {
            reportCache.put(customerId, report);       // (4)
        }

        report = null;                                 // (5)
        System.out.println("Selesai generate untuk " + customerId);
    }

    private Report buildReport(String customerId) {
        Report r = new Report(customerId);              // (6)
        return r;
    }

    private boolean shouldCache(String customerId) {
        return customerId.startsWith("VIP");
    }
}
```

Jawab untuk tiap nomor (1)-(6): tempat penyimpanan (stack/heap, dan kalau heap sebutkan itu reference-nya di mana), lalu untuk (3) dan (6) khususnya — jelaskan **2 skenario berbeda** (kalau `shouldCache()` return `true` vs `false`) kapan object `Report` yang dibuat di `buildReport()` benar-benar jadi eligible for GC.
    (a) apakah dia disimpan di stack atau heap
        1. reportCache: reference static yang terkait dengan class, menunjuk ke object HashMap di heap. HashMap tersebut menjadi reachable melalui GC Root/class static reference, selama class masih loaded.
        2. stack
        3. skenario shouldCache() = true -> stack : report, belum eligible GC, karena masih reachable melalui reportCache.
           skenario shouldCache() = false -> stack : report, eligible GC, karena report = null.
        4. customerId: reference → stack frame; String object yang direferensikan → heap.
        5. stack
        6.  skenario shouldCache() = true -> reference-nya di stack, object-nya di heap
            skenario shouldCache() = false -> reference-nya di stack, object-nya di heap

    (b) kapan tepatnya (kondisi apa) dia menjadi eligible for GC.
        ketika report = null dan object report tidak ada yang reacable dari GC Root, maka object report jadi kandidat untuk GC.

### Interview Questions

1. Jelaskan perbedaan mendasar antara apa yang disimpan di stack dan apa yang disimpan di heap, untuk sebuah local variable bertipe object.
    
    Stack menyimpan local variable dan, jika variabel tersebut bertipe object, biasanya yang disimpan adalah reference menuju object.

    Sedangkan object itu sendiri berada di heap.

    public void process() {
        User user = new User("Sopian");
    }

    Jadi user adalah reference yang berada dalam stack frame, sedangkan new User("Sopian") adalah object yang berada di heap.

2. Kenapa `someObject = null;` tidak menjamin object itu langsung jadi eligible for GC? Berikan contoh konkret situasi di mana ini gagal.
    someObject = null hanya menghilangkan satu reference dari local variable ke object. Itu tidak menjamin object langsung menjadi eligible for GC.

    Object baru menjadi eligible for GC jika tidak ada lagi reference yang reachable dari GC Root.
    
    contoh : 

        public class ReachabilityDemo {
            // GC Root: static field
            private static final List<byte[]> leak = new ArrayList<>();

            public static void main(String[] args) throws InterruptedException {
                for (int i = 0; i < 5; i++) {
                    byte[] someObject = new byte[10 * 1024 * 1024]; // 10MB per iterasi
                    leak.add(someObject); // sengaja disimpan -> tetap reachable dari GC Root "leak"
                    someObject = null;    // reference lokal putus, TAPI objectnya tetap hidup lewat "leak"

                    System.gc(); // cuma "saran", JVM boleh mengabaikannya
                    Thread.sleep(200);
                    System.out.printf("Iterasi %d — used heap: %.1f MB%n",
                        i, (Runtime.getRuntime().totalMemory() - Runtime.getRuntime().freeMemory()) / 1024.0 / 1024.0);
                }

            }
        }

3. Apa itu GC Root, dan sebutkan minimal 3 contoh yang termasuk GC Root.
    GC Root adalah object/reference tertentu yang dianggap sebagai titik awal traversal reachability.
    1. Local variables/reference pada active thread stack
    2. Static fields
    3. Active threads
    4. JNI references
    5. Beberapa reference yang dikelola JVM/runtime

4. Jelaskan kenapa Java tidak menggunakan reference counting untuk garbage collection, dan apa konsekuensi praktis dari pilihan desain ini (bandingkan dengan bahasa yang pakai reference counting).
    Java tidak menggunakan reference counting sebagai mekanisme utama GC karena reference counting memiliki masalah dengan circular reference.

    Contohnya:

    class A {
        B b;
    }

    class B {
        A a;
    }

    Misalnya:

    A → B
    ↑   ↓
    └───┘

    Jika tidak ada lagi reference dari GC Root ke A, sebenarnya A dan B sudah tidak dapat digunakan.

    Tetapi jika menggunakan reference counting:

    A memiliki reference count = 1
    B memiliki reference count = 1

    karena keduanya masih saling menunjuk, reference count tidak pernah menjadi 0. Akibatnya cycle tersebut tidak dapat dibersihkan hanya dengan reference counting.

    Java menggunakan pendekatan tracing GC berdasarkan reachability. Jika object tidak lagi reachable dari GC Root, object tersebut dapat menjadi eligible for GC meskipun masih memiliki reference ke object lain dalam cycle.

    Konsekuensinya, Java dapat menangani circular reference, tetapi garbage collection memerlukan proses tracing dan memiliki overhead seperti pause dan CPU usage.

    Python berbeda karena menggunakan reference counting sebagai mekanisme utama, tetapi Python juga memiliki mekanisme tambahan untuk menangani reference cycles.

5. Sebuah service melempar `OutOfMemoryError: Metaspace` setelah berjalan lama. Apa yang membedakan ini dari `OutOfMemoryError: Java heap space` dari sisi akar penyebab yang mungkin?
    `OutOfMemoryError: Java heap space` berarti JVM gagal mengalokasikan object baru di Java Heap.

    Kemungkinan penyebabnya antara lain:

    * terlalu banyak object yang masih reachable
    * memory leak
    * heap terlalu kecil
    * allocation rate terlalu tinggi

    Heap dapat dikontrol dengan konfigurasi seperti:

    ```bash
    -Xms
    -Xmx
    ```

    Sedangkan:

    `OutOfMemoryError: Metaspace`

    berhubungan dengan memory yang digunakan untuk metadata class, bukan object Java biasa di heap.

    Salah satu kemungkinan penyebabnya adalah jumlah class yang terus bertambah, misalnya karena:

    * dynamic class generation
    * classloader yang terus dibuat dan tidak dapat di-unload
    * proxy/class generation yang tidak terkendali

    Contohnya aplikasi yang terus membuat class melalui framework/proxy sehingga class metadata terus bertambah.

    Metaspace juga dapat memiliki batas melalui:

    ```bash
    -XX:MaxMetaspaceSize
    ```

    Jadi perbedaan utamanya adalah:

    ```text
    Java heap space → heap untuk object
    Metaspace       → metadata class
    ```


6. Kenapa `System.gc()` tidak bisa diandalkan untuk memastikan garbage collection benar-benar terjadi saat itu juga?
     System.gc() tidak bisa diandalkan untuk memastikan garbage collection terjadi saat itu juga karena pemanggilan tersebut hanya merupakan request atau hint kepada JVM.

    JVM tetap memiliki keputusan akhir apakah GC perlu dijalankan dan kapan GC dijalankan.

    Selain itu, meskipun GC dijalankan, tidak berarti semua object yang tidak digunakan langsung dibersihkan pada saat itu.

    Jadi:

    System.gc();

    bukan berarti:

    "jalankan GC sekarang dan bersihkan semua garbage."

    Melainkan lebih seperti:

    "JVM, saya menyarankan agar kamu mempertimbangkan melakukan GC."

    Karena itu aplikasi tidak boleh bergantung pada System.gc() untuk mengontrol memory management.
