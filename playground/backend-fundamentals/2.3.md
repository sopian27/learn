### Exercise / Task

Anda punya 2 service call yang **saling bergantung** (dependent, bukan independen kayak Exercise 2.2):

```java
public class OrderSummaryService {

    // Panggilan 1: ambil data customer dari customer ID
    public Customer fetchCustomer(String customerId) { /* ~120ms, network call */ }

    // Panggilan 2: BUTUH loyaltyTier dari hasil panggilan 1, ambil diskon aktif berdasarkan tier itu
    public Discount fetchDiscountForTier(String loyaltyTier) { /* ~90ms, network call */ }

    // Panggilan 3: independen, gak butuh apa pun dari 1 atau 2
    public List<Product> fetchRecommendedProducts(String customerId) { /* ~200ms, network call */ }

    public OrderSummary getSummary(String customerId) {
        Customer customer = fetchCustomer(customerId);
        Discount discount = fetchDiscountForTier(customer.getLoyaltyTier()); // bergantung ke customer
        List<Product> recommendations = fetchRecommendedProducts(customerId); // independen

        return new OrderSummary(customer, discount, recommendations);
    }
}
```

Total waktu sekarang ~410ms (120+90+200, semua sekuensial) — padahal panggilan 3 sebenarnya bisa jalan paralel sama panggilan 1+2.

**Tugas Anda:**

1. Refactor `getSummary()` jadi `getSummaryAsync()` yang return `CompletableFuture<OrderSummary>`, pakai `CompletableFuture` (bukan raw `Future`/`ExecutorService.submit()` manual). Panggilan 1→2 itu **dependen** (butuh operator yang tepat untuk ini — pikirkan lagi beda `thenApply` vs `thenCompose` dari Theory), panggilan 3 **independen** dan harus jalan paralel dengan rantai 1→2 (pikirkan operator gabung yang tepat untuk 2 hasil independen).

    ```java
    public CompletableFuture<OrderSummary> getSummaryAsync(String customerId){
        //panggilan 1-> 2 dependen
        CompletableFuture<CustomerDiscount> customerDiscountFuture = CompletableFuture
            .supplyAsync(() -> fetchCustomer(customerId), executor)
            .thenCompose(customer -> 
                CompletableFuture
                    .supplyAsync(() -> fetchDiscountForTier(customer.getLoyaltyTier()), executor)
                    .exceptionally(ex -> {
                        log.warn("Discount gagal untuk {}", customerId, ex);
                        return Discount.NONE;
                    })
                    .thenApply(discount ->
                        new CustomerDiscount(customer, discount)
                    )
            );
        
        //panggilan 3 independen
        CompletableFuture<List<Product>> recommendationsFuture = CompletableFuture
            .supplyAsync(() -> fetchRecommendedProducts(customerId), executor);

        return customerDiscountFuture.thenCombine(
            recommendationsFuture, (cd, recommendations) -> new OrderSummary(cd.customer(), cd.discount(), recommendations)
            );

    }
    ```

    Karena call kedua menghasilkan CompletableFuture:

    fetchCustomer()
        ↓
    Customer
        ↓
    fetchDiscountForTier()
        ↓
    CompletableFuture<Discount>

    thenCompose() menghindari:

    CompletableFuture<CompletableFuture<Discount>>

    Sedangkan thenApply() cocok kalau transformasinya tidak menghasilkan Future baru.

2. Tentukan `Executor` yang Anda pakai (jangan andalkan default `commonPool()`) — sizing-nya ikuti rumus dari 2.2, sebutkan CPU-bound atau I/O-bound dan kenapa.
    ini I/O bound. karena ±120 ms + ±90 ms + ±200 ms sebagian besar thread menunggu network.

    N_threads ≈ N_cpu × (1 + W/C)
    CPU = 8
    W/C = 10

    N ≈ 8 × (1 + 10)
      = 88 threads
    
    ExecutorService ioExecutor = Executors.newFixedThreadPool(88);

    Catatan: angka 88 hanya contoh berdasarkan asumsi W/C = 10; production harus memakai pengukuran workload nyata.

3. Tambahkan exception handling: kalau `fetchDiscountForTier` gagal (misal service diskon lagi down), sistem tetap harus bisa kasih `OrderSummary` dengan `Discount.NONE` sebagai fallback — bukan gagal total. Tapi kalau `fetchCustomer` sendiri yang gagal (customer gak ketemu), seluruh operasi harus gagal (gak ada fallback yang masuk akal tanpa data customer). Tulis kode yang membedakan dua kebijakan ini di titik yang tepat dalam chain.

    Call	                    Gagal	    Kebijakan
    fetchCustomer()	            ❌	    Gagal total
    fetchDiscountForTier()	    ❌	    Discount.NONE
    fetchRecommendedProducts()	❌	    Gagal total (sesuai requirement)

    Kuncinya: recovery discount ditempatkan tepat setelah discount call:

    .supplyAsync(() -> fetchDiscountForTier(...), executor)
    .exceptionally(ex -> Discount.NONE)

    Bukan di akhir seluruh chain, karena kalau ditaruh di akhir, kegagalan customer juga bisa ikut ter-recover secara tidak sengaja.

4. **Analisis:** Kalau `getSummaryAsync()` ini dipanggil dari sebuah Spring WebFlux controller (`Mono<OrderSummary>`) yang butuh ribuan request/detik dengan backpressure ke klien, apakah `CompletableFuture` di sini masih pilihan yang tepat, atau harus ditulis ulang total pakai `Mono`/`Flux`? Jelaskan alasannya berdasarkan tabel perbandingan di Theory — apa yang berubah (atau tidak berubah) dari kebutuhan ini dibanding versi murni blocking controller.
    
    Untuk Spring WebFlux + ribuan request/detik + backpressure, lebih tepat menggunakan Mono/Flux end-to-end. Bukan karena CompletableFuture tidak async, tetapi karena:

    CompletableFuture
        ↓
    future-based async abstraction
        ↓
    WebFlux harus adaptasi ke Mono

    Sedangkan:

    Mono
    ↓
    Mono
    ↓
    Mono
    ↓
    WebFlux

    langsung berada dalam reactive pipeline.

    Kesimpulan:

    Service biasa / async API → CompletableFuture masih bagus.
    WebFlux end-to-end → prefer Mono/Flux.
    Backpressure → CompletableFuture tidak punya mekanisme backpressure.
    Mono/Flux → dirancang untuk reactive streams + backpressure.
