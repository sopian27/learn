Yang hilang:

@Tag / grouping endpoint.
@Operation + summary/description bisnis.
@ApiResponse untuk setiap status code yang mungkin.
@Content + @Schema untuk response/request.
@ExampleObject untuk contoh sukses/gagal.
Dokumentasi @PathVariable.
Dokumentasi validation error (400).
Dokumentasi 404 untuk GET /products/{id}.
Jika DTO punya enum: @Schema(description=...) pada enum/value-nya.

**Bagian 3 — Contract-first thinking.** Bayangkan Anda mau menambah endpoint baru `PATCH /orders/{id}/status` untuk mengubah status order (dipakai tim operasional internal, belum ada konsumen eksternal). Tim frontend internal minta bisa mulai kerja dari mock server **sebelum** Anda selesai implementasi backend-nya. (1) Apakah skenario ini cocok pakai code-first atau contract-first? Jelaskan alasannya merujuk kriteria di Theory. (2) Kalau pakai contract-first, tulis potongan `openapi.yaml` untuk endpoint ini (path, method, requestBody dengan enum `OrderStatus` yang didokumentasikan penuh, response 200/400/404). (3) Sebutkan satu rule yang akan Anda pasang di Spectral (linter) untuk mencegah tag generik atau response tanpa deskripsi lolos review ke depannya.

1. Pilihan

Contract-first, karena frontend ingin mulai development menggunakan mock server sebelum backend selesai.

Contract menjadi kesepakatan antara frontend dan backend: struktur request, response, status code, dan enum sudah jelas sebelum implementasi.

2. openapi.yaml
paths:
  /orders/{id}/status:
    patch:
      tags:
        - Orders
      summary: Update order status
      description: Mengubah status order untuk kebutuhan operasional internal.

      parameters:
        - name: id
          in: path
          required: true
          description: ID unik order
          schema:
            type: integer
            format: int64
          example: 1001

      requestBody:
        required: true
        content:
          application/json:
            schema:
              type: object
              required:
                - status
              properties:
                status:
                  $ref: '#/components/schemas/OrderStatus'
            example:
              status: SHIPPED

      responses:
        '200':
          description: Status order berhasil diperbarui
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Order'

        '400':
          description: Request tidak valid

        '404':
          description: Order tidak ditemukan

components:
  schemas:
    OrderStatus:
      type: string
      description: Status lifecycle order.
      enum:
        - PENDING
        - PAID
        - PROCESSING
        - SHIPPED
        - COMPLETED
        - CANCELLED
      x-enum-descriptions:
        - Order dibuat tetapi belum dibayar.
        - Pembayaran berhasil.
        - Order sedang diproses.
        - Order sudah dikirim.

### Interview Questions

1. Jelaskan beda code-first dan contract-first OpenAPI. Sebutkan satu skenario konkret yang cocok masing-masing.
    Code-first: implementasi controller dulu, lalu OpenAPI spec digenerate dari kode + anotasi seperti @Operation dan @Schema. Spec menjadi representasi dari implementasi yang sudah ada.
    Cocok: deadline sangat sempit dan API relatif sederhana, misalnya perlu demo dalam 1 minggu lalu patch/drop dalam 1 bulan.
    Contract-first: openapi.yaml dibuat dan direview dulu sebelum implementasi. Setelah contract disepakati, backend dan consumer bekerja berdasarkan contract tersebut.
    Cocok: ada tim consumer yang perlu mulai development menggunakan mock server sebelum backend selesai, atau API besar yang membutuhkan formal design review.

2. Kenapa `springfox` tidak lagi direkomendasikan untuk proyek Spring Boot 3 baru? Apa penggantinya?
     Karena Springfox sudah tidak maintained secara aktif dan tidak mendukung Spring Boot 3/Jakarta secara penuh. Penggantinya yang umum adalah springdoc-openapi, yang mendukung Spring Boot 3 dan OpenAPI 3.

3. Kenapa reusable schema (`components.schemas`) penting untuk `ApiError`, dan apa masalah nyata yang muncul kalau tidak direuse?
    Supaya schema seperti ApiError didefinisikan sekali dan digunakan kembali oleh banyak endpoint melalui $ref.

    Kalau setiap endpoint mendefinisikan error schema sendiri, akan muncul duplikasi dan inkonsistensi. Misalnya endpoint A mengembalikan message, endpoint B errorMessage, padahal seharusnya contract error-nya sama.

4. Bagaimana OpenAPI membantu memitigasi risiko "menambah value enum baru" yang dibahas di Lesson 5.2? Sebutkan mekanisme konkretnya.
    OpenAPI memaksa kita mendokumentasikan setiap enum value dan business meaning-nya. Dokumentasi juga bisa memberi catatan bahwa enum dapat bertambah.

    Dengan begitu consumer tahu bahwa enum bukan selalu daftar yang immutable dan sebaiknya menangani unknown/future value, misalnya dengan default pada switch.

    OpenAPI membantu menginformasikan dan menguji contract, tetapi tidak otomatis mencegah consumer yang salah menangani enum baru.

5. Apa fungsi tool seperti Spectral dan `openapi-diff` di pipeline CI? Bagaimana keduanya berbeda perannya?
    Spectral: melakukan linting terhadap kualitas/design spec, misalnya setiap operation harus punya description, tag tidak boleh generik, dan response tertentu harus memiliki schema.
    openapi-diff: membandingkan dua versi spec untuk mendeteksi perubahan, terutama breaking changes seperti menghapus field atau mengubah tipe data.

6. Kalau spec OpenAPI Anda bilang field X wajib (`required`), tapi kode controller ternyata membolehkan field X kosong — mana yang "benar", dan bagaimana Anda mencegah situasi ini terjadi?
    Keduanya tidak boleh dibiarkan berbeda. OpenAPI adalah contract yang dikonsumsi client, sedangkan kode adalah implementasinya. Kalau spec mengatakan required tetapi backend menerima null, berarti terjadi contract drift.

    Pencegahannya bukan sekadar melihat versi terbaru dengan openapi-diff, karena openapi-diff hanya membandingkan spec dengan spec, bukan memvalidasi spec terhadap kode.

    Yang lebih tepat:

    Validation di kode menggunakan @NotNull, @NotBlank, dll.
    Generate/document OpenAPI dari source yang sama bila memakai code-first.
    Jalankan contract/API tests di CI untuk memastikan implementasi benar-benar mengikuti contract.
    Gunakan Spectral untuk kualitas spec dan openapi-diff untuk mendeteksi breaking changes antarversi.
