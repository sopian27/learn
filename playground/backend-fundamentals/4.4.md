### Exercise / Task

**Bagian 1 — Diagnosis mekanis.** Diberi kode berikut (asumsikan `@EnableTransactionManagement` sudah aktif dan `paymentRepository`/`ledgerService` adalah bean nyata):

```java
@Service
public class PaymentService {

    private final PaymentRepository paymentRepository;
    private final LedgerService ledgerService;

    public PaymentService(PaymentRepository paymentRepository, LedgerService ledgerService) {
        this.paymentRepository = paymentRepository;
        this.ledgerService = ledgerService;
    }

    public void processPayment(Payment payment) {
        paymentRepository.save(payment);
        this.recordLedgerEntry(payment); // panggilan internal
        ledgerService.notifyExternal(payment);
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void recordLedgerEntry(Payment payment) {
        // insert ke tabel ledger, HARUS di transaksi terpisah dari processPayment
    }
}
```

Jelaskan **persis** apa yang terjadi saat `processPayment` dipanggil dari controller — apakah `recordLedgerEntry` benar-benar jalan di transaksi terpisah (`REQUIRES_NEW`) seperti yang dimaksud penulisnya? Rujuk ke mekanisme proxy/self-invocation, bukan cuma bilang "salah".
    

**Bagian 2 — Perbaikan dengan 2 pendekatan berbeda.** Perbaiki `PaymentService` di atas dengan **dua cara berbeda** dari tiga yang dibahas di Theory (self-injection, pisah bean, atau `AopContext.currentProxy()` — pilih 2 dari 3). Tulis kode lengkap kedua versi, lalu jelaskan **1 alasan konkret** kenapa Anda akan merekomendasikan salah satunya sebagai pilihan utama untuk tim produksi (bukan cuma "keduanya benar").

**Bagian 3 — JDK Dynamic Proxy vs CGLIB, kasus konkret.** Diberi dua bean berikut:

```java
public interface Notifier {
    void notify(String message);
}

@Service
public class EmailNotifier implements Notifier {
    @Transactional
    public void notify(String message) { /* ... */ }

    public void logInternal(String message) { /* method TIDAK ada di interface Notifier */ }
}
```

Kalau `spring.aop.proxy-target-class=false` (memaksa JDK dynamic proxy dipakai kalau memungkinkan), jelaskan: (a) apakah `@Transactional` di `notify(...)` tetap berfungsi normal saat dipanggil lewat reference bertipe `Notifier` — kenapa/kenapa tidak, dan (b) apa yang terjadi kalau ada kode lain yang mencoba `context.getBean(EmailNotifier.class)` (bukan `Notifier.class`) untuk memanggil `logInternal(...)`. Jelaskan mekanismenya, bukan cuma tebak hasil.
