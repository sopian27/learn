### Exercise / Task

**Bagian 1 — Diagnosis mekanis.** Diberi kode berikut (asumsikan `@EnableTransactionManagement` sudah aktif dan `paymentRepository`/`ledgerService` adalah bean nyata):

```java
@Service
public class PaymentService {

    private final PaymentRepository paymentRepository;
    private final LedgerService ledgerService;

    public PaymentService(PaymentRepository paymentRepository, LedgerService ledgerService) {
        this.paymentRepository = paymentRepository;
        this.ledgerService = ledgerService;
    }

    public void processPayment(Payment payment) {
        paymentRepository.save(payment);
        this.recordLedgerEntry(payment); // panggilan internal
        ledgerService.notifyExternal(payment);
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void recordLedgerEntry(Payment payment) {
        // insert ke tabel ledger, HARUS di transaksi terpisah dari processPayment
    }
}
```

Jelaskan **persis** apa yang terjadi saat `processPayment` dipanggil dari controller — apakah `recordLedgerEntry` benar-benar jalan di transaksi terpisah (`REQUIRES_NEW`) seperti yang dimaksud penulisnya? Rujuk ke mekanisme proxy/self-invocation, bukan cuma bilang "salah".
    Salah. recordLedgerEntry() tidak berjalan dalam transaksi REQUIRES_NEW.

    PaymentService yang dikelola Spring dapat berupa proxy:

    Controller
    ↓
    PaymentService Proxy
    ↓
    PaymentService target

    Ketika controller memanggil:

    paymentService.processPayment(payment);

    call masuk melalui proxy, sehingga advice @Transactional pada processPayment() dapat dijalankan.

    Namun di dalam processPayment() terdapat:

    this.recordLedgerEntry(payment);

    this menunjuk langsung ke target object, bukan proxy.

    Akibatnya:

    this.recordLedgerEntry()
            ↓
    target.recordLedgerEntry()

    bukan:

    proxy.recordLedgerEntry()
            ↓
    @Transactional interceptor
            ↓
    REQUIRES_NEW transaction
            ↓
    target.recordLedgerEntry()

    Jadi @Transactional(REQUIRES_NEW) pada recordLedgerEntry() tidak di-intercept.

    Tidak ada exception hanya karena self-invocation. Annotation-nya tetap ada, tetapi tidak pernah diproses oleh interceptor transaction pada call tersebut.

**Bagian 2 — Perbaikan dengan 2 pendekatan berbeda.** Perbaiki `PaymentService` di atas dengan **dua cara berbeda** dari tiga yang dibahas di Theory (self-injection, pisah bean, atau `AopContext.currentProxy()` — pilih 2 dari 3). Tulis kode lengkap kedua versi, lalu jelaskan **1 alasan konkret** kenapa Anda akan merekomendasikan salah satunya sebagai pilihan utama untuk tim produksi (bukan cuma "keduanya benar").

    versi 1 Pisah jadi 2 bean berbeda :
        
        ```java
        @Service
        public class PaymentService {

            private final PaymentRepository paymentRepository;
            private final LedgerService ledgerService;
            private final RecordLedgerEntryService recordLedgerEntryService;

            public PaymentService(PaymentRepository paymentRepository, LedgerService ledgerService, RecordLedgerEntryService recordLedgerEntryService) {
                this.paymentRepository = paymentRepository;
                this.ledgerService = ledgerService;
                this.recordLedgerEntryService  = recordLedgerEntryService;
            }

            public void processPayment(Payment payment) {
                paymentRepository.save(payment);
                recordLedgerEntryService.record(payment);
                ledgerService.notifyExternal(payment);
            }
        }
        
        @Service
        public class RecordLedgerEntryService {

            private final RecordLedgerEntryRepository recordLedgerEntryRepository;

            public RecordLedgerEntryService(RecordLedgerEntryRepository recordLedgerEntryRepository) {
                this.recordLedgerEntryRepository = recordLedgerEntryRepository;
            }

            @Transactional(propagation = Propagation.REQUIRES_NEW)
            public void record(Payment payment) {
                recordLedgerEntryRepository.save(payment);
            }
        }
        ```

    versi 2 Self-injection:

        ```java
        @Service
        public class PaymentService {

            private final PaymentRepository paymentRepository;
            private final LedgerService ledgerService;
            private final ApplicationContext context;

            public PaymentService(PaymentRepository paymentRepository, LedgerService ledgerService, ApplicationContext context) {
                this.paymentRepository = paymentRepository;
                this.ledgerService = ledgerService;
                this.context = context;
            }

            public void processPayment(Payment payment) {
                paymentRepository.save(payment);
                PaymentService self = context.getBean(PaymentService.class);
                self.recordLedgerEntry(payment);
                ledgerService.notifyExternal(payment);
            }

            @Transactional(propagation = Propagation.REQUIRES_NEW)
            public void recordLedgerEntry(Payment payment) {
                // insert ke tabel ledger
            }
        }
        ```

        kesimpulan : saya lebih menyarankan yang pertama karena lebih easy to maintain , dan menggunakkan pattern single responsibility principle bagus untuk di production, dan mudah untuk di lanjutkan oleh developer lain.


**Bagian 3 — JDK Dynamic Proxy vs CGLIB, kasus konkret.** Diberi dua bean berikut:

```java
public interface Notifier {
    void notify(String message);
}

@Service
public class EmailNotifier implements Notifier {
    @Transactional
    public void notify(String message) { /* ... */ }

    public void logInternal(String message) { /* method TIDAK ada di interface Notifier */ }
}
```

Kalau `spring.aop.proxy-target-class=false` (memaksa JDK dynamic proxy dipakai kalau memungkinkan), jelaskan: (a) apakah `@Transactional` di `notify(...)` tetap berfungsi normal saat dipanggil lewat reference bertipe `Notifier` — kenapa/kenapa tidak, dan (b) apa yang terjadi kalau ada kode lain yang mencoba `context.getBean(EmailNotifier.class)` (bukan `Notifier.class`) untuk memanggil `logInternal(...)`. Jelaskan mekanismenya, bukan cuma tebak hasil.
    a. Normal. 
        Karena notify() dideklarasikan pada interface:

        Notifier
            ↓
        notify()

        Spring dapat membuat:

        JDK Proxy
        ↓
        Notifier
        ↓
        EmailNotifier

        Ketika kode melakukan:

        Notifier notifier = context.getBean(Notifier.class);

        notifier.notify("hello");

        call masuk ke JDK proxy sehingga transaction interceptor dapat berjalan.

    b. Error:
        Dengan JDK Dynamic Proxy, object yang dikembalikan Spring adalah proxy yang terutama bertipe interface:

        Notifier proxy

        bukan:

        EmailNotifier proxy

        Karena itu:

        context.getBean(EmailNotifier.class);

        umumnya tidak dapat menemukan bean dengan tipe EmailNotifier dan akan menghasilkan NoSuchBeanDefinitionException.

        Jadi:

        context.getBean(Notifier.class)

        → berhasil.

        Sedangkan:

        context.getBean(EmailNotifier.class)

        → dapat gagal karena proxy JDK tidak merupakan subclass dari EmailNotifier.

### Interview Questions

1. Jelaskan kenapa Spring butuh proxy untuk implementasi `@Transactional`, dan di fase bean lifecycle mana proxy itu dibuat.
    Spring AOP default menggunakan proxy-based AOP.

    Secara sederhana:

    Caller
    ↓
    Proxy
    ↓
    Transaction Interceptor
    ↓
    Target Method

    Proxy dibuat oleh infrastructure Spring AOP, khususnya BeanPostProcessor seperti AbstractAutoProxyCreator, setelah proses initialization bean dan sebelum bean final dikembalikan ke container.

    Karena itu hanya invocation yang melewati proxy yang dapat di-intercept.

    Inilah alasan self-invocation menjadi masalah.
    
2. Apa beda mekanisme JDK dynamic proxy dan CGLIB, termasuk syarat/batasan masing-masing?
    JDK Dynamic Proxy

        Menggunakan interface:

        public interface Notifier {
            void notify(String message);
        }

        Proxy secara konseptual:

        Notifier Proxy
            ↓
        EmailNotifier

        Keterbatasannya:

        membutuhkan interface;
        proxy beroperasi berdasarkan interface;
        method tambahan yang hanya ada di implementation class tidak tersedia melalui reference interface.

    CGLIB

        Spring membuat subclass dari target:

        EmailNotifier$$SpringCGLIB
                ↓
        EmailNotifier

        Karena menggunakan subclassing:

        class final tidak dapat di-subclass;
        method final tidak dapat di-override;
        method private tidak dapat di-override;
        static bukan instance method dan tidak dapat di-intercept seperti method instance biasa.

3. Kenapa method `private` tidak pernah bisa di-`@Transactional`/`@Cacheable`, terlepas dari self-invocation sekalipun?
    Karena Spring AOP proxy harus dapat mengintercept invocation terhadap method tersebut.

    Pada proxy berbasis subclass, method harus dapat di-override.

    private void process() {}

    tidak dapat di-override oleh subclass.

    Akibatnya proxy tidak dapat memasang transaction interceptor pada method tersebut.

    Jadi:

    @Transactional
    private void process()

    tidak membuat method private tersebut menjadi transactional melalui Spring proxy AOP.

4. Jelaskan secara mekanis kenapa `this.method()` di dalam class yang sama tidak melewati proxy.
   Karena:

    this.method();

    adalah direct invocation pada target object.

    Misalnya:

    Proxy
    ↓
    Target
    ↓
    this.method()
    ↓
    Target.method()

    Call kedua tidak kembali ke proxy.

5. Sebutkan minimal 2 cara memperbaiki self-invocation pitfall, dan trade-off masing-masing.
    1. Self-injection

        Ambil reference bean dari Spring sehingga call dilakukan melalui proxy:

        PaymentService self =
                context.getBean(PaymentService.class);

        self.recordLedgerEntry(payment);

        Trade-off:

        tetap berada dalam satu class;
        tetapi business code menjadi bergantung pada Spring container;
        lebih sulit dibaca dibanding dependency antar-bean yang eksplisit.
    
    2. Pisah menjadi bean
        PaymentService
            ↓
        RecordLedgerEntryService

        Trade-off:

        menambah class/bean;
        tetapi boundary dan dependency lebih jelas;
        lebih mudah dipahami dan di-maintain.
    
    3. AopContext.currentProxy()

        Dengan proxy exposure:

        ((PaymentService) AopContext.currentProxy())
                .recordLedgerEntry(payment);

        Trade-off:

        tidak perlu memisahkan bean;
        tetapi coupling ke Spring AOP menjadi lebih kuat;
        mekanismenya lebih implicit dan kurang mudah dibaca.

6. Apa default proxy strategy di Spring Boot modern (`proxy-target-class`), dan kenapa itu dipilih ketimbang JDK dynamic proxy walau bean-nya implement interface?
    Spring Boot menggunakan CGLIB/class-based proxy sebagai default untuk Spring AOP ketika proxy-target-class bernilai true.

    Konfigurasinya:

    spring.aop.proxy-target-class=true

    Artinya Spring dapat membuat proxy berdasarkan subclass class target, sehingga tidak bergantung pada apakah bean memiliki interface atau tidak.

    Jika ingin menggunakan JDK Dynamic Proxy:

    spring.aop.proxy-target-class=false

    Perbedaan praktisnya penting:

    JDK Proxy
        → proxy berdasarkan interface

    CGLIB
        → proxy berdasarkan subclass class target

    Karena itu pemilihan strategy memengaruhi tipe object proxy yang dapat di-cast atau diambil dari Spring container.
