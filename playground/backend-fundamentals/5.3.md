```java

        String customerEmail,
        List<OrderItemRequest> items,
        BigDecimal totalPrice,
        BigDecimal discountAmount
) {}

public record OrderItemRequest(
        Long productId,
        Integer quantity

```

Untuk tiap celah, jelaskan **skenario input konkret** yang lolos validasi (kalau ada) tapi seharusnya ditolak, dan konsekuensinya kalau sampai lolos ke service layer/database.
    fixing :
    ```java
        public record CreateOrderRequest(
                @NotBlank
                @Email
                String customerEmail,

                @NotEmpty
                List<@Valid OrderItemRequest> items,

                @NotNull
                @PositiveOrZero
                BigDecimal totalPrice,
                
                @NotNull
                @PositiveOrZero
                BigDecimal discountAmount
        ) {}

        public record OrderItemRequest(
                @NotNull
                @Positive
                Long productId,
                
                @NotNull
                @Positive
                Integer quantity
        ) {}
        ```
        **Revisi — skenario konkret per celah:**
        - `customerEmail = ""` → tanpa `@NotBlank`, string kosong lolos dan bisa menyebabkan data customer invalid.
        - `items = []` → `List<@Valid ...>` tetap lolos karena `@Valid` cuma validasi isi list, bukan memastikan list punya item.
        - `items = [ { productId = null, quantity = 1 } ]` → tanpa `@NotNull` pada `productId`, null lolos dan bisa bikin error saat service/database cari product.
        - `quantity = 0` → `@PositiveOrZero` meloloskan 0, padahal order dengan quantity 0 tidak bermakna.
        - `totalPrice = null` → `@Positive` tidak menolak null; perlu `@NotNull`.
        - `discountAmount = 150, totalPrice = 100` → validasi field-level tetap lolos, padahal melanggar aturan bisnis/cross-field.

        ```java
        @ValidDiscount
        public record CreateOrderRequest(
                @NotBlank
                @Email
                String customerEmail,

                @NotEmpty
                List<@Valid OrderItemRequest> items,

                @NotNull
                @PositiveOrZero
                BigDecimal totalPrice,

                @NotNull
                @PositiveOrZero
                BigDecimal discountAmount
        ) {}

        public record OrderItemRequest(
                @NotNull
                @Positive
                Long productId,

                @NotNull
                @Positive
                Integer quantity
        ) {}
        ```

    public record ApiError(
            Instant timestamp,
            int status,
            String error,
            String message,
            String path,
            String traceId,
            List<FieldErrorDetail> errors
    ) {
        public static ApiError of(HttpStatus status, String errorCode, String message, String path, String traceId) {
            return new ApiError(Instant.now(), status.value(), errorCode, message, path, traceId, List.of());
        }
    }

    public record FieldErrorDetail(String field, String message, Object rejectedValue) {}

    // Centralized exception handler — SATU pintu untuk semua error, format selalu konsisten
    @RestControllerAdvice
    public class GlobalExceptionHandler {

        private static final Logger log = LoggerFactory.getLogger(GlobalExceptionHandler.class);

        // Gagal @Valid di @RequestBody
        @ExceptionHandler(MethodArgumentNotValidException.class)
        public ResponseEntity<ApiError> handleValidation(MethodArgumentNotValidException ex, HttpServletRequest req) {
            String traceId = UUID.randomUUID().toString();
            List<FieldErrorDetail> fieldErrors = ex.getBindingResult().getFieldErrors().stream()
                    .map(fe -> new FieldErrorDetail(fe.getField(), fe.getDefaultMessage(), fe.getRejectedValue()))
                    .toList();
            ApiError body = new ApiError(Instant.now(), 400, "VALIDATION_FAILED",
                    "Request tidak valid, cek field errors", req.getRequestURI(), traceId, fieldErrors);
            log.warn("Validation failed traceId={} path={} errors={}", traceId, req.getRequestURI(), fieldErrors);
            return ResponseEntity.badRequest().body(body);
        }

        // Gagal @Validated di @RequestParam/@PathVariable
        @ExceptionHandler(ConstraintViolationException.class)
        public ResponseEntity<ApiError> handleConstraintViolation(ConstraintViolationException ex, HttpServletRequest req) {
            String traceId = UUID.randomUUID().toString();
            List<FieldErrorDetail> fieldErrors = ex.getConstraintViolations().stream()
                    .map(v -> new FieldErrorDetail(v.getPropertyPath().toString(), v.getMessage(), v.getInvalidValue()))
                    .toList();
            ApiError body = new ApiError(Instant.now(), 400, "VALIDATION_FAILED",
                    "Request tidak valid, cek field errors", req.getRequestURI(), traceId, fieldErrors);
            log.warn("Constraint violation traceId={} path={} errors={}", traceId, req.getRequestURI(), fieldErrors);
            return ResponseEntity.badRequest().body(body);
        }

        // Business rule dilanggar (service layer, bukan Bean Validation)
        @ExceptionHandler(BusinessException.class)
        public ResponseEntity<ApiError> handleBusiness(BusinessException ex, HttpServletRequest req) {
            String traceId = UUID.randomUUID().toString();
            ApiError body = ApiError.of(HttpStatus.UNPROCESSABLE_ENTITY, ex.getErrorCode(), ex.getMessage(),
                    req.getRequestURI(), traceId);
            log.warn("Business rule violated traceId={} code={} path={}", traceId, ex.getErrorCode(), req.getRequestURI());
            return ResponseEntity.status(HttpStatus.UNPROCESSABLE_ENTITY).body(body);
        }

        // Fallback — SEGALA exception tak terduga. Stack trace CUMA masuk log, TIDAK pernah ke response.
        @ExceptionHandler(Exception.class)
        public ResponseEntity<ApiError> handleUnexpected(Exception ex, HttpServletRequest req) {
            String traceId = UUID.randomUUID().toString();
            log.error("Unexpected error traceId={} path={}", traceId, req.getRequestURI(), ex); // stack trace lengkap DI LOG
            ApiError body = ApiError.of(HttpStatus.INTERNAL_SERVER_ERROR, "INTERNAL_ERROR",
                    "Terjadi kesalahan pada server, tim kami sudah diberi tahu", req.getRequestURI(), traceId);
            return ResponseEntity.internalServerError().body(body);
        }
    }

**Bagian 3 — Exception handler yang hilang.** `GlobalExceptionHandler` di Coding section belum menangani kasus: request JSON-nya **cacat secara struktur** (misalnya `{"rating": "lima"` — kurung gak ditutup, atau tipe data salah total kayak string dikirim untuk field integer). Exception apa yang Spring lempar untuk kasus ini? Tulis `@ExceptionHandler` untuk menangkapnya, pastikan responsnya tetap pakai bentuk `ApiError` yang sama, dan jelaskan kenapa status code-nya harus `400` bukan `500` (padahal ini "error saat parsing", kedengarannya kayak masalah server).

    @ExceptionHandler(HttpMessageNotReadableException.class)
    public ResponseEntity<ApiError> handleMalformedJson(
            HttpMessageNotReadableException ex,
            HttpServletRequest req) {

        String traceId = UUID.randomUUID().toString();

        ApiError body = ApiError.of(
                HttpStatus.BAD_REQUEST,
                "MALFORMED_REQUEST",
                "Request body tidak valid",
                req.getRequestURI(),
                traceId
        );

        log.warn(
                "Malformed request traceId={} path={}",
                traceId,
                req.getRequestURI()
        );

        return ResponseEntity.badRequest().body(body);
    }

    karena `400` = struktur request cacat, **Bean Validation** (`@Valid`, custom `ConstraintValidator`) selalu hasilnya `400` — karena semua yang dicek di layer ini murni soal *bentuk* data (field kosong, format salah, angka di luar rentang), bukan soal aturan bisnis yang butuh data lain (misalnya "stok gak cukup", yang butuh query ke database, dan itu levelnya *service*, bukan validasi bentuk request). Bean Validation tetap 400 dalam desain lesson ini. 422 untuk business rule setelah request berhasil diparse dan lolos structural validation.

### Interview Questions

1. Jelaskan beda `@Valid` dan `@Validated` — kapan Anda butuh yang mana, dan exception apa yang muncul kalau masing-masing gagal?

    **Revisi:**
    @Valid dan @Validated sama-sama dipakai untuk validation, tapi mekanismenya beda.

    @Valid biasanya dipakai di `@RequestBody` untuk jalankan Bean Validation pada object dan nested object. Kalau gagal, Spring lempar `MethodArgumentNotValidException`.

    @Validated adalah annotation milik Spring untuk aktifkan method-level validation, misalnya `@RequestParam` dan `@PathVariable`, serta dukung validation groups. Kalau constraint pada parameter method gagal, exception yang muncul `ConstraintViolationException`.

    Gotcha penting: kalau pakai `@Min`, `@NotBlank`, dan constraint method-level tapi lupa pasang `@Validated` pada controller/class, validation tersebut tidak jalan seperti diharapkan — jadi silent no-op.

    Pola mental:
    ```
    @Valid + @RequestBody        → MethodArgumentNotValidException
    @Validated + @RequestParam/@PathVariable → ConstraintViolationException
    Lupa @Validated               → constraint method-level tidak aktif
    ```

2. Kenapa `@NotNull` saja tidak cukup untuk memvalidasi String yang wajib diisi? Apa yang seharusnya dipakai?
    **`@NotNull` doang gak cukup buat String**. `@NotNull String name` masih meloloskan `""` (string kosong) — karena `""` itu bukan `null`. Kalau maksud Anda "field wajib diisi dengan isi beneran", yang benar adalah `@NotBlank`. Ini kelas bug halus yang sering lolos code review karena kelihatannya "udah ada validasi kok".

3. Bagaimana Anda membedakan validasi yang seharusnya ada di Bean Validation (`ConstraintValidator`) vs validasi yang seharusnya ada di service layer sebagai business rule? Beri contoh masing-masing.
    1. **Validasi satu field tapi butuh logic custom** (misalnya cek komentar review gak mengandung kata terlarang — ingat gap Lesson 5.1 soal `rating` yang gak divalidasi? Ini pasangannya di sisi konten).
    @Target({ ElementType.FIELD, ElementType.PARAMETER })
    @Retention(RetentionPolicy.RUNTIME)
    @Constraint(validatedBy = NoBannedWordsValidator.class)
    public @interface NoBannedWords {
        String message() default "comment mengandung kata yang tidak diperbolehkan";
        Class<?>[] groups() default {};
        Class<? extends Payload>[] payload() default {};
    }

    @Component
    public class NoBannedWordsValidator implements ConstraintValidator<NoBannedWords, String> {

        private static final Set<String> BANNED_WORDS = Set.of("scam", "penipu", "bohong"); // contoh sederhana

        @Override
        public boolean isValid(String value, ConstraintValidatorContext context) {
            if (value == null) return true; // biarkan @NotBlank yang urus kasus null/kosong — jangan dobel tanggung jawab
            String lower = value.toLowerCase();
            return BANNED_WORDS.stream().noneMatch(lower::contains);
        }
    }

    2. **Validasi lintas-field** (cross-field) — misalnya "tanggal selesai harus setelah tanggal mulai", atau "diskon gak boleh lebih besar dari total harga". Ini gak bisa dicek dari satu field doang, butuh akses ke seluruh objek.
    
    @Target(ElementType.TYPE)
    @Retention(RetentionPolicy.RUNTIME)
    @Constraint(validatedBy = ValidDiscountValidator.class)
    public @interface ValidDiscount {
        String message() default "discountAmount tidak boleh lebih besar dari totalPrice";
        Class<?>[] groups() default {};
        Class<? extends Payload>[] payload() default {};
    }

    public class ValidDiscountValidator implements ConstraintValidator<ValidDiscount, CreateOrderRequest> {
        @Override
        public boolean isValid(CreateOrderRequest request, ConstraintValidatorContext context) {
            if (request.discountAmount() == null || request.totalPrice() == null) return true; // biar @NotNull yang urus
            return request.discountAmount().compareTo(request.totalPrice()) <= 0;
        }
    }

    @ValidDiscount
    public record CreateOrderRequest(
            @NotEmpty List<@Valid OrderItemRequest> items,
            @NotNull @PositiveOrZero BigDecimal totalPrice,
            @NotNull @PositiveOrZero BigDecimal discountAmount
    ) {}


4. Kenapa response error tidak boleh menampilkan stack trace ke klien, padahal itu informasi paling detail untuk debugging? Ke mana seharusnya detail itu pergi?
    response yang diberikan ke klien harus generik dan global yang mengabarkan field error nya atau di wrapper dulu oleh exception handler, tidak boleh detail atau membongkar stack trace, atau kondisi table atau database, karena ini adalah dapur backend tidak boleh dibuka keluar, adapun untuk error detail nya di simpan di log, untuk actionable developer tracing.  

5. Apa fungsi `traceId` di response error, dan bagaimana itu menghubungkan apa yang dilihat klien dengan apa yang ada di log server?
    traceid itu adalah unik id yang di generate manakala terjadi error di production ketika user melakukan request untuk mempermudah deveoper dalam debugging, misalkan ketika client mengirimkan ada request error 400, atau 422, kita bisa grep ke log based on traceid nya, sehingga, issue bisa segera di remidiasi.

6. `ProblemDetail` (RFC 9457) sudah disediakan Spring Boot secara native — kenapa lesson ini tetap menunjukkan cara bikin `ApiError` custom? Kapan Anda akan pilih salah satu dari keduanya?
    Spring Framework 6 / Boot 3 nyediain class `ProblemDetail` yang ngikutin standar RFC 9457 (Problem Details for HTTP APIs, obsoletes RFC 7807) — field standarnya `type`, `title`, `status`, `detail`, `instance`, plus Anda bisa nambah property custom lewat `setProperty(key, value)`. Ini **alternatif valid** buat envelope custom di atas: sudah standar industri, sudah didukung native (`ResponseEntityExceptionHandler` di Spring MVC otomatis balikin `ProblemDetail` untuk banyak exception bawaan), dan konten type-nya `application/problem+json` bikin klien yang paham RFC ini bisa parsing generik.

    Trade-off-nya: field bawaan RFC 9457 gak persis sama sama daftar wajib `standards/ERROR_HANDLING_STANDARDS.md` (gak ada `traceId`/`errors` bawaan) — jadi kalau pakai `ProblemDetail`, Anda tetap harus `setProperty("traceId", ...)` dan `setProperty("errors", fieldErrorList)` manual buat memenuhi kontrak standar repo ini. Buat course ini, kita pakai **custom envelope** (`ApiError`) di Coding section supaya field-nya eksplisit 100% cocok sama `standards/ERROR_HANDLING_STANDARDS.md` tanpa nebak-nebak mapping ke `ProblemDetail` — tapi di production nyata, `ProblemDetail` + `setProperty` sama validnya kalau tim Anda sudah sepakat itu jadi kontrak.
