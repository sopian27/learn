### Exercise / Task

### Coding

Kode nyata yang "jalan" tapi mengandung tiga pelanggaran dari Theory di atas:

```java
public class PaymentProcessor {

    // (1) checked exception generik di API publik — memaksa SEMUA pemanggil
    //     ikut throws Exception atau catch-wrap, tanpa bisa membedakan jenis kegagalan
    public void charge(String orderId, double amount) throws Exception {
        try {
            gateway.submit(orderId, amount);
        } catch (IOException e) {
            // (2) root cause dibuang — cuma pesan string yang disimpan
            throw new RuntimeException("Payment gagal: " + e.getMessage());
        }
    }

    public void chargeAll(List<Order> orders) {
        for (Order order : orders) {
            try {
                charge(order.getId(), order.getAmount());
            } catch (Exception e) {
                // (3) anti-pattern catch kosong — kegagalan per-order hilang tanpa jejak
            }
        }
    }
}
```

**Bagian 1 — Perbaiki `PaymentProcessor` di atas.** Identifikasi ketiga pelanggaran bernomor, lalu refactor dengan: (a) keputusan checked vs unchecked yang beralasan (bukan sekadar "ganti jadi unchecked"), (b) custom exception yang bermakna kalau relevan, (c) root cause selalu disertakan saat membungkus exception, (d) `chargeAll` tidak boleh menelan kegagalan diam-diam — per `standards/ERROR_HANDLING_STANDARDS.md` bagian Batch Processing ("Handle individual record failures separately... Generate failure reports"), kegagalan tiap order harus tetap tercatat meski loop lanjut ke order berikutnya. Sertakan justifikasi tiap perubahan.

    Saya akan membuat exception domain PaymentGatewayException sebagai unchecked exception:

    ```java
    public class PaymentGatewayException extends RuntimeException {

        public PaymentGatewayException(String message, Throwable cause) {
            super(message, cause);
        }
    }
    ```

    Kemudian:

    ```java
    public class PaymentProcessor {

        public void charge(String orderId, double amount) {
            try {
                gateway.submit(orderId, amount);
            } catch (IOException e) {
                throw new PaymentGatewayException(
                    "Payment gateway gagal untuk orderId=" + orderId,
                    e
                );
            }
        }

        public BatchPaymentResult chargeAll(List<Order> orders) {

            List<PaymentFailure> failures = new ArrayList<>();

            for (Order order : orders) {
                try {
                    charge(order.getId(), order.getAmount());

                } catch (PaymentGatewayException e) {

                    failures.add(
                        new PaymentFailure(
                            order.getId(),
                            e.getMessage(),
                            e
                        )
                    );

                    log.error(
                        "Payment gagal untuk orderId={}",
                        order.getId(),
                        e
                    );
                }
            }

            return new BatchPaymentResult(failures);
        }
    }
    ```

    Misalnya hasil batch:

    ```java
    public record PaymentFailure(
        String orderId,
        String reason,
        Throwable cause
    ) {}
    public record BatchPaymentResult(
        List<PaymentFailure> failures
    ) {

        public boolean hasFailures() {
            return !failures.isEmpty();
        }

        public int failureCount() {
            return failures.size();
        }
    }
    ```

    Kenapa PaymentGatewayException unchecked? IOException adalah detail teknis dari implementasi gateway. Saya tidak ingin API domain:

    charge(...)

    memaksa setiap caller mengetahui bahwa implementasinya kebetulan menggunakan IOException. Yang penting adalah caller mengetahui domain failure:

    PaymentGatewayException

    bukan:

    IOException

    Caller yang memang bisa melakukan recovery dapat menangkapnya:

    ```java
    try {
        paymentProcessor.charge(orderId, amount);
    } catch (PaymentGatewayException e) {
        retryPayment(orderId);
    }
    ```

    Sementara caller yang tidak bisa melakukan recovery tidak dipaksa melakukan catch palsu hanya supaya compiler diam. Yang paling penting: root cause

    Kode awal:

    throw new RuntimeException("Payment gagal: " + e.getMessage());

    kehilangan exception asli.

    Yang benar:

    throw new PaymentGatewayException(
        "Payment gateway gagal untuk orderId=" + orderId,
        e
    );

    Parameter e menjadi cause.

    Jadi stack trace tetap menunjukkan:

    PaymentGatewayException
        └── caused by IOException

**Bagian 2 — Diagnosis.** Sebuah scheduled job jalan tiap malam memproses ribuan record, dan dashboard monitoring menunjukkan job ini **selalu sukses** (tidak pernah muncul di alert). Tapi setelah 2 minggu, tim sadar ada ratusan record yang seharusnya terupdate tapi datanya tetap stale — tidak ada satu pun exception yang pernah tercatat di log. Berikut potongan kode job itu:

```java
for (Record record : records) {
    try {
        recordService.update(record);
    } catch (Exception e) {
        // dianggap "biar job tidak berhenti gara-gara 1 record bermasalah"
    }
}
```

Jelaskan (tanpa lihat lagi jawaban Theory di atas — coba rekonstruksi sendiri): kenapa dashboard tetap melaporkan "sukses" padahal ada kegagalan nyata, dan usulkan perbaikan yang tetap mempertahankan niat baik di komentar itu (1 record error tidak boleh menghentikan job) tanpa kehilangan visibilitas kegagalan.
    
    Kalau hanya menambahkan:

    log.error("Update gagal", e);

    memang visibility membaik. Tetapi dashboard masih bisa mengatakan:

    SUCCESS

    karena exception tetap ditangkap dan tidak pernah dikomunikasikan ke level job. Jadi kita membutuhkan dua level handling:

    Level 1 — per-record

    Jangan hentikan batch:
    ```java
    for (Record record : records) {
        try {
            recordService.update(record);
        } catch (Exception e) {
            log.error(
                "Failed to update record {}",
                record.getId(),
                e
            );

            failures.add(record.getId());
        }
    }
    ```

    Level 2 — job-level

    Setelah seluruh record selesai:
    ```java
    if (!failures.isEmpty()) {
        throw new BatchProcessingException(
            "Job selesai dengan " + failures.size() + " record gagal"
        );
    }
    ```

    Dengan begitu niat baik dari komentar tetap dipertahankan:

    1 record error tidak boleh menghentikan job.

    Tetapi kita juga mendapatkan:

    job tidak boleh pura-pura sukses ketika ada record yang gagal.

**Bagian 3 — Pilihan checked vs unchecked.** Untuk tiap skenario berikut, tentukan checked atau unchecked DAN alasan singkatnya (kaitkan ke "bisakah pemanggil pulih secara berarti?"):

* (a) Method yang mem-parsing file CSV hasil upload user — baris yang formatnya salah adalah hal biasa terjadi, dan controller di layer atas perlu menampilkan pesan validasi ke user.

        Checked
        karena ini adalah kondisi yang expected dan caller memang bisa melakukan recovery secara bermakna.

        try {
            csvService.parse(file);
        } catch (InvalidCsvException e) {
            return badRequest(e.getMessage());
        }

        Jadi ini kandidat bagus untuk checked exception, terutama jika arsitektur/team memang menggunakan checked exception untuk memaksa handling terhadap expected recoverable conditions.

* (b) Method internal `calculateDiscount(Order order)` yang dipanggil hanya setelah `order` divalidasi lengkap di layer sebelumnya — kalau `order` ternyata `null` di titik ini, itu artinya ada bug di kode pemanggil.
        Unchecked

        Karena:

        order sudah divalidasi
            ↓
        calculateDiscount()
            ↓
        order == null

        Ini bukan kondisi normal yang caller seharusnya "recover".

        Itu indikasi:

        BUG / broken invariant

        Maka tidak masuk akal memaksa semua caller:

        try {
            calculateDiscount(order);
        } catch (SomethingException e) {
            ...
        }

        Lebih tepat:

        public Money calculateDiscount(Order order) {
            Objects.requireNonNull(order, "order must not be null");

            ...
        }

* (c) Method yang memanggil API payment gateway eksternal — bisa gagal karena network timeout sesaat, dan pemanggil mungkin ingin retry.
        Unchecked custom exception, misalnya:

        PaymentGatewayException

        Alasannya sedikit lebih nuanced.

        Timeout adalah kondisi yang secara teknis bisa recoverable, misalnya:

        timeout
        ↓
        retry
        ↓
        success

        Tetapi tidak otomatis berarti harus menggunakan checked exception.

        Yang penting adalah exception tersebut memberikan informasi yang cukup agar caller yang memang punya recovery strategy dapat mengambil tindakan:

        try {
            paymentProcessor.charge(orderId, amount);
        } catch (PaymentGatewayException e) {
            retry(orderId);
        }

### Interview Questions

Coba jawab dulu sebelum minta saya review — ini bukan kuis hafalan, jawab dengan alur reasoning-nya:

1. **Kenapa *Effective Java* menyarankan unchecked exception untuk error programming/precondition violation, dan checked untuk kondisi yang pemanggil bisa pulih darinya?** Beri satu contoh nyata masing-masing.
    A. Programming error / precondition violation → unchecked

    Contoh:

    public void calculateDiscount(Order order) {
        Objects.requireNonNull(order, "order must not be null");

        // ...
    }

    Misalnya kontraknya adalah:

    calculateDiscount() hanya boleh menerima Order yang tidak null. Kalau ternyata caller memberikan null, itu bukan kondisi bisnis normal seperti:

    "User memasukkan data yang salah."

    Itu lebih mungkin berarti ada bug pada program pemanggil.

    Caller tidak punya recovery yang meaningful seperti:

    try {
        calculateDiscount(null);
    } catch (...) {
        // lalu melakukan apa?
    }

    Tidak ada tindakan bisnis yang masuk akal. Yang harus diperbaiki adalah kode pemanggilnya. Karena itu unchecked exception seperti NullPointerException, IllegalArgumentException, atau IllegalStateException cocok.

    Prinsipnya:
    Programming error → jangan paksa setiap caller menangani bug.

    B. Recoverable condition → checked

    Contoh nyata: membaca file konfigurasi yang memang bisa tidak ditemukan.

    public Config loadConfig(Path path) throws IOException {
        return Files.readString(path);
    }

    Caller mungkin memang bisa melakukan recovery:

    try {
        Config config = configLoader.loadConfig(path);
    } catch (IOException e) {
        // gunakan default config
        // atau minta user memilih file lain
    }

    Ini berbeda dengan null yang muncul akibat programming bug.

    Di sini:

    File tidak ditemukan
            ↓
    kondisi yang mungkin terjadi secara normal
            ↓
    caller punya pilihan recovery
            ↓
    checked exception masuk akal

    Sedangkan:

    Order == null
            ↓
    melanggar kontrak internal
            ↓
    caller harus diperbaiki

2. **Kenapa `catch (Exception e) {}` kosong dianggap salah satu anti-pattern paling berbahaya di production — bukan cuma soal "gaya kode jelek"?**
    
    Karena kode itu bukan sekadar "jelek". Ia mengubah informasi kegagalan menjadi informasi palsu.

    Misalnya production job memproses:

    10.000 records

    Kemudian:

    9.700 → berhasil
    300   → gagal

    Dengan:

    for (Record record : records) {
        try {
            recordService.update(record);
        } catch (Exception e) {
            // ignored
        }
    }

    yang terjadi:

    300 exception
        ↓
    catch
        ↓
    DIBUANG
        ↓
    loop lanjut
        ↓
    method selesai normal
        ↓
    scheduler melihat "SUCCESS"

    Padahal kenyataannya:

    SUCCESS = false
    Masalah #1 — False success

    Monitoring bisa mengatakan:

    Job: SUCCESS

    padahal sebagian pekerjaan gagal. Ini jauh lebih berbahaya daripada job langsung gagal. Failure menjadi silent failure.

    Masalah #2 — Menghilangkan root cause

    Ketika production engineer akhirnya menemukan data stale dua minggu kemudian, log tidak memberikan:

    record mana yang gagal
    kapan gagal
    exception apa
    stack trace
    dependency mana yang gagal
    apakah timeout/database/API issue
    berapa kali gagal

    Akibatnya debugging berubah dari:
    Biaya investigasi bisa jauh lebih besar.

    Masalah #3 — Merusak observability

    Production system biasanya punya beberapa mekanisme:

    Exception
    ↓
    Log
    ↓
    Metric
    ↓
    Alert
    ↓
    Incident

    catch kosong memutus rantai tersebut:

    Exception
    ↓
    catch {}
    ↓
    no info

    Tidak ada signal untuk sistem monitoring.

3. **Kalau Anda membungkus exception (`throw new CustomException(msg, e)`), kenapa parameter `cause` (`e`) itu wajib disertakan, bukan cukup `e.getMessage()` saja?**
    kalau hanya e.getMessage(): informasi yang tersisa hanya message nya saja tapi kita kehilangan exception object dan stack trace asli. Kalau object e ikut disertakan, Kita mendapatkan exception chain.
