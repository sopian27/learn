    ### recentOrders: gunakan ArrayList
    Karena pola akses utamanya:

    recentOrders.get(index)
    ArrayList lebih tepat daripada LinkedList.

    private final List<Order> recentOrders = new ArrayList<>();

    Kompleksitas:
    ArrayList.get(index) → O(1)
    LinkedList.get(index) → O(n)
    ArrayList.add() di akhir → O(1) amortized

    Insertion order tetap terjaga karena ArrayList mempertahankan urutan elemen.
    Jadi kalau getRecentOrder(index) dipanggil sering, ArrayList jauh lebih cocok.

    ### OrderKey: jadikan immutable

    Masalah utama:

    class OrderKey {
        String region;
        long orderId;
    }

    Setelah key dimasukkan ke HashMap:
    ordersByKey.put(key, order);

    kalau region atau orderId berubah, hashCode() juga berubah.
    Contoh:

    key:
    region = "ID"
    orderId = 100

    hashCode() → X
        ↓
    HashMap menaruh key di bucket X

    Kemudian:
    key.region = "SG";

    Sekarang:

    hashCode() → Y

    HashMap masih menyimpan object tersebut di bucket X, tetapi ketika melakukan:

    ordersByKey.get(key)

    HashMap mencari bucket Y.

    Akibatnya key yang sebenarnya ada bisa terlihat seperti tidak ada.
    Perbaikannya:

    public final class OrderKey {
        private final String region;
        private final long orderId;


        public OrderKey(String region, long orderId) {
            this.region = Objects.requireNonNull(region);
            this.orderId = orderId;
        }


        public String getRegion() {
            return region;
        }


        public long getOrderId() {
            return orderId;
        }


        @Override
        public boolean equals(Object o) {
            if (!(o instanceof OrderKey k)) return false;


            return orderId == k.orderId
                    && region.equals(k.region);
        }


        @Override
        public int hashCode() {
            return Objects.hash(region, orderId);
        }
    }

    Intinya:

    Field yang digunakan oleh equals() dan hashCode() sebagai HashMap key sebaiknya immutable selama object tersebut menjadi key.

    Kontrak pentingnya:

    a.equals(b) == true
    a.hashCode() == b.hashCode()

    Tetapi kebalikannya tidak wajib:

    hashCode sama
    ≠
    equals pasti true
    Hasil akhir OrderCache

    public class OrderCache {


        private final List<Order> recentOrders = new ArrayList<>();
        private final Map<OrderKey, Order> ordersByKey = new HashMap<>();


        public Order getRecentOrder(int index) {
            return recentOrders.get(index); // O(1)
        }


        public void indexOrder(OrderKey key, Order order) {
            ordersByKey.put(key, order); // O(1) average
        }
    }

**Bagian 2 — Diagnosis.** Anda menemukan bug production: sebuah `Map<Customer, List<Order>>` kadang-kadang `get(customer)` balikin `null` walau customer itu jelas-jelas sudah pernah di-`put()` sebelumnya (dibuktikan dari log). Tim curiga ada race condition, tapi aplikasinya single-threaded. `Customer` adalah entity JPA biasa dengan `equals()`/`hashCode()` berbasis seluruh field (`name`, `email`, `loyaltyPoints`, dst — bukan cuma `id`), dan `loyaltyPoints` di-update tiap kali customer itu transaksi. Jelaskan akar masalahnya (tanpa lihat lagi jawaban Theory di atas — coba rekonstruksi alurnya sendiri), dan usulkan perbaikan yang tepat.

    Ini bukan race condition. Masalahnya adalah mutable object digunakan sebagai HashMap key.

    Misalnya awalnya:
    Customer customer = new Customer(
        "Sopian",
        "sopian@mail.com",
        100
    );

    Kemudian:

    map.put(customer, orders);
    Saat itu hashCode() dihitung berdasarkan:

    name
    email
    loyaltyPoints = 100

    Misalnya:

    hashCode = X
    HashMap menyimpan customer di bucket berdasarkan X.
    Kemudian customer melakukan transaksi:
    customer.setLoyaltyPoints(200);

    Karena loyaltyPoints ikut digunakan oleh hashCode():

    sebelum:
    loyaltyPoints = 100
    hashCode = X

    sesudah:
    loyaltyPoints = 200
    hashCode = Y

    Sekarang:

    map.get(customer)

    mencari bucket Y.
    Padahal entry-nya masih berada di bucket X.

    Akibatnya:
    map.get(customer) // null

    Padahal log menunjukkan customer memang pernah di-put().
    Perbaikan

    Jangan menggunakan seluruh mutable state entity sebagai identitas map key.

    Gunakan immutable business identifier, biasanya customerId.

    Misalnya:

    Map<Long, List<Order>> ordersByCustomerId = new HashMap<>();

    ordersByCustomerId.put(customer.getId(), orders);

    List<Order> orders =
            ordersByCustomerId.get(customer.getId());

    Atau jika memang membutuhkan Customer sebagai key, equals()/hashCode() harus dirancang berdasarkan identifier yang stabil dan tidak berubah selama object digunakan sebagai key.

### Interview Questions

1. **Kenapa `HashMap.get()` disebut O(1) rata-rata, tapi bisa jadi O(n) atau O(log n) di kasus terburuk?** Kaitkan dengan collision dan mekanisme treeify Java 8+.
    Karena HashMap menggunakan hashCode() untuk langsung menentukan bucket tempat key berada.

    key → hashCode() → bucket → entry
    Rata-rata: O(1), karena distribusi hash cukup baik sehingga bucket berisi sedikit entry.
    Collision: beberapa key masuk bucket yang sama → harus mencari di antara entry tersebut → bisa O(n).
    Java 8+: jika collision dalam satu bucket mencapai kondisi tertentu, bucket dapat di-treeify menjadi Red-Black Tree → pencarian menjadi O(log n).

    Jadi:

    normal       → O(1) average
    collision    → O(n) worst case
    treeified    → O(log n)

2. **Kalau Anda override `equals()` di sebuah class tapi TIDAK override `hashCode()`, apa yang sebenarnya masih dipakai `hashCode()`-nya, dan kenapa itu merusak `HashMap`?**
    hashCode() yang diwarisi tetap berasal dari Object, sehingga biasanya berdasarkan identity object, bukan berdasarkan field yang digunakan equals().

    Contoh:

    User a = new User("Sopian");
    User b = new User("Sopian");

    a.equals(b) == true

    Tetapi bisa:

    a.hashCode() ≠ b.hashCode()

    Ini melanggar kontrak:

    Jika a.equals(b) true, maka a.hashCode() wajib sama dengan b.hashCode().

    Akibatnya HashMap bisa mencari b di bucket yang berbeda dari tempat a disimpan.

    map.put(a, value);

    map.get(b); // bisa null

3. **Kenapa `TreeMap` butuh key yang `Comparable` sementara `HashMap` tidak?** Jelaskan dari cara masing-masing struktur data mencari posisi entry-nya.
    Karena cara mereka menentukan posisi berbeda.

    HashMap:
        key
        ↓
        hashCode()
        ↓
        bucket

        Tidak perlu tahu apakah A < B atau A > B.

    TreeMap:

        key
        ↓
        compareTo() / Comparator
        ↓
        kiri / kanan
        ↓
        kiri / kanan...

        TreeMap adalah sorted tree, jadi harus bisa menentukan:

        key baru < key sekarang → ke kiri
        key baru > key sekarang → ke kanan
        key baru = key sekarang → entry ditemukan

        Karena itu key harus punya ordering melalui Comparable atau Comparator.

    HashMap membutuhkan hashing; TreeMap membutuhkan ordering.
