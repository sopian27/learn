# 7.3 — Anatomi Sesi Vibe Coding yang Baik

### Quiz

1. Kenapa tahap "Observe" adalah tahap yang paling gampang dilakukan secara dangkal di vibe coding, dan kenapa itu berbahaya secara SPESIFIK — bukan cuma "kurang teliti secara umum"? Kaitkan dengan konsep "lapis verifikasi" dari Theory.
    Karena Observe terlihat seperti aktivitas pasif: melihat terminal "success", melihat test hijau, melihat output yang tampak masuk akal, lalu merasa selesai. Masalah spesifiknya: Observe adalah lapisan yang menentukan apakah evidence benar-benar membuktikan intent, bukan sekadar apakah program "jalan".

2. Setuju atau tidak dengan klaim ini, dan kenapa: "Sesi vibe coding yang bagus adalah sesi yang loop describe→run→observe→iterate-nya paling CEPAT (paling sedikit iterasi/waktu)."
   Tidak setuju. Kecepatan loop bukan metric utama. Yang lebih tepat: Sesi vibe coding yang bagus adalah sesi yang memiliki feedback loop secepat mungkin TANPA menurunkan kualitas verifikasi yang dibutuhkan oleh stakes-nya.

3. Claude Code mempercepat infrastruktur loop (auto-run tool, auto-accept edit di sandbox). Kenapa percepatan infrastruktur ini TIDAK otomatis membuat sesi vibe coding lebih aman? Kaitkan jawabanmu dengan matrix stakes vs reversibility dari 7.2.
   Karena Claude Code mempercepat execution, bukan otomatis memperkuat judgment dan verification. contoh nulis ulang CSS styling di production itu high-visibility tapi reversible (gampang di-revert commit) dan low stakes riil (tidak ada data/uang yang hilang kalau salah) — beda jauh dari migration SQL yang drop kolom (irreversible begitu dijalankan, meski "cuma 1 baris SQL").

### Exercise — Diagnosis Loop yang Gagal

Untuk tiap skenario, tentukan tahap mana (Describe / Run / Observe / Iterate) yang gagal dieksekusi dengan benar, dan jelaskan konsekuensinya:

1. User minta Claude Code "bikin fungsi validasi format email", Claude generate kode-nya, user langsung commit tanpa menjalankan sama sekali.
    Tahap yang gagal: Run
    Tidak ada evidence bahwa kode bahkan bisa berjalan. Bisa saja ada compile error, runtime error, atau behavior yang salah. Karena kode tidak pernah di-run, tidak ada lapis verifikasi sama sekali—kita hanya memiliki hasil generate dari Claude, bukan bukti bahwa implementasinya benar. Akibatnya, tahap Observe juga tidak bisa dilakukan karena tidak ada hasil eksekusi yang dapat diverifikasi.

2. Script gagal jalan (exception muncul di terminal), user cuma bilang ke Claude "masih error, coba lagi" tanpa paste pesan error-nya.
    tahap yang gagal: Iterate

    Pesan error adalah input penting bagi Iterate. Tanpa itu, Claude harus menebak.
    Konsekuensinya:
    diagnosis menjadi spekulatif;
    iterasi bisa semakin menjauh dari root cause;
    jumlah iterasi meningkat;
    AI bisa melakukan perubahan yang tidak relevan.

3. User describe intent "buat script backup semua file di folder ini ke folder `backup/`", tidak menyebut bahwa folder `backup/` sudah berisi file dari backup sebelumnya yang tidak boleh ketimpa — Claude generate script yang overwrite semua file tanpa cek.
    Tahap yang gagal: Describe

    Constraint penting tidak disebutkan dalam Describe: file yang sudah ada di backup/ tidak boleh ditimpa. Akibatnya, Claude dapat menghasilkan script yang secara literal sesuai dengan instruction yang diberikan, tetapi tidak sesuai dengan actual intent.
    Dalam konteks auto-run/auto-accept, risikonya menjadi lebih besar karena Claude Code dapat langsung menjalankan script dan menerima perubahan secara otomatis, sehingga requirement yang tidak pernah dinyatakan di Describe tidak akan tiba-tiba muncul sebagai guardrail. Automation hanya mempercepat eksekusi terhadap specification yang diberikan; ia tidak dapat memverifikasi constraint yang tidak pernah di-describe. Akibatnya, script bisa langsung melakukan overwrite sebelum user menyadari bahwa requirement penting tadi belum pernah masuk ke loop.

4. User run script, outputnya bilang "sukses: 100 file diproses", user langsung anggap selesai dan ship — padahal folder source sebenarnya cuma berisi 80 file (ada file yang diproses dobel akibat bug loop).
    Tahap yang gagal: Observe

    Run berhasil secara teknis.
    Output juga terlihat sukses:
    Tetapi user tidak melakukan cross-check terhadap expected state.
    Akibatnya bug loop lolos dan masuk ke production/shipped state.
