3. Agent `sonarqube-reviewer` secara eksplisit didesain sebagai "reviewer, bukan fixer".     Masalahnya adalah tidak ada separation of validation. Agent memiliki kepentingan untuk menganggap tindakannya berhasil dan mungkin tidak menyadari atau melaporkan kegagalannya sendiri.
    Dengan sonarqube-reviewer:
    Agent A → melakukan perubahan

    execution ≠ verification.
    Kode yang berhasil compile, test yang pass, atau agent yang mengatakan "done" belum otomatis membuktikan bahwa perubahan aman dan sesuai spec.

4. Target coverage 92% (dari data yang dikutip di 8.1) itu rule of thumb, bukan angka mutlak. Kasih satu contoh konkret (dari pengalaman/konteks kerja kamu sendiri atau hipotetis yang realistis) jenis kode di mana target itu HARUS lebih tinggi dari 92%, dan satu contoh di mana target itu boleh lebih rendah. Jelaskan alasannya pakai matrix stakes vs reversibility dari 7.2.
    Contoh target lebih tinggi dari 92%
    Misalnya kode yang menangani perhitungan saldo atau transaksi finansial. Saya akan menargetkan misalnya 98–100% untuk business-critical paths, terutama:
    - perhitungan saldo,
    - debit/kredit,
    - idempotency,
    - rollback,
    - boundary conditions,
    - authorization.
    Alasannya, kode ini masuk kategori high-stakes. Kesalahan bisa menyebabkan kerugian finansial dan mungkin sulit atau bahkan tidak mungkin diperbaiki setelah transaksi terjadi. Dalam matrix stakes vs reversibility:
    High stakes + low reversibility → membutuhkan verification lebih ketat.

    Contoh target boleh lebih rendah
    Misalnya kode untuk UI internal sederhana, seperti formatter untuk menampilkan tanggal atau helper untuk menghasilkan label pada halaman admin.
    Target misalnya 80–85% bisa reasonable jika:
    - dampaknya rendah,
    - mudah terlihat oleh user,
    - mudah diperbaiki,
    - perubahan bisa langsung di-revert,
    - dan tidak menyentuh data kritis.
    Alasannya : Low stakes + high reversibility → verification dapat lebih ringan.

    resource exhaustion (DoS).

    Walaupun SSRF sudah dicegah, attacker masih bisa memberikan URL ke server yang mengembalikan response sangat besar atau sengaja lambat.

    Mitigasi

    HTTP timeout = 5 seconds

    checklist security :

    Dependencies → parser/HTTP library harus diperiksa terhadap vulnerability.
    Rate limiting/resource limits → timeout, maximum response size, dan concurrency limit.
