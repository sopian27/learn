### mini latihan tulis
Sebelum exercise formal — coba tulis draft frontmatter (name + description saja, belum body) buat skill hipotetis: "review PR sesuai gaya tim lo sendiri" (nanti ini calon Mini Project Module 4).
  name : pr-review
  descrption :  Review pull requests against our team's coding, architecture, and review conventions defined in CLAUDE.md and project documentation. Use when reviewing PRs to ensure changes follow team-specific standards before merging.

### Exercises
1. Tulis description buat skill "generate SQL migration dari perubahan schema Prisma" — harus spesifik, ada trigger phrase kayak contoh di atas.
   description : Generate SQL database migrations from Prisma schema changes while following project database standards. Use when the Prisma schema has been modified and a database migration needs to be generated.

2. Klasifikasi level: skill dokumentasi API internal 500 baris (banyak endpoint). Bagian mana taruh Level 2 (SKILL.md body) vs Level 3 (references/)? Kenapa?
   Level 2 — SKILL.md
      1. Identify the REST endpoint being created or modified.
      2. Check request/response structure, validation, error handling, and HTTP semantics.
      3. Follow the team's OpenAPI conventions.
      4. If the endpoint is an internal API, consult the relevant reference documentation.
      5. Validate the OpenAPI definition before completing the change.
   level 3 : reference/api-internal-500.md

3. Bug hunt: description ini kenapa gagal reliable trigger — "description: Helps with testing" — sebutin minimal 2 alasan konkret.
Kerjain, gue review.
   Karena model sulit menentukan relevansi skill. Selain terlalu general, description yang tidak memiliki trigger keyword dapat menyebabkan collision dengan skill lain atau membuat skill tidak ter-trigger sama sekali.

### Interview Questions (mikir dulu, jangan langsung buka)
1. Kenapa description skill signifikan lebih penting dari isi body-nya buat reliability sistem?
   Description sangat penting karena menjadi sinyal utama untuk skill discovery. Jika description buruk kegagalannya bersifat silent: skill bisa tidak pernah dipanggil sama sekali tanpa error atau warning. Akibatnya user hanya melihat Claude tidak menggunakan skill tersebut.

2. Trade-off: skill vs subagent vs slash command — kapan masing-masing dipilih?
   skill: knowledge yang di-load ke main thread context untuk membantu mengerjakan task.
   subagent: agent dengan context terisolasi yang digunakan untuk mendelegasikan pekerjaan dan melindungi context utama.
   slash command: Slash command adalah explicit action yang dipanggil langsung oleh user, sehingga trigger-nya deterministik, berbeda dengan skill yang dipilih berdasarkan kecocokan description secara probabilistik.

3. Staff-level: gimana desain description biar gak collide/overlap sama skill lain yang mirip topik?
   1. scope boundary : Do not use for OpenAI, Gemini, or other providers.
   2. Gunakan keyword/entity yang spesifik : Use when writing JUnit tests for Spring Boot services using Mockito.
   3. Cek collision dengan skill lain : Jangan hanya melihat skill sendiri. Bandingkan descriptions-nya.
