### Quiz

1. Kaitkan definisi "agentic" dari Karpathy (developer tidak menulis kode langsung 99% dari waktu, tapi orchestrating + acting as oversight) ke SATU mekanisme spesifik Modul 3 (subagent / Plan Mode / Background Agent / MCP / Hooks / Permission Model). Kenapa mekanisme itu yang paling literal mewujudkan definisi tersebut, dibanding mekanisme Modul 3 yang lain?
    Definisi agentic Karpathy adalah developer tidak lagi menulis setiap detail kode, melainkan mendelegasikan pekerjaan ke agent lalu mengorkestrasi dan mengawasi hasilnya. Dari mekanisme Modul 3, subagent paling literal karena secara langsung mengubah pola:
    developer → menulis kode
    menjadi:
    developer → memberi task/delegasi → subagent mengerjakan → developer mengawasi/menggabungkan hasil.
    Plan Mode lebih berfungsi sebagai mekanisme planning, Background Agent sebagai eksekusi asynchronous, MCP sebagai akses ke tools/data, Hooks sebagai automation, dan Permission Model sebagai kontrol akses. Semuanya mendukung agentic workflow, tetapi subagent adalah mekanisme yang secara langsung mewujudkan delegation + orchestration.

2. Karpathy bilang di level atas, technical mastery "even more of a multiplier than before" — bukan less. Kaitkan ke paradox overconfidence Stanford (8.1): kenapa orchestrating banyak agent secara paralel justru MEMPERBESAR taruhan paradox itu, bukan memperkecilnya?
    Justru karena jumlah agent bertambah, volume output meningkat lebih cepat daripada kemampuan manusia untuk memverifikasinya.
    Misalnya satu agent menghasilkan 5 perubahan dan kita punya kapasitas review yang cukup. Tetapi kalau 10 agent paralel menghasilkan 50 perubahan. Di sinilah paradox Stanford menjadi lebih berbahaya: AI meningkatkan kemampuan produksi, tetapi manusia bisa menjadi terlalu percaya diri terhadap kemampuan AI sekaligus meremehkan kebutuhan technical mastery. Padahal ketika orchestration scale naik, masalahnya bukan lagi:
    "Apakah agent bisa membuat kode?"
    melainkan:
    "Apakah saya cukup mengerti sistem untuk mendeteksi bahwa 10 agent menghasilkan perubahan yang salah secara kolektif?"
    Jadi technical mastery justru menjadi multiplier yang semakin penting. Tanpa pemahaman teknis, itu hanya vibe coding paralel.

3. 5 tahap SDD (8.2) dan 3 gerbang verifikasi (8.3) awalnya dirancang untuk konteks satu sesi/satu agent. Kalau sekarang ada armada agent paralel, apa yang HARUS berubah dari cara menerapkannya (disesuaikan skalanya, bukan dibuang)? Kaitkan jawabanmu ke insiden Replit soal siapa yang boleh punya akses apa.
    Prinsipnya tidak dibuang, tetapi unit verifikasinya berubah dari:
    1 agent → 1 task → 1 verification
    menjadi:
    fleet → task boundaries → individual verification → integration verification → final human approval
    Contohnya:
    Agent : Setiap agent tetap punya spec yang jelas
    Task  : Setiap agent punya scope dan acceptance criteria sendiri
    Verification : Setiap agent melewati 3 gerbang
    Integration : Hasil antar-agent diverifikasi bersama
    Fleet : Human memverifikasi apakah seluruh perubahan memenuhi system-level spec

    Yang paling penting adalah permission boundary ikut di-scale. Insiden Replit menunjukkan masalah bukan sekadar "agent membuat kesalahan", tetapi agent memiliki akses yang terlalu besar dibandingkan pekerjaan yang seharusnya dilakukan. Ketika jumlah agent meningkat, ketiganya harus menjadi control system, bukan sekadar checklist individual.

4. Karpathy bedakan "vibe coding ships fast but ships slop" vs "agentic engineering ships fast and ships quality". Dari pengalaman/konteks kerjamu sendiri (bukan definisi generik) — satu kebiasaan kerja KONKRET apa yang membedakan satu sesi orchestrating banyak agent jadi "ships quality" ketimbang "ships slop lebih banyak sekaligus"?
    Jangan membiarkan agent langsung masuk implementation setelah requirement diberikan. Paksa setiap agent menghasilkan Task Plan terlebih dahulu, lalu lakukan review/approval sebelum coding. Ini penting terutama ketika banyak agent paralel. Misalnya ada 5 agent:
    Agent A: API
    Agent B: database
    Agent C: test
    Agent D: Kubernetes
    Agent E: documentation

    Kalau semuanya langsung coding, kita bisa mendapatkan 5 perubahan yang masing-masing terlihat masuk akal tetapi secara sistem saling bertentangan.
    Dengan checkpoint:
    Requirement → Spec → Task Plan → Human approval → Implementation → Verification → PR

    developer punya kesempatan untuk menemukan kesalahan sebelum biaya implementasi dan konflik antar-agent membesar. Jadi perbedaan utamanya bukan:
    "Saya menggunakan 5 agent vs 1 agent."
    Tetapi:
    "Saya menggunakan 5 agent dengan 5 output yang tidak terkontrol, atau 5 agent yang masing-masing bekerja di dalam boundary dan checkpoint yang jelas."
    Itulah yang membuat orchestration menjadi agentic engineering, bukan sekadar vibe coding yang diparalelkan.

### Exercise — Rancang Alur Agentic Engineering

Ambil scope yang lebih besar dari Mini Project Modul 7 (bukan 1 tool tunggal) — misal fitur dengan 3 bagian yang bisa independen: (1) fetch & parse data dari sumber luar, (2) simpan hasilnya ke storage, (3) expose lewat CLI/API sederhana untuk baca kembali. **Rancang alur ORKESTRASI-nya (bukan kodenya):**

1. **Spec design** — tulis define intent + minimal 3 poin remove ambiguity untuk scope gabungan ini (ringkas, fokus ke pembagian tugas, bukan detail implementasi tiap bagian).
    Intent:
    Membangun satu pipeline data sederhana yang mengambil data dari sumber luar, menormalisasi hasilnya, menyimpannya secara durable, lalu menyediakan interface CLI/API untuk mengambil kembali data yang sudah tersimpan.

    Remove ambiguity:
    1. Contract antarbagian
    - Fetch/parse menghasilkan struktur data yang sudah dinormalisasi.
    - Storage menerima struktur tersebut dan bertanggung jawab terhadap persistence.
    - CLI/API hanya membaca dari storage, bukan langsung dari external source.
    2. Source of truth
    - Setelah data berhasil disimpan, storage menjadi source of truth untuk CLI/API.
    - CLI/API tidak boleh melakukan fetch ulang sebagai fallback tersembunyi.
    3. Failure & acceptance criteria
    - Fetch gagal → tidak boleh menghasilkan data parsial yang dianggap valid.
    - Storage gagal → pipeline harus dianggap gagal.
    - CLI/API hanya dianggap selesai jika dapat membaca data yang memang sebelumnya tersimpan.

2. **Pembagian ke agent** — bagian mana dikerjakan subagent yang mana. Jelaskan alasan pembagiannya (independensi antar bagian, tidak ada shared state yang bikin race condition).
    Agent A — Fetch/Parse
    Boleh bekerja relatif independen karena hanya menghasilkan data berdasarkan contract.

    Agent B — Storage
    Bisa dikembangkan berdasarkan data contract Agent A, tetapi tidak perlu menunggu implementasi Agent A. Agent B cukup menggunakan fixture/mock berdasarkan contract.

    Agent C — CLI/API
    Juga bisa bekerja terhadap storage contract/mock repository. Jadi tidak perlu menunggu database/storage implementation selesai.

3. **Mekanisme per bagian** — dari 3 bagian itu, mana yang cocok pakai Plan Mode dulu, mana yang cocok langsung didispatch sebagai Background Agent, mana yang cukup subagent biasa tanpa background. Jelaskan alasannya.
    Agent A — Fetch & Parse → Plan Mode terlebih dahulu
    Ini bagian yang paling tidak pasti karena bergantung pada external source. Sebelum implementation, agent perlu memetakan:
     - bentuk data external;
     - kemungkinan response/error;
     - mapping ke internal contract;
     - edge cases parsing.
    Setelah plan disetujui, baru implementation.

    Agent B — Storage → Background Agent
    Storage relatif bounded: menerima normalized data → persist → retrieve.
    Setelah contract-nya jelas, implementation-nya bisa berjalan cukup independen. Karena saya tidak perlu terus-menerus berinteraksi selama agent mengerjakan bagian yang sudah well-defined. Sementara agent berjalan, saya bisa melakukan review pada Agent A atau C.

    Agent C — CLI/API → Subagent biasa
    Saya tidak perlu menjadikannya background karena scope-nya kecil dan kemungkinan membutuhkan beberapa keputusan interface yang sebaiknya cepat saya review.
    Flow-nya:
    contract → implement → test → review.
    Jadi tidak semua task harus dipaksa menjadi Background Agent.
    Rule saya:
    semakin tinggi uncertainty → Plan Mode;
    semakin bounded dan asynchronous → Background Agent;
    semakin kecil tetapi butuh tight human feedback → subagent biasa.

4. **Titik oversight** — di titik mana KAMU (manusia) wajib review sebelum hasil satu agent dianggap boleh dipakai bagian lain (map ke 3 gerbang 8.3), dan titik mana yang bisa didelegasikan ke hook otomatis.
    Saya tidak akan menjadikan:
    agent selesai → langsung dipakai agent lain sebagai mekanisme integrasi. Setiap agent melewati 3 gerbang.

    Gerbang 1 — Review diff
    Saya review apakah perubahan benar-benar berada dalam scope.

    Gerbang 2 — Run/Observe
    Test harus dijalankan oleh mekanisme independen, bukan hanya success running.

    Gerbang 3 — Validate against spec
    Ini yang paling penting sebelum output Agent A menjadi input Agent B.
    Saya cek:
    "Apakah output ini benar-benar memenuhi contract yang disepakati?"
    Bukan sekadar:
    "Apakah programnya jalan?"
    Misalnya Agent A berhasil parsing JSON tetapi menghasilkan field date dalam format yang berbeda dari contract. Program mungkin jalan tanpa error, tetapi Agent A belum boleh dianggap selesai. Baru setelah Gerbang 3 lolos:
    Agent A output → approved contract → boleh dikonsumsi Agent B.

    Apa yang bisa di-hook otomatis?
    Hal-hal deterministic bisa didelegasikan:
    - formatting;
    - lint;
    - unit test;
    - contract/schema validation;
    - build;
    - static analysis;
    - check bahwa file di luar scope tidak berubah;
    - generated test report.

    ### revisi
    Test tidak cukup hanya dijalankan oleh mekanisme independen dan menghasilkan status PASS. Yang harus diverifikasi adalah apakah test benar-benar menguji perilaku yang diwajibkan oleh contract, terutama pada titik handoff antar-agent.

    Misalnya Agent A menghasilkan:

    {
    "id": "123",
    "date": "2026-08-16"
    }

    Contract mengatakan date harus dalam format YYYY-MM-DD. Test yang hanya membuktikan:
    JSON berhasil diparse belum cukup. Test harus membuktikan behavior seperti:
    - semua field wajib tersedia;
    - tipe setiap field benar;
    - format date sesuai contract;
    - nilai boundary/edge case ditangani;
    - malformed input ditolak dengan benar;
    - tidak ada field yang diam-diam berubah makna.

    Jadi di titik:
    Agent A → Agent B

    Gerbang 2 harus bertanya:
    "Apakah test memberikan evidence bahwa behavior output Agent A benar terhadap contract yang akan dikonsumsi Agent B?"

    Ini juga menghindari jebakan line coverage ≠ behavioral coverage. Kode AI-generated bisa memiliki coverage tinggi—bahkan target coverage seperti 92%—tetapi tetap tidak menguji behavior penting di contract boundary. Karena itu coverage menjadi indikator, bukan bukti tunggal correctness.

    Apa yang didelegasikan ke hook otomatis?
    Hook/CI cocok untuk hal-hal deterministic dan repeatable, misalnya:
    - formatting;
    - lint;
    - unit test;
    - contract/schema validation;
    - build;
    - static analysis;
    - check bahwa file di luar scope tidak berubah;
    - generated test report.

5. **Kalau salah satu agent gagal atau hasilnya salah** — siapa/apa yang harus mendeteksinya (bukan agent itu sendiri yang melaporkan "selesai")? Kaitkan jawabanmu ke insiden Replit di 8.1.

    Agent tidak boleh menjadi satu-satunya sumber kebenaran atas keberhasilannya sendiri. Kalau Agent A menghasilkan data salah tetapi test-nya juga terlalu lemah, maka Agent B harus tetap punya boundary validation sebelum menerima data tersebut. Ini penting karena insiden Replit menunjukkan problem yang lebih dalam daripada sekadar "AI coding error": agent diberi kemampuan/authority besar dan kemudian status yang dilaporkannya tidak diverifikasi secara independen. Untuk scope ini :

    - Agent A tidak boleh menyatakan sendiri bahwa data sudah valid.
    - Contract test memverifikasi bentuk data.
    - Human memverifikasi bahwa contract tersebut memang sesuai spec.
    - Agent B memverifikasi input sebelum persistence.
    - Integration test memverifikasi seluruh pipeline.
