### Quiz
1. Kenapa Veracode nemuin AI-generated code 2,74x lebih banyak vulnerability dibanding kode manusia, padahal model dilatih dari jutaan baris kode manusia (termasuk banyak kode yang aman)? Kaitkan dengan alasan spesifik dari studi (bukan cuma "AI belum sempurna").
  - AI mereplikasi pola kode yang ada, termasuk pola yang secara historis memang insecure. Training dari banyak kode manusia tidak berarti model belajar membedakan mana pola yang aman dan mana yang hanya common.
  - Model mengoptimalkan plausibility/functionality, bukan security. Kode yang terlihat benar dan memenuhi requirement belum tentu menerapkan security control dengan benar.
  - Ada kategori vulnerability tertentu yang berulang pada output AI, misalnya insecure handling of input, authentication/authorization, dan data protection.
  - AI juga dapat menghasilkan kode yang secara sintaks dan fungsional terlihat masuk akal sehingga vulnerability-nya lebih sulit terlihat saat review cepat.

2. GitClear nemuin refactoring (kode "moved") turun dari 24,1% ke 9,5% sementara copy-paste naik dari 8,3% ke 12,3% di periode yang sama. Kenapa tren ini spesifik menunjuk ke technical debt, bukan cuma "kualitas kode turun" secara umum? Kaitkan ke definisi refactoring vs duplikasi.
   Refactoring code berarti developer mengambil logic yang sudah ada lalu merestrukturisasi kode tanpa menggandakan implementasinya. Ini biasanya mengurangi fragmentasi dan menjaga satu sumber logic. Sebaliknya, copy-paste membuat implementasi yang sama muncul di beberapa tempat. Itu langsung berhubungan dengan technical debt karena setiap duplikasi menciptakan future maintenance cost: Bug fix di A → harus ingat memperbaiki B, C, D.

3. Riset Stanford nemuin developer yang pakai AI assistant justru LEBIH percaya diri soal keamanan kode mereka, padahal kodenya lebih rentan. Kaitkan paradox ini ke konsep "Observe" dari Lesson 7.3 — kenapa paradox ini      berbahaya secara SPESIFIK untuk sesi vibe coding, bukan cuma "overconfidence itu buruk" secara umum?
    Masalahnya, AI assistant bisa membuat developer merasa sudah mendapatkan validasi, padahal yang sebenarnya terjadi hanya:
    AI menghasilkan code → code terlihat masuk akal → developer percaya → lanjut iterate
    Ini berbahaya secara spesifik dalam vibe coding karena loop-nya sangat cepat dan jumlah perubahan bisa besar. Kalau Observe dilakukan berdasarkan keputusan yang dangkal, bukan berdasarkan evidence, maka false confidence ikut dipercepat.

4. Di insiden Replit, agent menghapus database production LALU melaporkan status yang menyesatkan soal apa yang terjadi. Kalau kamu cuma berpegang pada loop describe→run→observe→iterate dari 7.3, kenapa loop itu SENDIRI tidak cukup mencegah insiden ini? Apa yang harus ada di luar loop itu?
    Karena loop tidak menentukan batas tindakan yang boleh dilakukan agent. Kalau agent punya permission mengakses production, maka kesalahan fatal bisa terjadi pada tahap Run sebelum manusia sempat melakukan verification. Bahkan lebih parah, pada kasus Replit, Observe sendiri bisa unreliable karena agent melaporkan status yang menyesatkan. Jadi kita tidak bisa menganggap output agent sebagai ground truth. Karena itu, loop 7.3 harus dikelilingi oleh control layer, terutama:
    - Permission boundaries — agent tidak boleh bebas mengakses resource high-stakes.
    - Human approval gates untuk tindakan irreversible/high-impact.
    - staging environment sebelum production.
    - Backups + rollback/recovery mechanism.
    - Independent verification — jangan hanya percaya observasi/report dari agent yang melakukan tindakan.
    - Audit logs / traceability agar tindakan agent dapat diperiksa.

### Exercise — Diagnosis Kategori Risiko
Untuk tiap skenario, tentukan kategori risiko UTAMA (security flaw / technical debt / test coverage & overconfidence / credential leak), dan jelaskan alasannya dengan mengaitkan ke data/konsep di atas:

1. Developer vibe-code endpoint API auth pakai Claude Code tanpa baca implementasinya, menaruh JWT secret langsung di source code supaya "cepat testing", lalu push ke repo GitHub yang publik.
   Credential leak : JWT secret ditaruh langsung di source code lalu dipush ke public GitHub. Ini bukan sekadar security flaw pada implementasi auth; ada credential exposure yang konkret. Vibe coding mempercepat implementasi, tetapi developer tidak melakukan review terhadap secret handling. meskipun nanti di update lalu push ulang, history nya tidak akan pernah hilang.

2. Team pakai Claude Code buat generate fitur baru terus-menerus. Coverage report menunjukkan 90% line coverage, tapi bug production tetap sering lolos — termasuk bug yang seharusnya gampang ketahuan kalau ada test untuk edge case-nya.
   Test coverage & overconfidence : 90% line coverage ≠ 90% behavior teruji. Line coverage bisa tinggi sementara edge case penting sama sekali tidak diuji. Ini cocok dengan paradox Stanford: angka/indikator yang terlihat meyakinkan dapat meningkatkan confidence, padahal vulnerability/bug masih lolos.

3. Developer berulang kali menerima saran AI yang mirip dengan function yang sudah ada di codebase, alih-alih extract jadi shared utility — karena "AI yang generate, tinggal terima", bukan developer yang menulis manual.
   Technical debt : AI terus menghasilkan implementasi yang menduplikasi function yang sudah ada daripada melakukan refactoring/extraction. Ini paralel dengan temuan GitClear: refactoring/moved code turun, sementara copy-paste naik. Dampaknya adalah duplicated logic, maintenance cost, dan risiko behavior antar implementasi menjadi berbeda.

4. Tim deploy AI agent dengan akses ke database production untuk otomasi migrasi data, memberi instruksi eksplisit "jangan ubah apa pun tanpa izin", lalu tidak melakukan pengecekan independen terhadap status report yang diberikan agent setelah proses selesai.
   Security flaw : Masalah utamanya adalah agent memiliki akses ke production database untuk operasi yang berpotensi high-stakes/irreversible, sementara tim mempercayai status report agent tanpa independent verification. Ini terkait langsung dengan kasus Replit: Observe tidak cukup jika observation berasal dari agent yang melakukan tindakan. Harus ada permission boundary, approval gate, dan verification independen.
