### Exercise
1. Kamu mau setup scheduled task "tiap hari jam 9 pagi, cek inbox email, balas email rutin otomatis." Apa risiko utama kasih scope ini ke unattended task, dan gimana kamu batasi scope-nya?
   Risiko utamanya adalah unattended task bisa melakukan tindakan eksternal tanpa saya review, sehingga kalau email yang dipilih salah, instruksi email berbahaya, atau kondisi berubah, task bisa mengirim balasan yang salah atas nama saya.
   1. Hanya memilih email yang memenuhi kriteria sangat spesifik, misalnya sender tertentu + subject tertentu.
   2. Hanya membalas template yang sudah ditentukan, bukan membuat keputusan bebas.
   3. Untuk email yang ambigu/berisiko tinggi, skip

2. Kenapa scheduled/unattended task butuh notification/failure handling yang tidak dibutuhkan sesi interaktif biasa?
   karena scheduled task berjalan ketika saya tidak mengawasinya. sehingga di perlukan notification/failure terkait task nya.

3. Sebut 1 skenario kerja kamu (nyata, bukan hipotetis) yang cocok dijadiin scheduled task vs 1 yang TIDAK cocok — jelaskan kenapa pakai kriteria determinism/reversibility dari task tadi.
   cocok : Menjalankan test/build project secara rutin dan memberi laporan hasil.
   tidak cocok : Scheduled task yang otomatis membaca requirement/bug lalu langsung mengubah code dan membuat PR tanpa review.

### Interview Questions
1. "Jelaskan kenapa desain permission scheduled task harus di-lock di setup time, bukan runtime — beda dari sesi Claude Code interaktif biasa"
    Karena scheduled task akan berjalan unattended. Tidak ada manusia yang hadir untuk memberikan approval ketika task mulai berjalan. jadi kebutuhan harus jelas sebelum di eksekusi.

2. "Tim kamu mau ganti cron job Python yang jalan tiap malam jadi agentic scheduled task karena 'lebih fleksibel'. Kapan itu keputusan bagus, kapan itu downgrade reliability?"
    bagus : ketika task memang membutuhkan reasoning yang sulit atau lebih rumit jika di implementasikan via cron.
    tidak bagus : ketika task deterministik , mudah di debug dan aturan sudah jelas

3. "Scheduled task gagal 3 hari berturut-turut tanpa ketauan siapa pun. Root cause desain apa yang paling mungkin, dan gimana kamu cegah di setup berikutnya?"
   Tiga hari gagal tanpa diketahui menunjukkan failure observability tidak dirancang. Scheduled task harus punya notification, heartbeat/monitoring, retry, escalation, timeout, dan audit trail sehingga failure tidak menjadi silent failure.


### Actionable
2. Kenapa scheduled/unattended task butuh notification/failure handling yang tidak dibutuhkan sesi interaktif biasa?
   Scheduled/unattended task membutuhkan notification dan failure handling karena tidak ada manusia yang menjadi failure detector saat task berjalan. Pada sesi interaktif, saya melihat output secara real-time dan bisa langsung menyadari, menghentikan, atau memperbaiki ketika terjadi error. Pada unattended task, peran tersebut hilang, sehingga notification, logging, retry, dan escalation harus menggantikan peran manusia tersebut. Kalau tidak, task bisa gagal tanpa ada yang tahu dan menjadi silent failure.
